# taskcomm

Spring Boot стартер, инкапсулирующий таск-менеджмент и коммуникации с внешними системами.
Подключив стартер, приложение-потребитель получает: создание задач и процессоров по типам задач,
персистентность, повторы при ошибках, разбиение задач на подзадачи (`TaskUnit`) и группы подзадач
(`TaskBatch`), REST API для управления задачами, а также аналогичный механизм для коммуникаций
(процессоры по источнику/назначению) с горизонтальным масштабированием.

> **Статус: проект в начальной стадии.** Кода пока нет — этот файл описывает *целевые* правила.
> Если реальность разойдётся с написанным здесь, приоритет у этого файла: сначала обсуди
> расхождение, потом меняй правило или код.

**Грабля Spotless + palantir-java-format на Java 21.** Форматирование конструкций Java 21
(записи с распаковкой, `sealed`, pattern matching в `switch`, unnamed-паттерны `_`) у
`palantir-java-format` работает надёжно, только если **сам Gradle daemon запущен на JDK 21**
(а не только toolchain нацелен на 21) — либо если включено свойство
`palantir.native.formatter=true` в `gradle.properties`. Несовпадение версии daemon даёт
`FormatterException` на ровном месте. У нас toolchain и так Java 21 — держим `JAVA_HOME`
при сборке на JDK 21, чтобы это не всплыло.

**Не пиним** — версии приходят из BOM Spring Boot: Micrometer и его реестры, драйвер PostgreSQL,
Tomcat. Явный пин старой ветки Micrometer против Boot 3.5 ломает Actuator, а пин драйвера
вниз нарушает наше же правило «не понижать версии зависимостей».

Checkstyle обязан **разбирать синтаксис Java 21**: `sealed` с `permits` и pattern matching
в `switch` — основа дизайна, и парсер старше 2023 года на них не работает. Версии вида 10.3.x
для этого проекта непригодны.

В каталоге нет и не должно быть Spring Cloud, json-schema-validator, logback-access и logstash:
в дизайне taskcomm они не участвуют, а каждая зависимость стартера приезжает всем потребителям.

### Граница между Spotless и Checkstyle

За форматирование отвечает **только Spotless**: отступы, переносы, пробелы, положение скобок,
порядок импортов, длина строки, висячие запятые. Форматные правила из `checkstyle.xml` убраны
сознательно — два источника правды об одном приводят к тому, что Checkstyle ругается на строку,
которую только что записал Spotless.

Checkstyle отвечает за то, чего форматтер не видит: именование, структуру, сложность, Javadoc,
корректность, состав импортов. Он **заваливает сборку** (`severity=error`).

Из конфига отдельно убраны два правила, и не как форматные:

- `MissingSwitchDefault` — воркер разбирает запечатанную иерархию процессоров без ветки `default`
  ([ADR 0007](docs/adr/0007-processor-contracts.md)).
- `IllegalCatch` — воркер обязан перехватывать всё, что бросил процессор потребителя, иначе чужой
  код убьёт поток воркера.

Точечные исключения кладутся в `checkstyle-suppressions.xml` рядом с конфигом.

## Правила стартера

Это самый важный раздел: стартер подключают чужие приложения, и он не имеет права навязывать им
поведение.

- Автоконфигурации помечаются `@AutoConfiguration` и перечисляются в
  `taskcomm-autoconfigure/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.
  `spring.factories` для этого **не используется** — в Spring Boot 3 механизм удалён.
- Каждый бин объявляется явным `@Bean`-методом под `@ConditionalOnMissingBean`.
  Потребитель должен иметь возможность заменить любой наш бин своим.
- Каждая подсистема выключается свойством:
  `@ConditionalOnProperty(prefix = "taskcomm.<подсистема>", name = "enabled", havingValue = "true", matchIfMissing = true)`.
- **Никакого `@ComponentScan` в автоконфигурациях** и никаких `@Component` / `@Service` /
  `@Repository` на внутренних классах. Сканирование в стартере ломает потребителя непредсказуемым
  образом; все бины создаются вручную.
- **Не включать глобальные механизмы Spring за потребителя**: `@EnableScheduling`, `@EnableAsync`,
  `@EnableTransactionManagement` в автоконфигурациях запрещены — они меняют поведение всего
  приложения. Нужен планировщик — создавай собственный `TaskScheduler`/executor-бин.
- Порядок конфигураций задаётся через `@AutoConfiguration(after = ..., before = ...)`.
- Зависимости в `taskcomm-autoconfigure` объявляются как `compileOnly` / `optional`;
  реальные транзитивы собираются в `taskcomm-spring-boot-starter` через `api`.
- Подключён `spring-boot-configuration-processor` — свойства автодополняются в IDE потребителя.

### Свойства конфигурации

Префикс — **`taskcomm.*`**, без reverse-domain (так же, как `springdoc.*`, `resilience4j.*`).

Наборы **свои у каждой подсистемы**, общего корня нет ([ADR 0060](docs/adr/0060-retry-and-lease-configuration.md)):
общий корень стал бы первым шагом к общему коду, который запрещает
[ADR 0010](docs/adr/0010-separate-engines.md).

```yaml
taskcomm:
  enabled: true
  task:
    enabled: true
    poll: { interval: 1s, batch-size: 100, workers: 8,
            claim-order: deadline, deadline-step: 1m }   # deadline | priority | quota
    lease: { duration: 60s, heartbeat-interval: 20s, max-execution-time: 30m }
    retry: { max-attempts: 3, initial-delay: 5s, multiplier: 2.0, max-delay: 1h, jitter: 0.2 }
    types:                          # ключ — taskType
      price-update:
        priority: 50
        lease: { max-execution-time: 30m }
        retry: { max-attempts: 5 }
        phases:                     # PROCESS | EXPAND | COLLECT
          expand:
            lease: { max-execution-time: 2h }
    pollers:                        # дополнительные к основному
      urgent: { types: [order-urgent], workers: 4, claim-order: priority }
  communication:
    enabled: true
    poll: { interval: 1s, batch-size: 100, workers: 8 }
    lease: { duration: 60s, heartbeat-interval: 20s, max-execution-time: 5m }
    retry: { max-attempts: 5, initial-delay: 10s, multiplier: 2.0, max-delay: 1h, jitter: 0.2 }
    circuit-breaker:                # только исходящие; выключен по умолчанию
      enabled: false
      window: 60s
      minimum-calls: 10
      failure-rate-threshold: 0.5
      wait: { initial-delay: 30s, multiplier: 2.0, max-delay: 10m, jitter: 0.2 }
      probe: { calls: 3, timeout: 1m }
    systems:                        # ключ — имя внешней системы
      supplier-b:
        rate-limit-per-instance: 10
        retry: { max-attempts: 8 }
        failure-statuses: [5xx, 429]  # исход попытки, а не только размыкатель
        circuit-breaker: { enabled: true }
  search:
    remove-undeclared-fields: false
  results:
    discard: after   # never | immediately | after
    discard-after: 7d
  rest:
    enabled: true
    base-path: /api/taskcomm
```

**Числа здесь — отправная точка, а не рекомендация.** Их надо перепроверить нагрузкой на этапах
3–4; сейчас они выбраны правдоподобно, а не выверенно.

- Все длительности — формат `Duration` Spring Boot (`1s`, `30m`, `7d`).
- Ключ переопределения у задач — `taskType`, у коммуникаций — **имя внешней системы**: по нему же
  ищется процессор. Слова `types` у коммуникаций нет, `communicationType` отвергнут
  ([ADR 0052](docs/adr/0052-communication-transport-contracts.md)).
- `retry` и `lease` действуют **на все виды попыток** — `PROCESS`, `EXPAND`, `COLLECT`. Раскрытие
  и сборка повторяются под теми же настройками, что обработка.
- `poll` и `workers` **не переопределяются по типу задачи**: свой такт и свой пул на тип — это
  отдельная очередь под каждый тип, и заводится она выделенным поллером, а не переопределением.

### Порядок разрешения настроек

Настройки приходят из двух источников: **аннотация на процессоре** — значение по умолчанию
от автора, который знает профиль своей фазы, и **`application.yml`** — переопределение для
эксплуатации ([ADR 0061](docs/adr/0061-processor-configuration-annotations.md)).

**Пять уровней, от сильного к слабому:**

1. `yaml`: тип и фаза
2. `yaml`: тип
3. аннотация на методе
4. аннотация на классе
5. глобальное значение по умолчанию подсистемы

**Любое значение из `yaml` сильнее любой аннотации** — правило по источнику, а не по специфичности.
Обратный порядок («побеждает более специфичное») отвергнут как ловушка: эксплуатация правила бы
конфиг во время инцидента, а он молча не применялся бы к фазе с аннотацией на методе.

Фазы есть и в `yaml` именно поэтому: иначе переопределение по типу либо не доставало бы до фазы,
либо накрывало все фазы разом — включая `process`, которому положены секунды.

Аннотация задаёт всё, что и `yaml` на уровне типа, **и на классе, и на методе**; метод перекрывает
класс. `poll` и `workers` аннотацией не задаются никогда.

Аннотаций **две, по одной на подсистему** ([ADR 0066](docs/adr/0066-processor-settings-annotation-names.md)):
`@TaskProcessorSettings` в `task.api` и `@CommunicationProcessorSettings` в `communication.api`.
Общая на обе подсистемы запрещена тем же правилом, что и общий код.

**Стартер обязан печатать при старте итоговое значение по каждому типу и фазе и уровень, с которого
оно взято.** Это не удобство: пять уровней без такой печати делают вопрос «почему у меня предел
тридцать минут» вопросом без ответа.

### Проверки настроек при старте

Граница проходит по вопросу «способна ли система вообще работать с этим значением».

**Падение при старте:** `max-attempts < 1`; `initial-delay > max-delay`; `multiplier < 1`;
`jitter` вне `(0, 1]` — **включая ноль**, потому что джиттер объявлен обязательным
([ADR 0009](docs/adr/0009-retry-and-progress.md)) и настройка не должна выключать обязательное;
`max-execution-time < heartbeat-interval`; `priority <= 0`; один тип задачи назван в двух поллерах.
У размыкателя ([ADR 0065](docs/adr/0065-communication-circuit-breaker.md)): `failure-rate-threshold`
вне `(0, 1]`; `minimum-calls < 1`; `probe.calls < 1`; `window` не положительное; для `wait` — те же
правила, что для `retry`, включая запрет нулевого джиттера. Аннотация настроек не своей
подсистемы на процессоре — `@TaskProcessorSettings` на процессоре коммуникаций и наоборот
([ADR 0066](docs/adr/0066-processor-settings-annotation-names.md)).

**Предупреждение:** `heartbeat-interval > duration / 3` — громко и с рекомендуемым значением;
`duration <= poll.interval`; `batch-size > workers`; `probe.timeout` меньше предела обработки
системы; список исключений размыкателя задан у системы с выключенным размыкателем.

### Регистрация обработчиков

Потребитель объявляет процессор — одного из трёх наследников `TaskProcessor`, либо
`CommunicationProcessor` — как обычный `@Bean` или `@Component` **в своём коде**. Стартер собирает
их инъекцией `List<TaskProcessor<?>>`. Не писать `ImportBeanDefinitionRegistrar` и не сканировать
classpath — Spring уже всё нашёл.

## Доменный словарь

| Тип | Что это |
|---|---|
| `Execution` | Набор связанных действий вокруг одного повода. Агрегат над задачами и коммуникациями |
| `Task` | Задача целиком: что нужно сделать над множеством бизнес-объектов потребителя |
| `TaskBatch<B>` | Группа подзадач внутри задачи; `B` — параметры группы |
| `TaskUnit<U>` | Подзадача: обработка **одного** бизнес-объекта. Минимальная единица работы и повтора |
| `TaskProcessor<T>` | Запечатанный базовый контракт; потребитель реализует одного из трёх наследников |
| `Communication<C>` | Коммуникация с внешней системой. **Атомарна**, на части не делится |
| `CommunicationProcessor<C, R>` | Запечатанный базовый контракт по транспорту; `R` — доменная форма ответа. Пишет потребитель |

Ключевое ограничение модели: стартер **не знает и не должен знать**, какие бизнес-объекты
обрабатывает потребитель. Полезная нагрузка — параметр типа `P`, непрозрачный для стартера.
Отсюда правило именования: доменные типы называют *единицу работы и её место в иерархии*, а не
содержимое. Имена вроде `Entity`, `Record`, `Document` запрещены — они утверждают что-то про
полезную нагрузку и вдобавок сталкиваются с `jakarta.persistence.Entity` и `java.lang.Record`.

Иерархия у задач и коммуникаций **намеренно разная**: `Task → TaskBatch → TaskUnit` против плоской
`Communication`. У коммуникаций нет батчей и единиц — одна коммуникация неделима, и повтор при
ошибке применяется к ней целиком. Не «унифицировать» две модели ради симметрии и не заводить
`CommunicationBatch` / `CommunicationUnit`.

Направление — **тип, а не значение поля**:

```java
public sealed interface Communication<C> {
    record Inbound<C>(String source, C requestPayload)       implements Communication<C> {}
    record Outbound<C>(String destination, C requestPayload) implements Communication<C> {}
}
```

Невалидную коммуникацию (обе стороны пустые, обе заполненные) нельзя собрать в принципе, а процессор
разбирает направление через pattern matching. В БД по-прежнему две колонки и признак направления.

Нагрузка называется `requestPayload`, а не `payload`: доменных форм у коммуникации две — запроса
и ответа ([ADR 0055](docs/adr/0055-communication-exchange-storage.md)). У задач колонка остаётся
`payload`, и это расхождение подсистем сознательное.

Процессор ищется по внешней стороне — `source` для входящих, `destination` для исходящих.
Фактически **один процессор = один адаптер к одной внешней системе**: если в эту систему уходят
сообщения разных видов, разбирается с этим сам процессор.

### Транспортные контракты

Контракт процессора определяется **транспортом**, и иерархия запечатана дважды
([ADR 0052](docs/adr/0052-communication-transport-contracts.md)):

```java
sealed interface CommunicationProcessor<C, R>
        permits HttpCommunicationProcessor, KafkaCommunicationProcessor, RawCommunicationProcessor

sealed interface HttpCommunicationProcessor<C, R> extends CommunicationProcessor<C, R>
        permits RestCommunicationProcessor, SoapCommunicationProcessor
```

- Воркер разбирает её pattern matching'ом **без ветки `default`** — то же правило, что у задач.
- Транспорт нужен стартеру до вызова процессора: разбор тела идёт **при создании** коммуникации,
  и кодек задаёт именно контракт.
- Форма контракта — колонка `contract_shape` в `tc_communication`: `REST` | `SOAP` | `KAFKA` |
  `RAW`. Проставляется при первом захвате, несовпадение отменяет коммуникацию — как у задач.
- **Транспорт не входит в ключ реестра.** Процессор по-прежнему ищется по внешней стороне;
  транспорт — проверяемое свойство найденного, иначе к одной системе оказалось бы два процессора.
- Своего транспорта потребитель добавить не может: для экзотики есть `RawCommunicationProcessor`
  с сырым текстом.
- **Заголовки в контрактах процессоров — только свой нейтральный тип** поверх
  `Map<String, List<String>>`. Перегрузка с `HttpHeaders` допустима исключительно в методах приёма
  `CommunicationService`, под `@ConditionalOnClass`. `kafka-clients` в зависимостях не появляется
  никогда: тип в сигнатуре процессора необратим, потому что процессор не удаляется никогда.

### Приём входящих

Входящие коммуникации создаёт потребитель — из своего контроллера или слушателя, через API
стартера. Собственного приёмного endpoint стартер не даёт. Режимов **два**, выбирает потребитель
([ADR 0053](docs/adr/0053-inbound-reception-modes.md)):

- **Синхронный.** Процессор вызывается прямо в потоке контроллера. Аренды и heartbeat нет —
  претендовать на работу некому. **Попытка одна, повторов нет.** И успех, и ошибка записываются
  и возвращаются вызывающему, чтобы тот отдал результат внешней системе. Коммуникация терминальна
  сразу.
- **Асинхронный.** Контроллер заполняет и поля запроса, и поля ответа — ответом служит то, что он
  сам собирается отдать, — и отвечает внешней системе сам. **Процессор ответа не формирует**, это
  договорённость. Настоящий ответ уйдёт позже отдельной исходящей коммуникацией.

Разбор тела — **при создании**, на уровне `CommunicationService`, в потоке контроллера: только так
callback на неразбираемое тело успевает вернуть ошибку в правильном формате. В БД ложатся **обе
формы** — сырая текстом и доменная в `jsonb`; воркер берёт доменную и текст заново не разбирает.

**Неразбираемое тело — коммуникация создаётся сразу `FAILED`**, с попыткой, причиной, сырым телом
и отданным ответом. Повторов нет: текст не станет валидным сам собой.

Приём принимает **неизменяемое значение-запрос**, а запускает метод сервиса. Самозапускающегося
билдера нет сознательно: забытый терминальный вызов молча терял бы коммуникацию, а Java не умеет
`must_use`. Типов запроса два, и у синхронного нет полей ответа — противоречие ловит компилятор.

**Асинхронный ответ на исходящую — это новая входящая коммуникация**, находящая исходный
`Execution` через реестр корреляции. Дописывать ответ в закрытую попытку нельзя и не нужно.

### Хранение обмена

Запрос и ответ целиком лежат **в строке попытки**, колонками прямо в `tc_communication_attempt`
([ADR 0055](docs/adr/0055-communication-exchange-storage.md)). Отдельной таблицы нет: связь 1:1
по построению, а партиционирование и дроп вместе с агрегатом достаются бесплатно.

`request_id`, `request_at`, `request_headers`, `request_body`, `response_id`, `response_at`,
`response_status`, `response_headers`, `response_body`, `response_payload`.

- **Смысл направление-зависимый**: у входящей запрос — то, что прислали нам, ответ — то, что
  ответили мы; у исходящей наоборот.
- **Тела — `text`, оба.** Внешняя система отвечает чем угодно: JSON, XML, HTML от балансировщика,
  пустое тело. `jsonb` уронил бы запись именно на том сообщении, ради которого разбор и затевают.
  **Двоичные форматы кладутся base64** — и это обязано быть в комментарии к колонке.
- `request_at` / `response_at` — **свои колонки**, а не `started_at` / `finished_at` попытки:
  между захватом и отправкой процессор строит запрос и ждёт ограничитель скорости.
- `response_status` осмыслен у REST и SOAP, у брокеров пуст. Пустая половина строки — нормальное
  состояние, а не потеря данных.
- **Повтор входящей копирует `request_*` в новую попытку** (запрос пришёл один раз и не меняется);
  у исходящей копирования нет — каждая попытка строит свой запрос.
- Запись идёт **двумя каналами**: внутри процессора — методами `CommunicationContext`, вне —
  при создании коммуникации. Каждая запись **немедленно, своей короткой транзакцией**: копить
  до конца попытки нельзя, иначе падение после отправки сотрёт то, ради чего всё писалось.
  В свою попытку воркер вправе писать всегда, даже потеряв аренду.
- **Индекс по `request_id` есть** — под разбор инцидентов и поиск через REST. Ключа
  партиционирования в таком запросе нет, поэтому лукап обходит все партиции; это операция разбора,
  а не горячий путь, и **переиспользовать её в захвате или диспетчеризации нельзя**.
- **Очистки тел нет.** `taskcomm.results.discard` — только про результаты детей у задач; тела
  коммуникаций уходят с дропом партиции. Это осознанно, хотя тела и самое объёмное в схеме.

**Дедупликация входящих делится пополам.** Потребитель извлекает ключ идемпотентности из сообщения
(формат знает только он: заголовок, `messageId`, хеш). Стартер гарантирует, что второй коммуникации
с таким ключом не появится: уникальный индекс `(source, dedup_key)` в **отдельной
непартиционированной** таблице `tc_communication_dedup` — см. раздел «Партиционирование и очистка»,
— приём через `ON CONFLICT DO NOTHING` с возвратом существующей. Ключ необязателен — не передали,
дедупликации нет. Это **не** отменяет требования идемпотентности к процессору: дедупликация защищает от повторной
доставки внешней системой, идемпотентность — от повторного выполнения по истёкшей аренде.

Порядок выполнения коммуникаций **не гарантируется**, всё идёт параллельно. Ключа упорядочивания
нет; если понадобится — это переделка захвата, а не добавление колонки.

Ограничение скорости встроено и настраивается для каждого процессора. Лимит действует
**на экземпляр приложения**, и свойство называется `rate-limit-per-instance` — имя не должно врать,
потому что три инстанса с лимитом 10 дадут внешней системе 30. Распределённый лимит можно добавить
позже, не переименовывая существующее свойство.

### Исход попытки по ответу и размыкатель

Правила из [ADR 0065](docs/adr/0065-communication-circuit-breaker.md).

**У коммуникаций успех — не просто нормальный возврат.** Записанный ответ с отказным статусом делает
попытку `FAILED` со всеми последствиями, включая повтор, даже если процессор вернулся нормально.
`status_description` при этом пишет стартер из ответа («ответ 503»). Правило действует **всегда**,
включён размыкатель или нет. У задач успех по-прежнему — отсутствие исключения; расхождение
сознательное.

- Отказные статусы — `failure-statuses` в `systems.<имя>`, **вне** `circuit-breaker`. По умолчанию
  зависят от транспорта: `5xx` и `429` у REST и SOAP (`4xx` не всегда проблема системы), **пусто
  у RAW** — смысл статуса знает только автор процессора, — у Kafka статуса нет.
- REST- или SOAP-процессор вернулся нормально, не записав ответ, — `SUCCEEDED` и WARN.

**Размыкатель — только у исходящих**, ключ — `destination`, **выключен по умолчанию**: пороги
не проверены нагрузкой, а размыкатель с неверными порогами молча перестаёт отправлять в исправную
систему. У входящих его нет: процессор входящей в `source` не ходит, и его отказы говорят о нас,
а не о ней.

- **Что считается.** Отказ — исключение из списка (пустой список, по умолчанию, — все исключения;
  сужается аннотацией на процессоре или в `yaml`, `yaml` сильнее) и отказной статус. Успех —
  нормальный возврат без отказного статуса. **Не считаются вовсе** исключение после `doNotRetry`
  и превышение предела обработки. Исключение вне списка всё равно делает попытку `FAILED` —
  список сужает только размыкатель.
- **Размыкание** — по доле отказов за окно времени при минимальном числе вызовов.
- **Разомкнутая система не захватывается**: её набор передаётся в запрос захвата тем же условием,
  каким основной поллер исключает системы выделенных. Попытки не сгорают — строку никто
  не захватил. Выделенный поллер, у которого разомкнуты все системы, в БД не ходит вовсе.
- **Возврат.** Ожидание до пробы растёт по правилам backoff, с обязательным джиттером. Проба —
  **отдельный захват `LIMIT k`** по этой системе, а не снятие фильтра: строки системы самые старые,
  и первый захват забрал бы ими весь `batch-size`. Проба удалась, только если **все `k`** вызовов
  успешны. У пробы **свой срок**: не дождались всех исходов — снова размыкаем.
- **Состояние — в памяти экземпляра.** Синхронизация между экземплярами желательна и будет
  отдельным решением; свойство всё равно называется `circuit-breaker`, без `-per-instance`, и при
  синхронизации его смысл изменится — это объявляется в заметках к версии.
- **REST — только чтение**: состояние ответившего экземпляра с его именем в выдаче. Ручное
  размыкание и замыкание — вместе с синхронизацией, и **разовые**: перевести сейчас, дальше
  автоматика.
- Индикатор здоровья размыкатель **не трогает**; `oldest_claimable_age` разомкнутой системы
  не исправляется — её сообщения действительно опаздывают.
- Поток процессора не прерывается никогда: «прервали по времени» значит «закрыли попытку».
  От зависания без таймаута размыкатель не защищает — таймаут на клиенте обязан ставить
  потребитель, см. [consumer-contract.md](docs/consumer-contract.md).

**Задачи и коммуникации — две независимые реализации.** Захват, повторы и SQL у них похожи, но
общего кода между подсистемами нет и не должно быть. Дублирование здесь сознательное: подсистемы
обязаны меняться независимо. Не выносить `SKIP LOCKED`-захват, политику повторов и работу с арендой
в общий класс, даже если код выглядит одинаковым.

Расхождение уже перестало быть теоретическим: **у коммуникаций строка попытки создаётся вместе
с сущностью, а захват стал одноветочным** ([ADR 0054](docs/adr/0054-communication-attempt-lifecycle.md)).
Запросы захвата у подсистем разные по форме, и переносить форму одной на другую нельзя.

Так же запрещены имена, конфликтующие с ключевыми типами платформы и Spring: `TaskExecutor`
(есть `org.springframework.core.task.TaskExecutor`), `Package` (есть `java.lang.Package`,
и `package` — ключевое слово Java). По этому же правилу отвергнуто имя `Case` для агрегата —
`case` тоже ключевое слово ([ADR 0038](docs/adr/0038-execution-aggregate.md)).

### Агрегат `Execution`

Единственное, что общего у двух подсистем, — и оно **пассивно**: ни один движок не читает
`Execution` для захвата, повторов или аренды. Общего кода не появляется, появляется общее значение
([ADR 0038](docs/adr/0038-execution-aggregate.md)).

- Таблица `tc_execution`: `id`, `created_at`, `updated_at`. **Ни статуса, ни счётчиков,
  ни прогресса.** Агрегат не завершается и не отменяется — он живёт столько же, сколько сущности
  внутри него. Восемь статусов есть у задач, у `Execution` их ноль, и это не недоделка.
- **Корнями бывают только `Task` и `Communication`.** `TaskBatch` и `TaskUnit` рождаются только
  внутри `expand` / `expandBatch`, то есть всегда при живом родителе, и собственный `Execution`
  не создают никогда.
- Сущность создана **вне процессора** — заводится новый `Execution`. Создана **внутри
  процессора** — попадает в `Execution` обрабатываемого родителя.
- Потребитель может явно отказаться от привязки; тогда заводится **новый** `Execution`, а не
  «никакого». Обе колонки обязательны, но по разным основаниям: `execution_created_at` — потому
  что это ключ партиционирования и без него строку некуда положить, `execution_id` — потому что
  иначе строка лежала бы в партиции агрегата, не принадлежа никакому агрегату.
- Текущий `Execution` передаётся **неявно**, через контекст обработки, и снимается восстановлением
  снимка — тем же механизмом и в том же месте, что MDC. Отсюда ограничение, о котором обязан знать
  потребитель: **смены потока привязка не переживает.** Задача, созданная из чужого пула внутри
  `process()`, молча получит новый `Execution`.
- **Обход ловушки — явная передача** ([ADR 0056](docs/adr/0056-execution-ref.md)): `executionRef()`
  контекста обработки возвращает `ExecutionRef` — неизменяемую ссылку на текущее дело (id
  и `createdAt`, ключ партиционирования). Методы создания в `TaskService` и `CommunicationService`
  принимают её необязательным параметром из любого потока; явно переданное дело побеждает неявную
  привязку потока.
- Коммуникации дополнительно связываются через реестр корреляции
  ([ADR 0040](docs/adr/0040-communication-correlation.md)) — так асинхронный ответ, пришедший
  через час, находит дорогу в исходный `Execution`.

### Связи внутри дела

Внутри агрегата хранится **указатель на создателя**, и только он
([ADR 0064](docs/adr/0064-entity-origin-links.md)). Таблицы связей нет, closure table нет:
транзитивных запросов в сценариях не оказалось ни одного, а `Execution` **и есть** замыкание.

- Колонки `origin_type`, `origin_id`, `origin_attempt_id`, `origin_relation` — **только
  в `tc_task` и `tc_communication`**, там же, где `cancel_requested_at`, и по той же причине:
  только эти сущности появляются вне раскрытия. **Дети раскрытия к ним не имеют отношения** —
  их создатель выражен `parent_attempt_id`, и четвёртой копии иерархии не бывает.
- Значения `origin_type` — `TASK` | `BATCH` | `UNIT` | `COMMUNICATION`: словарь совпадает с `level`
  в `tc_task_attempt`, второго не заводить. `origin_relation` — `SPAWNED` (создано вызовом
  из процессора) | `RESPONSE` (колбэк, нашедший якорь по ключу корреляции).
- Связь **брат-брат — это значение `origin_relation`, а не вторая структура.** Колбэк хранится
  таким же направленным ребром; сбоку или снизу его рисовать — дело отрисовки.
- **Связь не выходит за дело.** Потребитель отказался от привязки или явно передал `ExecutionRef`
  другого дела — `origin_*` не заполняется. Отсюда инвариант: создатель всегда лежит в той же
  партиции, что и ребёнок, и читается по `(execution_created_at, origin_id)` с отсечением
  партиций.
- Новая **тихая** потеря связи, рядом с потерей дела при смене потока: чужое дело убирает и указатель,
  ошибки при этом нет. Место — в [consumer-contract.md](docs/consumer-contract.md).
- Связь **N:M выразить нельзя**: создатель у сущности один — тот, чья обработка шла в момент
  создания. Понадобится N:M — это новая таблица, а не новая колонка.
- Отсюда же закрыт вопрос «как процессор добирается до данных породившей его коммуникации»:
  `origin_id` плюс собственный `execution_created_at`, дальше обмен из строки попытки
  ([ADR 0055](docs/adr/0055-communication-exchange-storage.md)). Путь через нагрузку остаётся
  рабочим и документированным — он единственный, если от привязки отказались.

## Три контракта обработки задач

Тип задачи сам определяет, какой контракт реализует потребитель. Все три живут в `task/api`
и выбираются кодом потребителя, а не конфигурацией стартера.

1. **Плоская задача** — процессор выполняет `Task` целиком, подзадач нет.
2. **Задача с подзадачами** — `Task → TaskUnit[]`, процессор выполняет каждую подзадачу.
3. **Задача с пакетами** — `Task → TaskBatch[] → TaskUnit[]`. Батч даёт возможность один раз
   сходить во внешнюю систему за данными сразу для всей группы подзадач, вместо запроса на каждую.

Полезные нагрузки у уровней иерархии **разных типов**: `Task<T>` несёт параметры задачи
(например, диапазон дат), `TaskUnit<U>` — один бизнес-объект (например, заказ).

Контракты образуют запечатанную иерархию: `sealed interface TaskProcessor<T> permits
FlatTaskProcessor, UnitTaskProcessor, BatchTaskProcessor`. Воркер разбирает её через pattern
matching **без ветки `default`** — добавление четвёртого контракта должно ломать компиляцию во всех
местах, которые надо дописать.

**Параметров типа полный набор, и буква совпадает с уровнем** — `T`, `B`, `U` читаются как Task,
Batch, Unit, а `R` с тем же суффиксом означает результат этого уровня
([ADR 0059](docs/adr/0059-collect-contract.md)):

```java
FlatTaskProcessor<T, RT>
UnitTaskProcessor<T, U, RU, RT>
BatchTaskProcessor<T, B, U, RU, RB, RT>
```

Шесть параметров — самая тяжёлая подпись в публичном API, и это принятая цена типобезопасности.
Реализацию без комментария к каждому параметру читать нельзя, поэтому пример обязателен рядом
с контрактом. Тем же правилом названы буквы у коммуникаций: `Communication<C>`.

`ProcessingContext` идёт **параметром каждого метода**, а не полем процессора: иначе `executionRef()`
неоткуда взять ([ADR 0056](docs/adr/0056-execution-ref.md)).

**Имя интерфейса и значение `contract_shape` читаются одинаково**: `FlatTaskProcessor` → `FLAT`,
`UnitTaskProcessor` → `UNIT`, `BatchTaskProcessor` → `BATCH`. Держать это правило и при появлении
четвёртого контракта ([ADR 0045](docs/adr/0045-flat-task-processor.md)).

Реестр процессоров строится на старте из `List<TaskProcessor<?>>`. Два процессора с одинаковым
`taskType()` — падение при старте приложения, а не при первой задаче.

**Ограничение продукта: одна схема БД обслуживает одно приложение.** Реестр процессоров считается
исчерпывающим описанием всех типов задач в схеме — на этом держатся и обработка осиротевших задач,
и проверка формы контракта. Несколько сервисов на одной БД разводятся по разным схемам. Нарушение
не обнаруживается автоматически.

### Форма контракта

- В записи задачи хранится **форма контракта** — `FLAT` | `UNIT` | `BATCH`, — проставляемая
  **при первом захвате**. До захвата формы нет: ещё не начатая задача обрабатывается по актуальному
  контракту.
- Без пометки смена контракта у живого типа даёт **тихую порчу данных**: закрытие родителя смотрит
  на текущий контракт, не находит батчей у старой задачи и закрывает её, пока подзадачи работают.
- **Несовпадение формы с текущим процессором — задача отменяется**, в лог пишется ошибка, причина
  в `status_description`. Не доигрывать «совместимые случаи»: разбор матрицы совместимости
  контрактов — источник тонких ошибок.
- **Задачи типов без процессора в работу не берутся, но состояния не меняют** и остаются
  в `PENDING`. Вернули процессор — поехали дальше сами. Запрос захвата исключает неизвестные типы.
- Видимость таких задач — тремя каналами: громкое предупреждение при старте с перечнем типов
  и числом задач, метрика с разбивкой по типу, признак в REST-выдаче.
- `status_description` — **общее поле** причины терминального статуса для `SKIPPED` и `CANCELLED`.
  Обязательно: иначе отменённая движком задача неотличима от отменённой человеком.

### Миграция контракта

Контракт у существующего типа **не меняется** — заводится новый тип. Версии контракта в стартере
нет и не нужно. Порядок: клонировать процессор под новым `taskType` с суффиксом версии → переключить
постановку → пометить старый процессор `@Deprecated`.

**Процессор типа задачи не удаляется никогда.** Он **и есть исполнитель**: без него незавершённую
задачу некому доработать, а упавшую подзадачу из истории некому перезапустить. Восстановление
Java-типа нагрузки из его дженерика — причина вторая и производная: даже сохранив тип в БД
и разобрав нагрузку, выполнять её было бы нечем. Удаление процессора —
ломающее изменение на стороне потребителя, в одном ряду со сменой контракта. Следствия: реестр
процессоров растёт монотонно, `@Deprecated` — постоянное состояние, а не шаг к удалению, и старый
процессор обязан компилироваться и работать. Поиску по истории живой процессор при этом **не
нужен**: белый список полей лежит в БД ([ADR 0037](docs/adr/0037-search-field-registry.md)).

- **`@Deprecated` на классе процессора блокирует постановку новых задач** этого типа; существующие
  выполняются как обычно. Постановка отвергается исключением, через REST — ошибка клиента.
- Аннотация ищется на классе процессора, не на `@Bean`-методе.
- Список устаревших типов **громко печатается при старте**. Причина: `@Deprecated` в Java значит
  «не используйте в коде», а у нас ещё и «не принимай задачи» — тот, кто пометит процессор
  «на будущее», должен узнать о последствиях при деплое, а не при первой постановке.
- Нужны метрика незавершённых **с разбивкой по типу** и REST-сводка по типам: без них шаг
  «дождаться обнуления» непроверяем.

### Раскрытие

Подзадачи создаёт **процессор**, а не потребитель при постановке задачи. Через API задача ставится
параметрами, миллион бизнес-объектов в неё не передаётся. Каскад, каждый переход асинхронный:

```
Task ─expand─> TaskBatch[] ─expandBatch─> TaskUnit[] ─process─> ─collect─> ─collect─> готово
Task ─expand─> TaskUnit[]  ─process─────> ─collect─> готово
Task ─process────────────────────────────────────> готово      (плоский контракт)
```

Процессор отдаёт порождённое **в `Emitter<T>`**, а не возвращает `List`. Отсюда следствия:

- Раскрытие **не атомарно**: возможно частичное. «Раскрытие дошло до конца» ⟺ попытка раскрытия
  завершилась успешно; отдельной колонки `expanded_at` **нет**
  ([ADR 0047](docs/adr/0047-children-belong-to-attempt.md)).
- «Задача упала на раскрытии» определяется по исходу попытки, **а не по отсутствию подзадач**:
  раскрытие может успешно вернуть ноль подзадач, и это не ошибка.
- Каждый сброс буфера эмиттера — своя короткая транзакция. Ни миллион строк в памяти,
  ни миллион строк в одной транзакции.
- `Emitter` действителен только внутри вызова `expand` и не потокобезопасен. Вызов после
  возврата — `IllegalStateException`, а не тихая порча данных.
- Порядок в конце раскрытия: сначала финальный сброс, потом закрытие попытки успехом.
- **Дети принадлежат попытке раскрытия, а не родителю.** Ребёнок доступен для работы, только
  если его попытка-родитель успешна. Подзадачи батча идут в работу, как только раскрыт этот
  батч, — ждать раскрытия соседних батчей не нужно.
- **Повтор раскрытия ничего не удаляет.** Новая попытка порождает своих детей, прежние остаются
  при своей. Частичные дети неудачной попытки просто никогда не станут видимыми — мёртвый груз
  до дропа партиции. Ключа идемпотентности нет и не нужно: процессор всё равно перечисляет
  источник с начала.
- `Emitter<T>` — **единственный** интерфейс с единственным методом `emit(payload)`. Обе сигнатуры
  симметричны: `expand(Task, Emitter<B>)` и `expandBatch(TaskBatch, Emitter<U>)`. Бизнес-ключа
  нет ни у одной сущности — всё адресуется поиском по нагрузке
  ([ADR 0032](docs/adr/0032-no-business-key.md)).
- Раскрытие вернуло ноль детей — это `SUCCEEDED`, а не ошибка и не `WARNING`.

### Сборка результата

Обратная половина каскада ([ADR 0048](docs/adr/0048-collect-phase.md)). **Есть `expand` — есть
и `collect`**: у `BatchTaskProcessor` и `UnitTaskProcessor` обе фазы, у `FlatTaskProcessor` ни
одной.

- Сборка запускается, когда у актуальной попытки раскрытия не осталось незавершённых детей.
  Родитель возвращается в захват и получает попытку вида `COLLECT` — со своей арендой, heartbeat,
  повторами и пределом обработки, **всё по общим правилам**.
- **Вид попытки — явная колонка**: `PROCESS` | `EXPAND` | `COLLECT`. Выводить косвенно
  («раскрытие завершено, значит это сборка») нельзя — признак сломается на первом исключении.
  Значение читается так же, как имя метода.
- **Значение возвращают `process` и `collect`, но не `expand`** ([ADR 0059](docs/adr/0059-collect-contract.md)):
  раскрытие уже отдаёт результат — детей в `Emitter`, второй канал вывода ему не нужен.
  `Void` в параметре типа означает «результат не хранить». `skip(reason)` остаётся единственным
  каналом пропуска: результат — это данные, а не исход.
- **`collect` принимает поток, а не коллекцию.** Миллион объектов в метод не передать: раскрытие
  толкает детей через `Emitter`, сборка тянет их результаты обратно. Обработка обязана быть
  ленивой.
- **В поток идут все терминальные дети**, каждый обёрткой `CollectedUnit` / `CollectedBatch`:
  id, нагрузка, результат, статус, `statusDescription`. Только успешных было бы мало — сводка при
  `WARNING` обязана называть упавшие объекты. `result` пуст у неуспешных и у вернувших `null`.
- Имена парные, а не перегрузка: `collect` и `collectBatch` — по образцу `expand` и `expandBatch`.
- Неуспешная сборка делает родителя терминальным **при полностью успешных детях**. Состояние
  новое, и интерфейс обязан его объяснять.
- Результаты детей **удаляются после успешной сборки** — настраивается `taskcomm.results.discard`
  (`never` | `immediately` | `after`). Плюс ручное удаление через REST: всё либо старше N.
  Факт удаления помечается **на сущности родителя**, а не на миллионе детей, и снимает результаты
  детей **всех** попыток раскрытия сразу: актуальные уже собраны, прежние не нужны никому.
- **Результаты лежат в своей таблице `tc_task_result`** ([ADR 0058](docs/adr/0058-task-result-storage.md)),
  см. «Персистентность». У коммуникаций та же тема решена иначе
  ([ADR 0055](docs/adr/0055-communication-exchange-storage.md)) — там разложенный по колонкам обмен,
  здесь непрозрачное значение; переносить решение между подсистемами нельзя.

> **Контракт для потребителя: at-least-once, не exactly-once.** Аренда может истечь у живого,
> но медленного воркера, и подзадачу подберёт другой. Значит обработка обязана быть идемпотентной.
> Это требование к чужому коду — оно должно быть написано в Javadoc каждого интерфейса процессора,
> а не подразумеваться.

## Статусы и прогресс

- Прогресс задачи и батча **вычисляется агрегатом** по подзадачам. Денормализованных счётчиков нет.
- Обязателен индекс `(parent_attempt_id, status)` — агрегат считается по детям одной попытки
  раскрытия ([ADR 0047](docs/adr/0047-children-belong-to-attempt.md)). Проверка «все ли подзадачи
  завершены» делается через `EXISTS`, а не `COUNT ... GROUP BY` — иначе агрегат станет дорогим.
- Если часть подзадач исчерпала попытки, задача завершается в статусе `WARNING`, а не `FAILED`.
  Через REST API можно перезапустить **только упавшие** подзадачи.
- Отдельных статусов `RETRYING` / `SCHEDULED` нет: «ждёт повтора» — это `PENDING`
  с `next_attempt_at` в будущем.
- **Отложенный запуск — то же самое поле** ([ADR 0050](docs/adr/0050-deferred-start.md)). Постановка
  принимает необязательное «не раньше», значение кладётся в `next_attempt_at`, и больше не меняется
  ничего: ни захват, ни статусы, ни индексы. Не заводить `scheduled_at` и не заводить `SCHEDULED` —
  это второй источник ответа на «когда можно стартовать», который придётся учитывать в самом
  горячем запросе.
- **Отсрочка отличается от повтора по отсутствию попыток**: будущее время и ни одной строки
  попытки — запланирована; будущее время и попытки есть — ждёт повтора. Признак выводится,
  колонки под него нет.
- Это **не планировщик**: однократная отсрочка, без повторяемости, с точностью до такта поллера.
  Ручной перезапуск ставит `next_attempt_at` на сейчас и тем самым отсрочку отменяет.
- Статусы `TaskUnit` **и `Communication`** — общий набор из шести: `PENDING`, `RUNNING`,
  `SUCCEEDED`, `FAILED`, `CANCELLED`, `SKIPPED`. У коммуникации нет детей, поэтому
  `AWAITING_CHILDREN` и `WARNING` ей не нужны ([ADR 0042](docs/adr/0042-communication-statuses.md)).
  **Совпадение набора не повод для общего перечисления**: у каждой подсистемы своё, в своём `api`.
- Статусы `Task` и `TaskBatch` — общий набор: `PENDING`, `RUNNING`, `AWAITING_CHILDREN`,
  `SUCCEEDED`, `WARNING`, `FAILED`, `CANCELLED`, `SKIPPED`. `RUNNING` означает «захвачено
  и работает» — плоская задача выполняется, задача с детьми раскрывается. `AWAITING_CHILDREN` —
  раскрытие закончено, дети в работе, родитель **аренду не удерживает**. У плоской задачи этот
  статус не встречается.
- **Отмена — не статус, а факт `cancel_requested_at`.** Ортогонален статусу и потому работает
  в любой фазе, включая раскрытие. `CANCELLED` ставится, когда не осталось `RUNNING`.
- **Колонка `cancel_requested_at` есть только у `tc_task` и `tc_communication`** — там же, где
  могут начинаться агрегаты. У батча и подзадачи её нет: они читают флаг своей задачи, а в память
  его приносит поток heartbeat тем же тактовым запросом
  ([ADR 0041](docs/adr/0041-cancellation-on-root.md)). Отсюда два следствия: проверка «продолжать
  ли» бесплатна, но узнаёт об отмене с задержкой в такт; и раскрытие батча нельзя остановить,
  не отменив задачу целиком.
- Восемь статусов — потолок. Дальнейшие состояния выражать **фактами-колонками**, как
  `cancel_requested_at`, а не новыми статусами.
- Родителя в терминальный статус переводит воркер, завершивший последнего ребёнка; застрявших
  в `AWAITING_CHILDREN` добирает подстраховочный поллер. **Закрытие идемпотентно**: переход
  выполняется условно по текущему статусу, а не безусловной записью.
- `SKIPPED` ставит движок при отмене родителя, а на уровне задачи — процессор, вызвав
  `skip(reason)` **в контексте обработки**. `expand` и `process` остаются `void`: успех уже
  выражен отсутствием исключения, второй канал для того же факта не нужен.
- Пропуск засчитывается, только если метод вернулся нормально; **исключение перебивает пропуск**;
  `reason` обязателен и хранится в БД.
- Агрегат: есть `SKIPPED` среди детей — родитель `SUCCEEDED`; **все** дети `SKIPPED` — родитель
  `SKIPPED`. Собственная отмена родителя перебивает агрегат.
- **При отмене родителя дети в `PENDING` уходят в `SKIPPED`, а дети в `RUNNING` доигрывают
  и пишут свой настоящий исход.** Пометить `SKIPPED` всё незавершённое сразу нельзя: это скрыло бы
  реально выполненную работу и её побочные эффекты.
- Не путать: раскрытие, честно вернувшее ноль детей, — это `SUCCEEDED`. `SKIPPED` — явное
  «выполнять не надо». Разница в намерении процессора, а не в числе детей.
- Backoff экспоненциальный и **обязательно с джиттером**: иначе тысяча подзадач, упавших из-за
  недоступности внешней системы, проснётся одновременно и положит её повторно. Параметры —
  `initial-delay`, `multiplier`, `max-delay`, `jitter`; **`jitter: 0` валит запуск**, потому что
  настройка не должна выключать то, что решение назвало обязательным.
- Повторяются **только упавшие `TaskUnit`**, батч целиком не перезапускается.
- **Процессор может объявить неуспех неповторяемым** — `doNotRetry(reason)` в контексте обработки
  ([ADR 0062](docs/adr/0062-non-retryable-failure.md)). Вызванный до броска исключения, он делает
  сущность терминальной сразу, не досматривая остаток лимита: битая нагрузка не станет валидной
  от повтора. Вызвать надо **до** броска, и забыть об этом легко — проверить нечем, только Javadoc.
  Без последующего исключения вызов не делает ничего. `status_description` обязан отличать
  «повторять запрещено» от «попытки исчерпаны».
- **`skip(reason)` и `doNotRetry(reason)` — разного рода.** Первый объявляет исход и потому
  действует при нормальном возврате, а исключение его перебивает; второй исхода не объявляет,
  а меняет политику повторов, и потому осмыслен только при броске. Одинаковая форма подсказывает
  симметрию, которой нет.
- **Колонки `attempt` на сущности нет.** Число попыток — это строки попыток, начиная с отметки
  `retry_cycle_started_at` ([ADR 0046](docs/adr/0046-lease-in-attempt.md)).
- **Ручной перезапуск через REST двигает `retry_cycle_started_at`** на сейчас и ставит туда же
  `next_attempt_at` ([ADR 0043](docs/adr/0043-manual-restart-resets-attempts.md)). Иначе
  перезапуск подзадачи, исчерпавшей лимит, немедленно упирался бы в него снова. Затирать при этом
  нечего: попытки сохраняются все, а граница цикла становится явной.

### Перезапуск

Правила из [ADR 0049](docs/adr/0049-restart-semantics.md):

- **Подзадача** — на месте, заново `process`. Соседи не трогаются.
- **Батч** — новая попытка раскрытия: свежие общие данные из внешней системы, новый набор детей,
  затем сборка. Прежняя попытка со всеми своими детьми остаётся нетронутой. Повторно ходить
  во внешнюю систему — это смысл операции, а не побочный эффект.
- **Задача** — то же уровнем выше.
- **Перезапуск снимает терминальность с предков**: подзадача уходит в `PENDING`, батч и задача
  возвращаются в `AWAITING_CHILDREN`. Пока дети работают, задача не завершена. Отсюда же снова
  работает отмена — на терминальной задаче она была бессмысленной.
- **Терминальный статус перестаёт быть окончательным.** Любой внешний потребитель метрик
  или событий, считающий его финальным, ошибётся.
- **Преждевременной сборки не бывает**: триггер — «незавершённых детей не осталось», а не
  «ребёнок завершился». Перезапустили пять подзадач — сборка запустится один раз, когда
  закончится последняя.
- **Результаты группы удалены — перезапуск подзадачи отвергается**, перезапускать надо батч или
  задачу целиком; отказ обязан объяснять причину. Строго говоря, для группы из одной подзадачи
  запрет избыточен, но ветвить логику ради вырожденного случая **сознательно не будем**.
- Попытки считают **захваты**, а не только падения процессора: истечение аренды и превышение
  предела обработки тоже создают строку попытки.

### Попытки

Повтор работает **с той же строкой**: копий сущности не создаётся, агрегат и `EXISTS` не меняются
([ADR 0044](docs/adr/0044-attempt-log.md)). История каждой попытки живёт отдельно.

- Таблиц **две, по подсистемам**: `tc_task_attempt` с колонкой `level` (`TASK` | `BATCH` | `UNIT`)
  и `target_id`, и `tc_communication_attempt`. Общей таблицы нет: в неё писали бы оба движка,
  и общий код появился бы сам собой. `Execution` общий только потому, что пассивен.
- Строка пишется **на каждую попытку**, а не только на неуспешную, — вставляется при захвате
  в той же короткой транзакции и закрывается по завершении.
- Незакрытая строка при истёкшей аренде (`finished_at IS NULL`) — сама по себе диагноз: воркер
  не доработал, сопоставлять логи не нужно.
- Исход попытки хранится в колонке `status` самой строки попытки: `SUCCEEDED` | `FAILED` |
  `SKIPPED` | `LEASE_LOST`. Последний фиксирует случай, который иначе виден лишь как WARN: воркер
  доработал, обнаружил при записи чужой токен и результат не сохранил. Свою строку попытки он
  при этом пишет — она принадлежит ему.
- **В попытке живёт всё, что описывает один захват**: `locked_by`, `locked_until`, `lease_token`,
  `lease_renewals`, `started_at`, `finished_at`, `status`, `status_description`
  ([ADR 0057](docs/adr/0057-attempt-status-columns.md)). Имена совпадают с колонками сущности
  осознанно — это не коллизия, а разный объём одного и того же смысла: у сущности `status`
  и `status_description` про сущность целиком, у попытки — про один захват. В запросе, соединяющем
  обе таблицы, колонки различаются алиасом: `task.status AS task_status, attempt.status AS
  attempt_status`. **На сущности —**
  общее для всех попыток: нагрузка, `status`, `status_description`, `next_attempt_at`,
  `retry_cycle_started_at`, родство, `task_type`, `contract_shape`,
  `cancel_requested_at`. Колонка нагрузки называется `payload` у задач и `request_payload`
  у коммуникаций.
- **У коммуникаций в попытке лежит ещё и обмен** — запрос и ответ, см. «Хранение обмена».
  Это единственное, что там есть сверх описания захвата, и оно тоже принадлежит одной попытке.
- **У задач результат в попытке не лежит** — он в своей таблице `tc_task_result`
  ([ADR 0058](docs/adr/0058-task-result-storage.md)). Подсистемы здесь расходятся сознательно:
  у коммуникаций обмен разложен по колонкам, у задач результат непрозрачен и удаляется целой
  группой.
- `status_description` на сущности **сужается**: он про причину терминального статуса самой
  сущности. Отменённая или пропущенная сущность попыток не имела вовсе, и записать причину больше
  некуда. Причина каждой попытки — в её строке.
- `started_at` и `finished_at` есть **только в строке попытки**. Отсюда же берётся метрика времени
  выполнения: раньше длительность взять было неоткуда.
- **Попытка — не журнальная запись, а узел иерархии.** Слово «журнал» к этим таблицам
  не применять: в них аренда ([ADR 0046](docs/adr/0046-lease-in-attempt.md)) и дети
  ([ADR 0047](docs/adr/0047-children-belong-to-attempt.md)), движок читает их и в захвате,
  и в агрегате.
- Данные, собранные процессором при раскрытии батча, **материализуются в нагрузку `U` каждой
  подзадачи**. Подзадача самодостаточна: её повтор не требует ни батча, ни задачи. Отсюда `B` —
  это параметры группы, а не собранные данные.
- `TaskUnit` **обязан нести `taskId` и `batchId`** в публичном API: без них потребитель не сможет
  вести собственное хранилище общих данных по батчу, если дублирование окажется для него дорогим.
  Своего хранилища общих данных стартер не предоставляет — это осознанный не-goal.

## Персистентность и конкурентность

- Хранилище объявлено как SPI: интерфейсы (`TaskRepository`, `CommunicationRepository`) живут в
  `*/api`, реализация на Spring JDBC + PostgreSQL — в `*/internal`. Потребитель может подставить
  свою реализацию (сработает `@ConditionalOnMissingBean`). In-memory реализация планируется.
- Захват работы несколькими экземплярами приложения — через `SELECT ... FOR UPDATE SKIP LOCKED`.
  Никаких распределённых локов, ShedLock и брокеров.
- **Аренда живёт в строке попытки, а не в строке сущности**
  ([ADR 0046](docs/adr/0046-lease-in-attempt.md)). Система совершает попытку, а не сущность:
  `locked_by`, `locked_until`, `lease_token`, `lease_renewals` описывают один захват и вне
  попытки смысла не имеют. Сущность — агрегирующая запись: нагрузка, статус, расписание, родство.
- **Соединение в локирующем `SELECT` допустимо, если оно 1:1 и включает ключ партиционирования.**
  Запрещено соединение к **общему родителю**: миллион подзадач делят одну строку задачи, это
  fan-in, и `FOR UPDATE` заставил бы всех воркеров драться за неё. Соединение к **собственной
  попытке** этим свойством не обладает — у каждой строки своя. Не путать эти два случая: запрет
  относится к первому.
- **Запрос захвата у задач — две ветки через `UNION ALL`**, а не один `OR`: у половин разные точки
  входа. Первая — задачи, батчи и подзадачи в `PENDING` с `next_attempt_at <= now()`, у которых
  **открытой** попытки нет; ведёт частичный индекс активных статусов — тот из трёх, что отвечает
  форме захвата, выбранной в поллере. Вторая — открытые попытки с истёкшим `locked_until`, оттуда
  к сущностям; ведёт частичный индекс попытки по `locked_until`.
- Условие первой ветки — «нет **открытой** попытки» (`finished_at IS NULL`), а не «нет ни одной»:
  строка с закрытой упавшей попыткой, ждущая повтора, обязана проходить.
- **У коммуникаций запрос захвата другой — одноветочный**, и это не упрощение задачного, а прямое
  следствие того, что попытка создаётся вместе с сущностью
  ([ADR 0054](docs/adr/0054-communication-attempt-lifecycle.md)). Вход с сущности по тому же
  частичному индексу активных статусов, соединение 1:1 к открытой попытке, условие
  `locked_until IS NULL OR locked_until < now()`. Захват — **проставление аренды в существующую
  строку**, а не `INSERT`. Частичный индекс по `locked_until` этой таблице не нужен: второй ветки
  нет. Форму запроса коммуникаций **не переносить на задачи** — там попытки заранее не создаются.
- **Инвариант коммуникаций**: пока коммуникация не терминальна, у неё ровно одна открытая попытка.
  Держит его тот же уникальный частичный индекс. Следующую попытку открывает воркер, закрывая
  неуспешную; ручной перезапуск терминальной коммуникации обязан открыть попытку сам, иначе
  захват её молча не найдёт.
- **Двойной захват невозможен на уровне СУБД**: уникальный частичный индекс
  `(execution_created_at, target_id) WHERE finished_at IS NULL` не даёт завести вторую открытую
  попытку. Уникальность внутри партиции здесь достаточна — все попытки одной сущности делят
  её `execution_created_at`, в отличие от дедупликации и корреляции, где партиционирование
  уникальность ломало.
- **Захват по аренде.** Транзакция закрывается сразу после захвата, процессор работает вне её —
  соединение из пула не занято чужим кодом. Схема: короткая транзакция помечает сущность
  `RUNNING`, заводит в строке попытки новый токен и `locked_until = now() + аренда`, затем
  commit; результат пишется отдельной транзакцией. У задач строка попытки при этом **вставляется**,
  у коммуникаций — уже существует и лишь получает аренду.
- Раз транзакция короткая, падение воркера её не откатывает. Работу возвращает поллер: он забирает
  и `PENDING`, и сущности с открытой попыткой, у которой истёк `locked_until`.
- Долгие единицы работы продлевают аренду (heartbeat). Нужен верхний предел на выполнение, иначе
  зависший процессор будет продлевать аренду вечно.
- **Продлевает не воркер, а отдельный поток на инстанс**, одним запросом на такт по всем активным
  арендам. Воркер продлить себя не может: его поток занят синхронно выполняющимся кодом
  потребителя.
- Интервал heartbeat должен быть заметно меньше аренды — порядка трети, чтобы пережить два
  пропущенных такта. При старте соотношение проверяется, но выдаётся только **предупреждение**.
  Оно обязано быть громким и содержать рекомендуемое значение: неверная настройка проявится
  не при старте, а под нагрузкой, массовым двойным выполнением.
- Все три операции с арендой — захват, продление, завершение — включают в условие `lease_token`.
  `locked_by` для проверки владения недостаточно: тот же инстанс может захватить строку повторно.
- Продление трогает **только строки попыток**; сущность при этом не обновляется вовсе. Завершение
  условно по токену в строке попытки, и лишь затем правится сущность.
- Родитель в `AWAITING_CHILDREN` аренду **не держит**: переход выражается закрытием попытки
  раскрытия с исходом `SUCCEEDED`, а не обнулением колонок — обнулять больше нечего. Аренда
  защищает активную работу, подстраховочный поллер — ждущих родителей.
- Раскрытие идёт под арендой наравне с обработкой, heartbeat работает так же, предел обработки
  применяется к нему.
- **Сигнал прекращения — `shouldStop()` в контексте обработки.** Полярность положительная:
  `true` значит «пора останавливаться». Причин три — отмена, потеря аренды и собственный `skip()`
  процессора; различать их он не может и не должен, реакция одна
  ([ADR 0062](docs/adr/0062-non-retryable-failure.md)). Проверка добровольная и **бесплатная**:
  отвечает из памяти, без запроса к БД.
- Длительность аренды, интервал heartbeat и предел обработки настраиваются через
  `taskcomm.*`, см. «Свойства конфигурации». Слишком короткая аренда даёт двойное выполнение,
  слишком длинная — простой после падения. **Предел задаётся временем** (`max-execution-time`),
  а счётчиком продлений остаётся только внутри — значит точность до такта heartbeat, и смена
  интервала heartbeat пересчитывает предел молча.
- Предел обработки — **счётчик продлений аренды** (`lease_renewals` в строке попытки): дошли
  до предела, перестали продлевать, аренда истекла, работу подобрал поллер. Обнуление счётчика
  **структурно**: новая попытка — новая строка, помнить об этом отдельным правилом не нужно.
  Превышение предела — **обычная неуспешная попытка**, никакого особого статуса. Предел задаётся
  глобально с переопределением по типу задачи в `application.yml`.
- **Обязателен токен аренды.** При каждом захвате генерируется новый и кладётся в строку попытки;
  завершение условно по нему — `WHERE id = :attempt AND lease_token = :token`, и лишь при
  затронутой строке правится сущность. Иначе первый воркер, доработав после превышения предела,
  затрёт результат второго. Одного `locked_by` недостаточно: тот же воркер может захватить работу
  повторно.
- Воркер, обнаруживший при записи чужой токен, пишет WARN и **молча не сохраняет результат**.
  Исключение бросать нельзя: работа выполнена, ошибки в коде потребителя нет.
- SQL пишется руками, `JdbcClient`. Hibernate/JPA в проекте нет — не добавлять.
- Полезная нагрузка хранится в колонке `jsonb`, сериализация — Jackson. Не `bytea`: содержимое
  нагрузки должно быть видно и доступно для поиска прямо в SQL при разборе инцидентов.
- Java-тип нагрузки восстанавливается **из дженерика процессора** через Spring `ResolvableType`.
  FQCN в БД не хранится: потребитель переименует класс — старые задачи перестанут читаться.
- Таблицы называются с префиксом `tc_` и живут в схеме, которую использует потребитель (не
  обязательно `public`). Имя схемы **не хардкодится в SQL** — работаем в схеме соединения.
- **Перечислимые колонки — `text` с `CHECK`, а не нативный enum PostgreSQL.** Касается статусов
  всех сущностей, формы контракта, направления коммуникации и `FieldType`. Причина в том, что мы
  работаем в `DataSource` потребителя и не можем выставить `stringtype=unspecified`: с нативным
  enum пришлось бы писать каст `?::tc_task_status` в каждом запросе, а забытый каст — ошибка
  времени выполнения. См. [ADR 0036](docs/adr/0036-enumerated-columns.md).
- Значения в БД пишутся ровно как в Java-перечислении: `PENDING`, `AWAITING_CHILDREN`. Тогда
  `psql`, логи и REST показывают одно и то же.
- `CHECK` **дублирует Java-перечисление**, и копии могут разойтись. Нужен тест, сверяющий значения
  перечисления с содержимым ограничения.
- **Идентификаторы — UUIDv7**: `uuid` в БД, `java.util.UUID` в Java. Не `bigint`: последовательный
  идентификатор уходит наружу через REST и раскрывает объём у потребителя. Не UUIDv4: случайность
  бьёт по массовой вставке при раскрытии.
- Генератор UUIDv7 — **свой, в `internal`**, не публичный API; принимает `Clock` ради тестов.
  Библиотеку не тянем: новый транзитив приезжает всем потребителям ради тридцати строк.
- Генератор **обязан быть монотонным внутри миллисекунды** (счётчик в `rand_a`). Без этого
  идентификаторы, созданные в одну миллисекунду, упорядочены случайно — а при пачечной вставке
  миллиона подзадач таких большинство, и преимущество v7 теряется именно там, где нужно.
- Первичные ключи составные: **`(execution_created_at, id)`** у всех четырёх — `tc_task`,
  `tc_communication`, `tc_task_batch`, `tc_task_unit`. У `tc_execution` — `(created_at, id)`.
- Размер идентификатора **не влияет на вторичные индексы**: в PostgreSQL они ссылаются на `ctid`,
  а не на первичный ключ. «UUID раздувает все индексы» — это про InnoDB, не про нас.
  См. [ADR 0035](docs/adr/0035-uuidv7-identifiers.md).
- **В каждой таблице `created_at` и `updated_at`, сразу после `id`.** Порядок колонок фиксирован:
  `id`, `created_at`, `updated_at`, дальше предметные поля.
- **Результаты обработки задач — в `tc_task_result`** ([ADR 0058](docs/adr/0058-task-result-storage.md)):
  `attempt_id`, `level`, `target_id`, `result jsonb`, плюс общие `id`, `created_at`, `updated_at`,
  `execution_created_at`. Партиционируется и дропается наравне со всеми. Строка пишется, **только
  если метод вернулся нормально и вернул не `null`** — отсюда `result NOT NULL`, а отсутствие
  результата выражается отсутствием строки. `Void` в параметре типа значит «не хранить».
- **Текущий результат сущности — результат её последней попытки** по наибольшему `started_at`
  (не последней успешной: ручной перезапуск это меняет), попытки со `status = 'LEASE_LOST'`
  исключены. Последняя попытка неуспешна — результата нет. **У подзадачи правило вырождается**:
  перезапуск разрешён только из `FAILED`, у упавшей попытки результата нет, успех терминален —
  значит результат не более одного за всю жизнь, и сборка читает прямым соединением без сортировки.
  У батча и задачи нужен `LATERAL` с `ORDER BY started_at DESC LIMIT 1`, но там десятки строк.
- **`level` и `target_id` денормализованы в `tc_task_result`** из попытки — иначе соединение
  к `tc_task_attempt` обязательно и на миллионе подзадач.
- **`task_type` денормализован в `tc_task_batch` и `tc_task_unit`.** Не для удобства: индексы
  поиска по нагрузке частичные по типу задачи (`WHERE task_type = 'order-change'`), и без колонки
  условие индекса построить не на чем.
- **`execution_created_at` есть и в `tc_communication_dedup`.** Приём с ключом обязан вернуть уже
  существующую коммуникацию, а достать её без ключа партиционирования — это скан по всем
  партициям. Времени чего-либо в самой строке эта колонка не означает.
- **Указатель на создателя — четыре колонки `origin_*` в `tc_task` и `tc_communication`**
  ([ADR 0064](docs/adr/0064-entity-origin-links.md)), см. «Связи внутри дела». `origin_type`,
  `origin_id` и `origin_relation` заполняются и пустуют только вместе; пусты все четыре — сущность
  корневая. `origin_attempt_id` пуст у колбэка: его создаёт контроллер, попытки за ним нет.
  На подчинённых таблицах раскрытия этих колонок **нет**.
- `updated_at` проставляет **приложение**, явным `SET updated_at = now()` в каждом изменяющем
  состояние запросе. Триггеров в БД нет. Забыть легко, автоматики нет — это осознанный размен,
  см. [ADR 0033](docs/adr/0033-audit-timestamps.md).
- **Heartbeat `updated_at` не трогает**: продление аренды — не изменение состояния. Иначе колонка
  у всех выполняющихся строк была бы всегда свежей и ничего не значила. Сущности это больше
  не касается вовсе — heartbeat пишет только в строки попыток, — но на них оговорка остаётся.
- **У всех четырёх таблиц временных колонок две**: своя `created_at` и денормализованная
  `execution_created_at` — они законно расходятся, и в DDL это обязано быть прокомментировано.
  Раньше у `tc_task` и `tc_communication` собственный `created_at` служил заодно ключом
  партиционирования; теперь нет ([ADR 0039](docs/adr/0039-execution-partitioning.md)).
- У задачи в `AWAITING_CHILDREN` `updated_at` не двигается, пока работают дети. Строить на этой
  колонке алерт «задача зависла» нельзя — она про изменение состояния, а не про активность.
- **Постановка задачи пишется в текущую транзакцию потребителя.** Таблица задач работает как
  outbox: задача становится видимой воркеру ровно в момент коммита бизнес-данных. Отсюда —
  стартер использует `DataSource` потребителя и **не заводит собственный пул соединений**.
- **У работы есть приоритет** ([ADR 0063](docs/adr/0063-claim-ordering-and-pollers.md)): колонка
  `priority` во всех четырёх подчинённых таблицах, `smallint NOT NULL DEFAULT 100`,
  `CHECK (priority > 0)`. **Шкала по возрастанию — меньше значит важнее.** Это противоположно
  интуиции, и говорить об этом надо громко везде: в Javadoc, в документации потребителя,
  в комментарии к колонке.
  - Задаётся при создании; значение по умолчанию берётся по типу из аннотации или `yaml`.
  - **Дети наследуют приоритет родителя** — `Emitter` не меняется, у него один метод.
  - Ручной перезапуск приоритет не меняет.
- **Ключ порядка захвата — колонка `claim_order_at`**, а не `next_attempt_at`:
  `claim_order_at = next_attempt_at + priority × K`, где `K` — шаг дедлайна из настроек поллера.
  Имя выбрано сознательно: это не время захвата и вообще не время события, а ключ сортировки
  в форме отметки времени. **Считает его приложение**, а не генерируемая колонка Postgres, потому
  что `K` живёт в настройках; значит пересчитывать надо везде, где пишется `next_attempt_at` —
  backoff, отсрочка, ручной перезапуск.
- **Форм захвата три**, выбор в настройках поллера, по умолчанию `deadline`:
  `deadline` (`ORDER BY claim_order_at`), `priority` (`ORDER BY priority, next_attempt_at`)
  и `quota` (то же плюс заданная доля захватов по чистому FIFO). Голодание при `deadline`
  **невозможно арифметически**: смещение ограничено сверху, время ожидания — нет. Взамен приоритет
  перестаёт быть абсолютным: единица бьёт сотню только внутри окна.
- **Поллеров может быть несколько.** По умолчанию один; в настройках заводятся дополнительные
  с набором типов задач или имён внешних систем, и **основной их не берёт**. Тип, названный
  в двух поллерах, — падение при старте. Цена: основной поллер фильтрует по типу **после** чтения
  строки, и худший случай наступает ровно тогда, когда выделение полезнее всего — когда выделен
  самый шумный тип.
- Отмена **кооперативная**: новые единицы работы не захватываются, уже выполняющиеся доигрывают.
  Прерывать поток процессора нельзя. Подзадача, успешно завершившаяся после отмены, пишется
  как `SUCCEEDED`, а не `CANCELLED`, — её побочные эффекты существуют, и скрывать их опасно.

### Индексы

Требования разбросаны по решениям, здесь сводно:

- **Частичные по активным статусам — их три, по одному на форму захвата**
  ([ADR 0063](docs/adr/0063-claim-ordering-and-pollers.md)): `(status, claim_order_at)` под
  `deadline`, `(status, priority, next_attempt_at)` под `priority`, `(status, next_attempt_at)` под
  проход `quota` по чистому FIFO. Держатся **все три всегда**: форма выбирается конфигурацией,
  а индексы создаются миграцией, и связывать DDL с `application.yml` мы отказываемся. Платит
  массовая вставка при раскрытии.
  Список статусов в условии **разный по таблицам**: у `tc_task` и `tc_task_batch` это
  `('PENDING', 'RUNNING', 'AWAITING_CHILDREN')`, у `tc_task_unit` и `tc_communication` —
  `('PENDING', 'RUNNING')`: `AWAITING_CHILDREN` у них не встречается, детей нет.
- **`(parent_attempt_id, status)`** — агрегат прогресса и проверка `EXISTS` завершённости детей
  ([ADR 0047](docs/adr/0047-children-belong-to-attempt.md)). Считается по детям **одной попытки
  раскрытия**, поэтому дети прежних попыток в агрегат не попадают по построению. Завершающийся
  ребёнок спрашивает по **своей** ссылке — выяснять, какая попытка актуальна, ему не нужно.
- `(task_id, status)` и `(batch_id, status)` как индексы агрегата **не нужны**: `task_id`
  и `batch_id` остаются денормализованными ради публичного API и REST-фильтров, но признаком
  принадлежности текущему набору детей больше не служат.
- **`(execution_id)`** на каждой из четырёх таблиц — выдача «покажи весь `Execution`». Ключ
  партиционирования в этом запросе есть, отсечение работает, поэтому больше в индекс класть
  нечего.
- **Уникальный `(source, dedup_key)`** — в `tc_communication_dedup`, вне партиционирования.
- **Уникальный `(correlation_id)`** — в `tc_communication_correlation`, вне партиционирования.
  Первая регистрация выигрывает; повторная другой коммуникацией якорь не двигает и пишет WARN.
- **По одному частичному выражению на каждую строку `tc_searchable_field`**, с условием по типу
  задачи: `((payload->>'orderId')) WHERE task_type = 'order-change'`. Наборов три — по задачам,
  батчам и подзадачам. Эти индексы стартер не создаёт: проверяет наличие и печатает готовый DDL.
  Считать нужно именно по строкам реестра, а не по объявлениям живых процессоров: строка,
  которую больше никто не объявляет, обслуживает поиск по истории и без индекса пойдёт
  последовательным сканированием.
- **Уникальный `(execution_created_at, target_id) WHERE finished_at IS NULL`** в таблицах попыток —
  защита от двойного захвата: двух открытых попыток у сущности быть не может. У задач он же ведёт
  первую ветку запроса захвата, у коммуникаций — соединение к открытой попытке и инвариант
  «ровно одна открытая попытка, пока сущность не терминальна».
- **`(locked_until) WHERE finished_at IS NULL`** — **только в `tc_task_attempt`**: это вторая ветка
  задачного запроса захвата. У коммуникаций второй ветки нет, и индекс не нужен
  ([ADR 0054](docs/adr/0054-communication-attempt-lifecycle.md)).
- **`(level, target_id)`** в `tc_task_attempt` и **`(communication_id)`** в
  `tc_communication_attempt` — выдача истории попыток одной сущности.
- **`(request_id)`** в `tc_communication_attempt` — разбор инцидентов и поиск через REST по
  идентификатору запроса. Ключа партиционирования в таком запросе нет, поэтому лукап обходит все
  партиции; цена принята сознательно, но **в захвате и диспетчеризации этот путь использовать
  нельзя**.
- **Уникальный `(execution_created_at, attempt_id)`** в `tc_task_result` — одна строка результата
  на попытку.
- **`(execution_created_at, level, target_id)`** в `tc_task_result` — чтение результатов детей
  сборкой и выдача текущего результата.
- **`started_at` в составе индекса попыток** — без него `LATERAL` за последней попыткой батча
  и задачи будет сортировать на каждую строку ([ADR 0058](docs/adr/0058-task-result-storage.md)).
- **Внутри `tc_searchable_field` индексов нет**, кроме уникального по сигнатуре. Справочник
  на десятки строк читается последовательным сканированием быстрее, чем по индексу.
- Индекса по бизнес-ключу нет: бизнес-ключей нет ни в одной таблице.
- **Индекса по `origin_id` тоже нет** ([ADR 0064](docs/adr/0064-entity-origin-links.md)): «кого
  создала эта коммуникация» берётся чтением дела и фильтром в памяти — в деле десятки сущностей
  кроме детей раскрытия, а у тех `origin_*` пуст. Понадобится — добавляется аддитивно.

## Партиционирование и очистка

- Партиционируются по времени **восемь таблиц**: `tc_execution`, `tc_task`, `tc_task_batch`,
  `tc_task_unit`, `tc_communication`, две таблицы попыток — `tc_task_attempt`,
  `tc_communication_attempt` — и `tc_task_result`. Очистка — `DROP` партиции, а не `DELETE`.
  Справочники — `tc_communication_dedup`, `tc_communication_correlation` и `tc_searchable_field` —
  не партиционируются: временного измерения у них нет и дропать в них нечего. Всего таблиц
  в схеме одиннадцать.
- Таблицы попыток отдельной очистки **не получают**: они дропаются вместе с партицией своего
  агрегата. Хранить историю попыток дольше самих сущностей нельзя, короче — тоже.
- **`tc_task_result` — единственная партиционированная таблица со своей очисткой**: строки из неё
  удаляются `DELETE` по `taskcomm.results.discard`, не дожидаясь дропа партиции
  ([ADR 0058](docs/adr/0058-task-result-storage.md)). Отсюда же следует, что свойство
  [ADR 0047](docs/adr/0047-children-belong-to-attempt.md) «во всей системе не остаётся ни одного
  массового удаления или обновления» **больше не выполняется**.
- **Ключ партиционирования — время создания `Execution`.** У всех четырёх подчинённых таблиц это
  денормализованная колонка `execution_created_at`, а не их собственное время: агрегат по своей
  природе растёт во времени, и его части не должны разрываться между партициями.
  `tc_execution` партиционируется по собственному `created_at`.
- Колонки `task_created_at` **нет**: иерархия задач со-локализована через `Execution`, и второй
  денормализованный ключ не нужен.
- **Старые партиции остаются записываемыми.** Асинхронный ответ, пришедший через год, попадает
  в партицию своего `Execution` — это ожидаемое поведение. Любая оптимизация вида «старое только
  читается» с этой схемой несовместима.
- **Дроп партиции обязан вычищать записи `tc_communication_correlation`** с этим диапазоном.
  Иначе реестр накопит ключи, указывающие в пустоту, и колбэк упадёт на вставке в несуществующую
  партицию. Лукап, не нашедший якоря, заводит новый `Execution` и пишет WARN.
- **Внешних ключей между задачей, батчами и подзадачами нет** — партиционирование их не допускает.
  Целостность обеспечивается кодом.
- Ключи дедупликации коммуникаций живут в **отдельной непартиционированной** таблице
  `tc_communication_dedup`: на партиционированной таблице уникальный индекс обязан включать ключ
  партиционирования, и уникальность исчезает полностью. По той же причине непартиционирован
  и реестр корреляции `tc_communication_correlation`.
- Партициями управляет стартер. Размер партиции, число создаваемых заранее и глубина хранения
  задаются в `application.yml`. Это **единственное исключение** из правила «стартер не выполняет
  DDL в проде»: без заранее созданной партиции вставка падает и система встаёт.
- Удаление старых партиций **выключено по умолчанию** и обязано проверять, что в партиции нет
  незавершённых записей. Задача, созданная в январе и всё ещё выполняющаяся в апреле, лежит
  в январской партиции — слепой `DROP` по возрасту уничтожил бы активную работу.
- **Восемь партиций одного диапазона дропаются вместе**, и проверка «нет незавершённых записей»
  делается по четырём подчинённым таблицам: ни у `tc_execution`, ни у таблиц попыток, ни
  у `tc_task_result` статуса нет, проверять в них нечего.
  Дропнуть партицию агрегата, оставив партиции его содержимого, нельзя — это разорвало бы
  `execution_id` в никуда.
- Обязательны **частичные индексы** `WHERE status IN ('PENDING', 'RUNNING', 'AWAITING_CHILDREN')`
  на каждой партиции четырёх подчинённых таблиц — у `tc_execution` статуса нет и индексировать
  нечего. Запрос захвата не содержит ключа партиционирования, отсечение партиций
  не сработает, и без таких индексов планировщик пойдёт по всем партициям сразу. Один индекс
  на все активные статусы, а не отдельный под каждый запрос: главный выигрыш в том, что
  терминальные строки — подавляющее большинство — в индекс не попадают вовсе.

## REST API и события

- Пути живут под `taskcomm.rest.base-path`, вся подсистема выключается `taskcomm.rest.enabled`.
- **Стартер не объявляет `SecurityFilterChain` и вообще не трогает Spring Security.** Он отдаёт бин
  `RequestMatcher` со своими путями, чтобы потребитель вписал их в свою конфигурацию одной строкой.
  Цепочка, объявленная стартером, перекрывает конфигурацию потребителя — запрещено ровно так же,
  как `@EnableScheduling`.
- Состав API: чтение (списки и детали задач, батчей, подзадач, коммуникаций с фильтрами по
  статусам), поиск по содержимому нагрузки, создание задач и коммуникаций, перезапуск упавших
  подзадач, отмена, **весь `Execution` одной выдачей** (всё, что происходило вокруг одного повода,
  в порядке создания, вместе с ключами корреляции и **рёбрами — кем создана каждая сущность**),
  **список полей, доступных для поиска**
  (с подписями и описаниями из реестра — без него оформление было бы write-only), **сводка
  по типам** (сколько задач какого типа в каком статусе) и **признак осиротевшей задачи** в выдаче. Последние два — не удобство: на сводке держится шаг миграции
  «дождаться обнуления», а признак объясняет человеку, почему задача стоит.
- Отдельно у коммуникаций: **история попыток с обменом** (что ушло и что вернулось в каждой
  попытке) и **поиск коммуникации по `request_id`**. Второе — операция разбора инцидента: запрос
  не содержит ключа партиционирования и обходит все партиции, поэтому в горячих путях его
  использовать нельзя ([ADR 0055](docs/adr/0055-communication-exchange-storage.md)).
  Плюс **состояние размыкателей** — только чтение и только ответившего экземпляра, с его именем
  в выдаче ([ADR 0065](docs/adr/0065-communication-circuit-breaker.md)).
- Поиск по нагрузке — **только по белому списку полей**, который объявляет процессор:
  `searchableTaskFields()`, `searchableBatchFields()`, `searchableUnitFields()` — все три
  с реализацией по умолчанию. Уровни объявляются раздельно, потому что нагрузки уровней разного
  типа: в задаче параметры операции, в батче параметры группы, в подзадаче бизнес-объект.
- **Белый список живёт в БД, а не в памяти** — таблица `tc_searchable_field`
  ([ADR 0037](docs/adr/0037-search-field-registry.md)). Реестр описывает уже записанные данные
  и потому обязан переживать выкатку: нагрузка годовой давности лежит в форме годовой давности,
  и правка кода этого не меняет.
- **Тип задачи в запросе не обязателен** и служит лишь необязательным фильтром. Типы выводятся
  из реестра по имени поля: ищем во всех, кто объявил это поле. Требовать `taskType` нельзя —
  это ломает сценарий «найти всё, что делалось с этой сущностью, независимо от типа операции».
- Несколько полей в запросе сужают множество типов до объявивших **все** указанные поля.
  Поле не объявлено никем — `400` со списком известных имён.
- SQL собирается из объявленных `jsonPath` и `FieldType`. Пользовательский ввод в SQL
  не конкатенируется никогда.
- Индексы под поиск стартер **в проде сам не создаёт** — это блокировки на живой таблице в момент
  старта. При старте он проверяет их наличие и при отсутствии пишет WARN с готовым DDL. Уровнем
  мягче, чем проверка схемы: без индекса поиск работает, просто медленно, падать нельзя.
- Индексы частичные, по типу задачи — так они остаются компактными при двух десятках типов:
  `CREATE INDEX ... ON tc_task_unit ((payload->>'orderId')) WHERE task_type = 'order-change'`.
- Подробности и отвергнутые варианты — [ADR 0016](docs/adr/0016-payload-search.md)
  и [ADR 0037](docs/adr/0037-search-field-registry.md).
- **WebSocket отложен**, см. открытые вопросы. Когда дойдёт очередь: события best-effort, UI
  дочитывает состояние через REST при подключении и после разрыва. Хранения недоставленных
  событий не будет — это вторая очередь внутри очереди.

### Реестр полей поиска

- **Запись отождествляется сигнатурой объявления** — `(имя, FieldType, jsonPath)` в рамках своего
  уровня и типа задачи. Граница проходит по вопросу, на который отвечает колонка: **сигнатура —
  всё, что определяет, как данные находятся**, и она неизменяема.
- Отсюда главное следствие: **смена `jsonPath` или `FieldType` — не правка записи, а новое
  объявление.** Старая строка остаётся и продолжает находить старые нагрузки. Не заводить
  «обновление пути»: обновление затирает описание уже записанных данных описанием ещё
  не записанных.
- **`field_title` и `field_description` в сигнатуру не входят и обновляются на месте.** Это
  оформление для UI потребителя — подпись и пояснение поля в форме поиска; про уже записанные
  нагрузки они не утверждают ничего. Иначе исправленная опечатка в описании порождала бы вторую
  строку с тем же путём и вторую одинаковую ветку в поиске. Обе колонки необязательны: не
  заполнили — UI показывает `field_name`.
- Одно имя поля может иметь **разные подписи в разных типах задач** — это не конфликт, а данные.
  Стартер победителя не выбирает, отдаёт строки как есть; группировка — дело UI. Локализации нет:
  одна подпись на том языке, на котором её написали.
- Порядок при старте: собрать объявления процессоров **в памяти** → синхронизировать в таблицу →
  **реестр в памяти выбросить**. Дальше единственный источник истины — таблица, и разбор
  поискового запроса читает её. Проверяется только форма объявления — непустое имя, разбираемый
  путь; конфликтовать объявлениям не о чем.
- Синхронизация: нашли строку по сигнатуре — обновили `last_declared_at` и привели оформление
  к объявленному сейчас; не нашли — вставили; **не удаляем никогда**. Исключение —
  `taskcomm.search.remove-undeclared-fields`, по умолчанию `false`.
- `updated_at` двигается **только если оформление действительно изменилось**; `last_declared_at` —
  каждый старт. Колонка, свежая всегда, не значит ничего.
- Удаление означает ровно одно: поиск по этому полю перестаёт находить старые нагрузки. Данные
  не трогаются, вернуть строку — снова объявить поле и перезапуститься. Выключено по умолчанию
  не из-за опасности, а чтобы удаление не происходило от обновления версии зависимости. Каждая
  удалённая строка — отдельный WARN.
- Циклического удаления при rolling update **не бывает**: старые инстансы только гасятся,
  а удаляется при старте. Постоянное расхождение возможно лишь там, где два набора объявляются
  подолгу, — canary, blue-green, два приложения на одной схеме.
- **Правила «одно имя поля — один `FieldType`» больше нет.** У одного имени могут сосуществовать
  разные типы значения: реестр описывает данные, записанные в разное время и в разной форме.
  Конфликтовать объявлениям не о чем, и падать при старте на этом не за что. На практике
  расхождение будет редким — `payload->>'x'` отдаёт `text`, и почти всё окажется `STRING`.
- `FieldType` при этом не декоративен: он задаёт вид сравнения в SQL и выражение индекса.
  Индекс по `((payload->>'amount'))` не обслужит ветку с приведением к `numeric`.
- Запрос по имени разворачивается в `OR` по **всем** строкам с этим именем. Ветка, чей `FieldType`
  не принимает переданное значение, отбрасывается; отброшены все — `400`.
- Реестр *процессоров* в памяти остаётся: он нужен для диспетчеризации по `taskType` и для
  восстановления Java-типа нагрузки из дженерика. В БД уезжает только белый список полей.

## Наблюдаемость

- Micrometer — `optional`, метрики регистрируются под `@ConditionalOnClass`. Нет Micrometer'а
  у потребителя — стартер молчит и ничего не тянет.
- Метрики: длина очереди, время выполнения, доля ошибок, число повторов — **все с разбивкой
  по типу задачи**, плюс отдельно число осиротевших. Разбивка не декоративная: на ней держится
  шаг миграции контракта «дождаться обнуления счётчика».
- **«Длина очереди» — это `PENDING AND next_attempt_at <= now()`**, а не число `PENDING`
  ([ADR 0050](docs/adr/0050-deferred-start.md)). `PENDING` смешивает три популяции: ждущих
  мощности, ждущих backoff и отложенных. Считать их вместе — значит показывать «мы перегружены»
  там, где правда «мы падаем»: добавление воркеров на две последние не влияет никак.
- Рядом обязательны ещё две: **`delayed`** — `PENDING AND next_attempt_at > now()` с разбивкой
  по причине, и **`oldest_claimable_age`** — возраст самой старой захватываемой работы.
  Второе и есть сигнал SLA: количество отвечает на «сколько», а не на «опаздываем ли».
- **Длина очереди и `oldest_claimable_age` получают разбивку по поллеру и приоритету**
  ([ADR 0063](docs/adr/0063-claim-ordering-and-pollers.md)). Без неё выделенные поллеры невидимы,
  а `oldest_claimable_age` по всей очереди начинает врать: старейшая строка может быть
  низкоприоритетной и ждать совершенно законно.
- **Размыкатель**: метрика состояния по каждой системе и счётчик переходов; каждый переход — WARN
  с системой, причиной и долей отказов ([ADR 0065](docs/adr/0065-communication-circuit-breaker.md)).
  Разомкнутая система законно растит свой `oldest_claimable_age` — её сообщения правда опаздывают.
- **Health indicator — это живость собственных потоков экземпляра, и ничего больше**
  ([ADR 0051](docs/adr/0051-engine-health.md)). Красный, если поток поллера или поток heartbeat
  не тикали дольше заданного числа своих интервалов.
- В индикатор **не класть** длину очереди (краснела бы при исправной работе под нагрузкой),
  наличие истёкших аренд (истекают штатно при превышении предела обработки) и доступность БД
  (у неё свой индикатор). Индикатор, краснеющий при нормальной нагрузке, обесценивает мониторинг
  всего приложения, а не только нашей подсистемы.
- **Громкое предупреждение при старте, если не зарегистрировано ни одного процессора** — почти
  наверняка ошибка сборки. Но не `DOWN` и не падение: движок исправен, ему нечего делать.
- Структурные логи: `executionId`, `taskId`, `batchId`, `unitId` и номер попытки в MDC. Ключи идут
  **с префиксом, по умолчанию `tc.`** — `tc.executionId`, `tc.taskId`, `tc.unitId`; префикс
  настраивается через
  `taskcomm.logging.mdc-prefix`. Префикс нужен потому, что потребителю прямо разрешено класть
  в MDC своё, и столкновение имён вроде `taskId` иначе неизбежно.
- **MDC снимается восстановлением снимка**, а не удалением своих ключей поимённо. Потребитель
  может положить внутри `process()` свой `businessId` — при поимённой очистке этот ключ утёк бы
  в пул потоков и отравил чужие логи.
- **Лог неуспешной попытки пишется до восстановления снимка**, иначе в самой нужной строке
  бизнес-идентификатора не окажется.
- Мост «номер заказа → строка лога» держится на потребителе: своего бизнес-ключа у стартера нет
  ([ADR 0034](docs/adr/0034-mdc-business-id.md)). Логи, которые стартер пишет **вне** вызова
  процессора — захват, истечение аренды, закрытие родителя, — бизнес-значений не содержат
  и содержать не могут.
- Работа с MDC живёт в одном месте, а не размазана по воркеру.

## Схема и миграции

- Стартер везёт **и** Liquibase-changelog, **и** голый DDL, оба в
  `taskcomm-autoconfigure/src/main/resources/db/`. Liquibase — `optional`-зависимость.
  Потребитель на Liquibase включает наш master одной строкой:
  `<include file="db/changelog/taskcomm/master.xml" relativeToChangelogFile="false"/>` —
  changelog читается прямо из jar, миграции попадают в его `DATABASECHANGELOG`.
  Потребители на других инструментах берут голый DDL и нумеруют его у себя.
- Схема в changeSet'ах **не указывается** — применяется `defaultSchemaName` потребителя.
- **Каждая колонка снабжается комментарием на русском языке** — в голом DDL через
  `COMMENT ON COLUMN`, в Liquibase-changelog через `remarks` у колонки. Оба пути потребитель может
  выбрать, и в обоих схема обязана объяснять себя.
- Комментарий пишется про **смысл**, а не про тип: «факт того, что раскрытие дошло до конца», а не
  «timestamptz, nullable». Тип и ограничения и так видны в описании таблицы.
- Особенно это касается колонок, которые без пояснения выглядят дублем или ошибкой: собственная
  `created_at` и денормализованная `execution_created_at` — во **всех четырёх** таблицах,
  `cancel_requested_at` как факт, а не статус, `status_description` как общая
  причина для `SKIPPED` и `CANCELLED`, `execution_created_at` в `tc_communication_correlation`
  как ключ отсечения партиций, а не как время чего-либо в самой строке.
- Отдельно обязательны пояснения к порядку захвата: **`priority` со шкалой по возрастанию** —
  «меньше значит важнее», это противоположно интуиции; и **`claim_order_at`** как ключ сортировки
  в форме отметки времени, а **не** время захвата и не время какого-либо события.
- У колонок `origin_*` комментарий обязан сказать, что **пустое значение — норма**: у корневых
  сущностей указателя нет вовсе, а у детей раскрытия создатель выражен `parent_attempt_id`,
  и рёбра дела собираются по двум правилам. Без этого пояснения колонки выглядят
  недозаполненными ([ADR 0064](docs/adr/0064-entity-origin-links.md)).
- В `tc_communication_attempt` пояснения обязательны для всего обмена: `request_at`/`response_at`
  как время **из сообщения**, а не время захвата и завершения; `request_body`/`response_body`
  как сырой слепок, где **двоичные форматы лежат в base64**; `response_status` как осмысленный
  только у REST и SOAP; пустая половина ответа как нормальное состояние, а не потеря данных.
- Комментарии объявляются на родительской партиционированной таблице: смотрят в `psql`
  и в инструментах именно её, а не отдельные партиции.
- `taskcomm.schema.initialize` (`never` | `embedded` | `always`, дефолт `embedded`) поднимает
  `DataSourceScriptDatabaseInitializer` — это для тестов и локальной разработки.
  Продовую схему он не ведёт и не должен.
- **Выпущенный changeSet неприкосновенен.** Правка старого ломает контрольную сумму у каждого,
  кто его уже накатил, и приложение не стартует. Только новые changeSet'ы.
- **Миграции только аддитивные.** При rolling update новая схема какое-то время работает со старым
  кодом. Удаление и переименование колонки — не раньше следующего релиза после того, как код
  перестал ими пользоваться.
- Миграция, требующая ручного вмешательства при обновлении, — ломающее изменение, мажорная версия.
- При старте стартер **проверяет свои таблицы и колонки и падает с внятным сообщением**, если схема
  не соответствует версии. Потребитель должен прочитать «примени миграции taskcomm 2.1.0», а не
  ловить `column tc_task.contract_shape does not exist` на третий день работы.

## Стиль кода

- Конструкторная инъекция, поля `final`, `@RequiredArgsConstructor`. Полевая инъекция запрещена.
- Фичи Java 21 приветствуются: `record` для DTO и value-объектов, `sealed` для состояний,
  pattern matching в `switch`, text blocks для SQL.
- **Виртуальные потоки — с осторожностью и только по явному согласованию.** Помнить про pinning на
  `synchronized` и про то, что узким местом становится пул JDBC-соединений, а не потоки.
- Маппинг — MapStruct, руками мапперы не писать.
- Логирование — `@Slf4j`, параметризованные сообщения (`log.debug("задача {} провалена", id)`),
  без конкатенации строк.
- `Optional` — только как возвращаемое значение; не поле, не параметр метода.
- Исключения наследуются от общего `TaskcommException`. Не глотать и не делать
  «залогировал и пробросил» одновременно.
- Javadoc обязателен для всех публичных типов и методов (то есть для всего вне `internal`).
- **Комментарии, Javadoc и сообщения коммитов — на русском языке.**
- **Кальки с английского запрещены.** Проверка простая: есть обычное русское слово — берём его;
  слово называет паттерн, технологию или ключевое слово — оставляем **латиницей**,
  не транслитерируем.
  - Уже спотыкались: **ретенция** → очистка, глубина хранения; **контенция** → конкуренция
    за строку; **гранулярность** → детализация.
  - Не трогать: **fan-in**, **fan-out**, **backoff**, **heartbeat**, `SKIP LOCKED` — это имена,
    а не кальки.
  - «Персистентность» — исключение: термин проекта с самого начала, менять его поздно и незачем.
- **Не изобретать терминов.** Либо обычное русское слово, либо термин, уже определённый
  в доменном словаре. Самодельное слово хуже кальки: оно выглядит устоявшимся, и читатель идёт
  искать определение, которого нет. Если подходящего варианта не нашлось и хочется завести
  новый термин — **спроси явно**, не вводи молча.
  - Уже спотыкались: **«миллионный путь»** про чтение, идущее по миллиону строк. Мало того что
    нигде не определено, так ещё и читается как порядковое числительное — «путь номер миллион».

Обязательства, которые проверяет Checkstyle, — пиши сразу так, а не переписывай после прогона:

- `this.` перед каждым обращением к полю (`RequireThis`).
- `final` на всех параметрах и локальных переменных (`FinalParameters`, `FinalLocalVariable`).
- `package-info.java` с Javadoc **в каждом `api`-пакете** (`JavadocPackage`; для `internal`
  и тестов подавлено в `checkstyle-suppressions.xml`). Отдельно `MissingJavadocPackage` требует
  Javadoc в любом заведённом `package-info.java`, где бы он ни лежал.
- Аббревиатуры в CamelCase: `SqlBuilder`, `JsonCodec`, `RestApiConfig` — не `SQLBuilder`
  и не `RestAPIConfig` (`AbbreviationAsWordInName`).
- Не более трёх `return` на метод, фигурные скобки обязательны даже для однострочников.
- `org.junit.jupiter.api.Assertions` запрещён импортом — только AssertJ.

## Тесты

- `*Test` — unit-тесты, `*IT` — интеграционные.
- Автоконфигурации проверяются через `ApplicationContextRunner`. Для каждой автоконфигурации —
  минимум три сценария: бины создаются по умолчанию; подсистема выключается своим
  `enabled=false`; бин потребителя перекрывает наш (проверка, что `@ConditionalOnMissingBean`
  реально работает).
- ArchUnit-тест обязателен и проверяет: пакеты `internal` не импортируются извне своей подсистемы;
  `api` не зависит от `internal`; в `internal` нет стереотипных аннотаций Spring.
- Утверждения — AssertJ (`assertThat`), не `Assertions.assertEquals`.

## Совместимость и публикация

- Semver. Текущая версия — `2.0.0`.
- Мажорная версия поднимается **только** при потере обратной совместимости, и этого стараемся не
  допускать. Прежде чем менять публичную сигнатуру — предложи вариант с сохранением совместимости
  (перегрузка, `default`-метод, новый тип) и явно скажи, что альтернатива требует мажорной версии.
- Новое свойство конфигурации обязано иметь значение по умолчанию, сохраняющее прежнее поведение.
- Свойства и API не удаляются сразу: сначала `@Deprecated` с указанием замены, удаление — в
  следующей мажорной версии.

## Чего не делать без явной просьбы

- Не коммитить и не пушить. Изменения оставляй в рабочей копии, я коммичу сам.
- Не понижать версии зависимостей.
- Не добавлять новые внешние зависимости в `taskcomm-autoconfigure` — каждая становится транзитивной
  для всех потребителей. Сначала предложи и обоснуй.
- Не менять публичные сигнатуры, не сказав об этом прямо.
- Не отключать и не подавлять правила Checkstyle / Spotless / Error Prone, чтобы «прошла сборка».
  Чини код, а не правило.

## Порядок обсуждения

- **Ответ уточняющим вопросом на твой вопрос — это уточняющий вопрос, а не решение.** Услышав
  в ответ «а какую проблему мы решаем?» или «а какая цена такого-то варианта?», отвечай на
  заданное и **задавай свой вопрос повторно**. Выводить решение из формулировки встречного
  вопроса запрещено: вопрос выражает сомнение, а не выбор, и догадка о том, какой вариант за ним
  стоит, ошибётся ровно тогда, когда обсуждение важнее всего.
- Развилку закрывает человек. Пока прямого ответа нет, она открыта — сколько бы раундов
  ни потребовалось.

## Известные грабли сборки

- **Lombok + MapStruct**: нужен `org.projectlombok:lombok-mapstruct-binding` в `annotationProcessor`,
  иначе MapStruct отработает раньше Lombok и не увидит сгенерированные геттеры.
- **Error Prone + Java 21**: плагин `net.ltgt.errorprone`, компилятору нужны
  `-XDcompilePolicy=simple` и `--should-stop=ifError=FLOW`. На коде, сгенерированном Lombok,
  возможны ложные срабатывания — глушить точечно, не целым правилом.
- **Spotless и Checkstyle** должны быть настроены на один и тот же стиль, иначе они начнут
  переписывать код друг за другом.
- **Spotless + palantir-java-format на JDK младше 21**: см. раздел «Каталог версий» —
  Gradle daemon должен работать на JDK 21, иначе форматирование Java 21-конструкций падает.

## Открытые вопросы

Не решено — если задача упирается в один из пунктов, спроси, не выбирай сам:

1. WebSocket-подписка на события задач — отложена. Главная нерешённая часть: как событие с одного
   инстанса доходит до UI, подключённого к другому. Кандидат — Postgres `LISTEN/NOTIFY`, потому что
   не требует новой инфраструктуры у потребителей; Redis отвергнут по этой же причине.
2. **Поиск по нагрузке коммуникаций.** Белый список полей объявлен только для задач —
   `searchableTaskFields()`, `searchableBatchFields()`, `searchableUnitFields()`
   ([ADR 0037](docs/adr/0037-search-field-registry.md)); у коммуникаций есть только лукап
   по `request_id`. Сценарий «найти коммуникации по параметру вне зависимости от исполнения,
   а потом посмотреть связанные задачи» этим не обслуживается и пока обходится фильтром
   по `source` / `destination` внутри дела
   ([ADR 0064](docs/adr/0064-entity-origin-links.md)).

   Что решать, когда дойдёт очередь: общий это реестр с задачами или свой; объявляет поля
   процессор коммуникаций или что-то ещё; и по какой из двух доменных форм идёт поиск —
   `request_payload`, `response_payload` или по обеим. Изменение аддитивное, а до первого
   релиза ещё и не ломающее, поэтому ждать его не обязано ни одно другое решение.
3. **Механизм событий после `process`.** Вопрос **спорный**, и пока это так, формулировка важнее
   вариантов: речь о мутации сущностей без аспектов — если такое понадобится. То есть о штатном
   способе для потребителя дотянуться до сущности по завершении обработки, вместо того чтобы
   обвешивать вызовы стартера аспектами Spring AOP.
   Разбора вариантов не было, и цены механизма никто не считал. Изменение аддитивное, поэтому
   ничего не блокирует и ждёт первого реального применения.

Из списка **вышли** два вопроса, и оба закрыты [ADR 0064](docs/adr/0064-entity-origin-links.md).
Таблица связей сущностей: closure table не понадобился — ни один из сценариев не оказался обходом
графа, а `Execution` и есть замыкание; хранится только указатель на создателя, колонками `origin_*`
в двух таблицах. Доступ процессора к данным породившей его коммуникации: тот же указатель даёт
прямое чтение с отсечением партиций, а `ExecutionService` получил первых потребителей.

Вышел и размыкатель — закрыт [ADR 0065](docs/adr/0065-communication-circuit-breaker.md). Внутри
него отложены синхронизация состояния между экземплярами и ручное управление через REST; это
не открытый вопрос, а следующий шаг уже принятого решения.
