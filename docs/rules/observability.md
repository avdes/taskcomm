# Наблюдаемость

> Правила проекта, вынесенные из [CLAUDE.md](../../CLAUDE.md) по теме: метрики, health indicator, логи и MDC.
> Приоритет у них тот же, что у CLAUDE.md; обоснования — в [ADR](../adr/README.md).

- Micrometer — `optional`, метрики регистрируются под `@ConditionalOnClass`. Нет Micrometer'а
  у потребителя — стартер молчит и ничего не тянет.
- Метрики: длина очереди, время выполнения, доля ошибок, число повторов — **все с разбивкой
  по типу задачи** (у коммуникаций — по внешней системе), плюс отдельно число осиротевших —
  задач типов без процессора и коммуникаций систем без процессора
  ([ADR 0105](../adr/0105-orphan-communications.md)). Разбивка не декоративная: на ней держится
  шаг миграции контракта «дождаться обнуления счётчика».
- **«Длина очереди» — это `PENDING AND next_attempt_at <= now()`**, а не число `PENDING`
  ([ADR 0050](../adr/0050-deferred-start.md)). `PENDING` смешивает три популяции: ждущих
  мощности, ждущих backoff и отложенных. Считать их вместе — значит показывать «мы перегружены»
  там, где правда «мы падаем»: добавление воркеров на две последние не влияет никак.
- Рядом обязательны ещё две: **`delayed`** — `PENDING AND next_attempt_at > now()` с разбивкой
  по причине, и **`oldest_claimable_age`** — возраст самой старой захватываемой работы.
  Второе и есть сигнал SLA: количество отвечает на «сколько», а не на «опаздываем ли».
- **Длина очереди и `oldest_claimable_age` получают разбивку по поллеру**
  ([ADR 0063](../adr/0063-claim-ordering-and-pollers.md)): без неё выделенные поллеры невидимы.
  **Метки приоритета нет ни у одной метрики** ([ADR 0102](../adr/0102-schema-wide-metrics-snapshot.md)):
  приоритет задаётся любым значением, и метка раздула бы число рядов у потребителя.
- **Просрочка** — `max(now() − claim_order_at)` по захватываемым строкам, не меньше нуля,
  по типу и поллеру — у поллеров с формой `deadline`. Она отвечает на вопрос, на который
  `oldest_claimable_age` по всей очереди врёт: старейшая строка может быть низкоприоритетной и ждать
  законно, а просрочка показывает только тех, кто опоздал сверх своей форы. У форм `priority`
  и `quota` сигналом остаётся `oldest_claimable_age`: при строгом приоритете низкие ждут законно.
- **Метрики на всю схему считает один экземпляр за такт в снимок, публикуют все из снимка**
  ([ADR 0102](../adr/0102-schema-wide-metrics-snapshot.md)). Это длина очереди, `delayed`,
  `oldest_claimable_age`, просрочка, незавершённые и осиротевшие по типу или системе.
  - Справочник `tc_metrics_snapshot`: строка на сочетание метрики и меток, значение,
    `computed_at`. Считает экземпляр, взявший `pg_try_advisory_xact_lock` по постоянному ключу,
    одной транзакцией: обновил строки этого такта, удалил не обновлённые. Подсчёты — с границей
    активных партиций ([partitioning.md](partitioning.md)).
  - Каждый экземпляр по своему такту читает снимок и отдаёт значения из памяти; опрос метрик
    в базу не ходит. Такт — `taskcomm.metrics.interval`.
  - Каждый экземпляр публикует **возраст снимка** — `now() − computed_at`: снимок, который
    никто не обновляет, виден по нему.
  - Описание каждой метрики из снимка обязано сказать: значение на всю схему, агрегировать
    по экземплярам `max()`, не `sum()`.
  - Метрики того, что сделал сам экземпляр, — время выполнения, доля ошибок, повторы, такт
    захвата, состояние размыкателей — в снимок **не идут**: их сумма по экземплярам верна.
- **Размыкатель**: метрика состояния по каждой системе и счётчик переходов; каждый переход — WARN
  с системой, причиной и долей отказов ([ADR 0065](../adr/0065-communication-circuit-breaker.md)).
  Разомкнутая система законно растит свой `oldest_claimable_age` — её сообщения правда опаздывают.
- **Health indicator — это живость собственных потоков экземпляра, и ничего больше**
  ([ADR 0051](../adr/0051-engine-health.md)). Красный, если поток поллера или поток heartbeat
  не тикали дольше заданного числа своих интервалов.
- В индикатор **не класть** длину очереди (краснела бы при исправной работе под нагрузкой),
  наличие истёкших аренд (истекают штатно при превышении предела обработки) и доступность БД
  (у неё свой индикатор). Индикатор, краснеющий при нормальной нагрузке, обесценивает мониторинг
  всего приложения, а не только нашей подсистемы.
- **Громкое предупреждение при старте, если не зарегистрировано ни одного процессора** — почти
  наверняка ошибка сборки. Но не `DOWN` и не падение: движок исправен, ему нечего делать.
- Структурные логи: `executionId`, `taskId`, `batchId`, `unitId` и номер попытки в MDC. Ключи идут
  **с префиксом, по умолчанию `tc.`** — `tc.executionId`, `tc.taskId`, `tc.unitId`; префикс
  настраивается через
  `taskcomm.logging.mdc-prefix`. Префикс нужен потому, что потребителю прямо разрешено класть
  в MDC своё, и столкновение имён вроде `taskId` иначе неизбежно.
- **MDC снимается восстановлением снимка**, а не удалением своих ключей поимённо. Потребитель
  может положить внутри `process()` свой `businessId` — при поимённой очистке этот ключ утёк бы
  в пул потоков и отравил чужие логи.
- **Лог неуспешной попытки пишется до восстановления снимка**, иначе в самой нужной строке
  бизнес-идентификатора не окажется.
- Мост «номер заказа → строка лога» держится на потребителе: своего бизнес-ключа у стартера нет
  ([ADR 0034](../adr/0034-mdc-business-id.md)). Логи, которые стартер пишет **вне** вызова
  процессора — захват, истечение аренды, закрытие родителя, — бизнес-значений не содержат
  и содержать не могут.
- Работа с MDC живёт в одном месте, а не размазана по воркеру.
