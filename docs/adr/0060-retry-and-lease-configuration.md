# 0060. Настройки повторов и аренды

- **Дата:** 2026-09-03
- **Статус:** принято

## Контекст

Механика повторов и аренды описана подробно: backoff с джиттером ([0009](0009-retry-and-progress.md)),
попытки считают захваты ([0044](0044-attempt-log.md)), предел обработки как счётчик продлений
([0021](0021-execution-time-limit.md)), heartbeat около трети аренды ([0025](0025-lease-mechanics.md)).
Три места в документации прямо обещают, что всё это настраивается.

А настроек нет. В примере конфигурации стоит одна строка — `taskcomm.task.retry.max-attempts: 3`.
Ни длительности аренды, ни интервала heartbeat, ни предела обработки, ни параметров backoff, ни
настроек поллера. Этап 3 (персистентность) и этап 4 (движок) упрутся в это сразу: захват нечем
параметризовать.

## Рассмотренные варианты

### Общий корень или свои наборы

#### A. Общий корень на обе подсистемы — отвергнуто

`taskcomm.lease.*` и `taskcomm.retry.*` как значения по умолчанию, подсистема перекрывает при
необходимости. Меньше писать в типичном случае.

Отвергнуто: [0010](0010-separate-engines.md) разделил подсистемы намеренно, и общий корень
конфигурации — первый шаг к общему коду, который читает этот корень. Плюс профили нагрузки разные
по существу: коммуникация ждёт внешнюю систему секунды, подзадача считает миллисекунды.

#### B. Свои наборы у каждой подсистемы — выбрано

### Чем задаётся предел обработки

#### C. Числом продлений аренды — отвергнуто

Что внутри, то и снаружи: `max-lease-renewals: 90`. Никакого пересчёта и никаких сюрпризов при
смене интервала heartbeat.

Отвергнуто по эксплуатации. Во время инцидента человек думает временем, а не тактами, и вопрос
«сколько это в минутах» требует умножения в уме — ровно тогда, когда думать некогда.

#### D. Временем — выбрано

`max-execution-time: 30m`. Внутри остаётся счётчиком: `duration / heartbeat-interval`.

### Что переопределяется по типу задачи

#### E. Только предел обработки — отвергнуто

Буква [0021](0021-execution-time-limit.md), который ввёл переопределение ровно для предела.

Отвергнуто как слишком узкое. Синхронизация справочников раз в сутки и срочная выгрузка — разные
звери целиком: у них разные ожидания по числу повторов, по backoff и по длительности аренды, а не
только по пределу.

#### F. Повторы и аренда — выбрано

#### G. Плюс поллер и пул воркеров — отвергнуто здесь

Свой такт и свой пул на тип задачи — это фактически отдельная очередь под каждый тип. Вещь
осмысленная, но это другое решение с другой ценой; оно принимается
в [0063](0063-claim-ordering-and-pollers.md), а не здесь.

## Решение

Наборы **свои у каждой подсистемы**, общего корня нет.

```yaml
taskcomm:
  task:
    poll: { interval: 1s, batch-size: 100, workers: 8 }
    lease: { duration: 60s, heartbeat-interval: 20s, max-execution-time: 30m }
    retry: { max-attempts: 3, initial-delay: 5s, multiplier: 2.0, max-delay: 1h, jitter: 0.2 }
    types:
      price-update:
        lease: { max-execution-time: 30m }
        retry: { max-attempts: 5 }
        phases:
          expand:
            lease: { max-execution-time: 2h }
  communication:
    poll: { interval: 1s, batch-size: 100, workers: 8 }
    lease: { duration: 60s, heartbeat-interval: 20s, max-execution-time: 5m }
    retry: { max-attempts: 5, initial-delay: 10s, multiplier: 2.0, max-delay: 1h, jitter: 0.2 }
    systems:
      supplier-b:
        rate-limit-per-instance: 10
        retry: { max-attempts: 8 }
```

- Ключ переопределения у задач — `taskType`, у коммуникаций — **имя внешней системы**: по нему же
  ищется процессор ([0011](0011-communication-model.md)). Слово `types` там не годится,
  `communicationType` рассмотрен и отвергнут в [0052](0052-communication-transport-contracts.md).
- Пофазное измерение `phases` объясняется в [0061](0061-processor-configuration-annotations.md):
  без него `yaml` не смог бы точечно перекрыть аннотацию на методе.
- Все длительности — формат `Duration` Spring Boot, как уже сделано у `discard-after: 7d`.

### Повторы относятся ко всем видам попыток

`retry` и `lease` действуют на `PROCESS`, `EXPAND` и `COLLECT` одинаково. Сказать это надо прямо:
[0009](0009-retry-and-progress.md) говорит только про `TaskUnit`, и его легко прочесть так, будто
раскрытие и сборка не повторяются. Повторяются, и под теми же настройками.

### Проверки при старте

Граница проходит по вопросу «способна ли система вообще работать с этим значением».

**Падение при старте** — значения, бессмысленные по построению:

- `max-attempts < 1`;
- `initial-delay > max-delay`, `multiplier < 1`;
- `jitter` вне `(0, 1]` — в том числе **ноль**: джиттер объявлен обязательным
  ([0009](0009-retry-and-progress.md), «без джиттера механизм повторов превращается в механизм
  отказа в обслуживании»), и настройка не должна выключать то, что решение назвало обязательным;
- `max-execution-time < heartbeat-interval` — предел меньше одного такта убивал бы работу сразу.

**Предупреждение** — плохие, но рабочие соотношения:

- `heartbeat-interval > duration / 3` — как уже решил [0025](0025-lease-mechanics.md), громко
  и с рекомендуемым значением;
- `duration <= poll.interval` — аренда истекает быстрее, чем поллер приходит;
- `batch-size > workers` — захваченные сверх числа воркеров строки держат аренду, пока до них
  дойдёт очередь.

## Последствия

- **Точность предела — до такта heartbeat**, потому что внутри он остаётся счётчиком продлений.
  `max-execution-time: 30m` при `heartbeat-interval: 20s` означает 90 продлений, то есть «тридцать
  минут плюс-минус двадцать секунд».
- **Смена `heartbeat-interval` пересчитывает предел молча.** Уменьшили интервал вдвое — число
  продлений выросло вдвое, а фактический предел остался прежним; это верно и неочевидно. Обратная
  сторона выбора «задавать временем».
- **Числа в примере — отправная точка, а не рекомендация.** Их надо перепроверить нагрузкой
  на этапах 3–4, и это стоит пометить прямо в документации, иначе через год их примут за выверенные.
- **Поверхность конфигурации выросла с одной строки до трёх десятков ключей**, и каждый из них —
  публичный контракт: новое свойство обязано иметь значение по умолчанию, сохраняющее прежнее
  поведение, а удалять свойства нельзя без мажорной версии.
- **Два набора одинаковых по форме ключей**, `task` и `communication`, которые надо держать
  в голове. Признанная цена независимости подсистем; общий корень был бы дешевле в написании
  и дороже в поддержке.
- Настройки существуют **на трёх уровнях сразу** — глобально, по типу, по фазе, — и это ещё
  не всё: аннотации добавляют два ([0061](0061-processor-configuration-annotations.md)). Без печати
  итоговых значений при старте разобраться в этом будет нельзя.
