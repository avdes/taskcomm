# 0031. Поиск по нагрузке батча вместо бизнес-ключа

- **Дата:** 2026-08-27
- **Статус:** принято
- **Изменено:** [0032](0032-no-business-key.md) — расщепление на `Emitter` и `UnitEmitter` отменено
  вместе с бизнес-ключом у подзадачи. Третий уровень белого списка `searchableBatchFields()`
  и отсутствие ключа у батча остаются в силе.
- **Изменено:** [0037](0037-search-field-registry.md) — правило «одно имя поля — один `FieldType`
  во всём реестре», на которое здесь ссылаются, снято. Три уровня белого списка остаются в силе.

## Контекст

При разборе схемы выяснилось, что колонка `business_key` в `tc_task_batch` **не была решением**.
Она возникла побочно: `Emitter<T>` — один и тот же тип на обоих уровнях каскада, перегрузка
`emit(businessKey, payload)` доступна и при порождении батчей, и при порождении подзадач. Значит
батч тоже мог нести ключ. Обоснование в [0008](0008-expansion-emitter.md) при этом написано только
про подзадачу: «искать по номеру заказа, а не по внутреннему id».

Одновременно обнаружилась смежная дыра. [0016](0016-payload-search.md) определил поиск по нагрузке
ровно для двух уровней — `searchableTaskFields()` и `searchableUnitFields()`. Нагрузка батча `B`
(параметры группы: к какому контрагенту относится, какой диапазон покрывает) в поиске
не участвует вовсе.

То есть найти конкретный батч можно было только случайно уцелевшим побочным полем, а осмысленный
механизм поиска для этого уровня отсутствовал.

## Рассмотренные варианты

### A. Оставить `business_key`, третий уровень поиска не заводить — отвергнуто

Дёшево и ничего не добавляет в API. Но адресация батча держалась бы на поле, которое никто
не проектировал, а нагрузка батча оставалась бы невидимой для поиска. Необъяснённая колонка в схеме
живёт до первого человека, наводящего порядок.

### B. Завести `searchableBatchFields()`, убрать `business_key` у батча — выбрано

Батч адресуется тем же механизмом, что задача и подзадача, — по объявленным полям своей нагрузки.

### C. Убрать и то и другое — отвергнуто

Батч считался бы чисто внутренней группировкой и адресовался только через задачу. Последовательно,
но лишает возможности найти группу по контрагенту при разборе инцидента.

## Решение

Заводится **`searchableBatchFields()`**, симметрично двум другим уровням. Колонки `business_key`
у батча **нет**; перегрузка `emit(businessKey, payload)` доступна только при порождении подзадач.

Отсюда `Emitter` перестаёт быть единственным типом:

```java
public interface Emitter<T> {
    void emit(T payload);
}

public interface UnitEmitter<U> extends Emitter<U> {
    void emit(String businessKey, U payload);
}
```

Соответственно `expand(Task<P>, Emitter<B>)` и `expandBatch(TaskBatch<B>, UnitEmitter<U>)`.

## Последствия

- Реестр полей поиска получает **третий уровень**. Правило «одно имя поля — один `FieldType`
  во всём реестре» ([0016](0016-payload-search.md)) охватывает все три: имя живёт в общем
  пространстве имён независимо от уровня, иначе один и тот же запрос значил бы разное.
- Появляется третий набор частичных индексов — по нагрузке `tc_task_batch`, с условием по типу
  задачи. Их стартер по-прежнему не создаёт, а проверяет и печатает DDL.
- Поиск по полям батча возвращает **батчи**. Чтобы от них подняться к задачам, нужна отдельная
  операция REST — из батча в родителя.
- `Emitter` расщепляется на два интерфейса, то есть контракты процессоров расходятся ещё немного.
  Это цена отказа от бизнес-ключа на уровне батча.
- Колонка `business_key` остаётся только у `tc_task_unit`. Ни схемы, ни `Emitter` в коде пока нет —
  готов только скелет, — поэтому миграция не требуется.
- **Сценарий «найти батч, не зная задачи» не подтверждён.** Механизм заведён по симметрии
  с двумя другими уровнями. Если через год окажется, что `searchableBatchFields()` не реализовал
  ни один потребитель, это повод для нового ADR, снимающего уровень, — а не для того, чтобы
  оставить неиспользуемый код навсегда.
