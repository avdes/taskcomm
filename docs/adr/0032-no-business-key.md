# 0032. Бизнес-ключ убран полностью: адресация только по нагрузке

- **Дата:** 2026-08-28
- **Статус:** принято
- **Изменено:** [0034](0034-mdc-business-id.md) — потеря моста «номер заказа → строка лога»
  частично закрыта: идентификатор в MDC кладёт сам потребитель внутри `process()`.

## Контекст

[0008](0008-expansion-emitter.md) ввёл перегрузку `emit(businessKey, payload)` — чтобы подзадачу
можно было найти в REST и логах по номеру заказа, а не по внутреннему идентификатору.

Позже [0016](0016-payload-search.md) ввёл поиск по содержимому нагрузки через белый список полей,
а [0031](0031-batch-addressing.md) распространил его на батчи и убрал бизнес-ключ у батча.

После этого у подзадачи осталось **два механизма адресации, решающих одну задачу**: бизнес-ключ
в отдельной колонке и поиск по объявленному полю нагрузки. Номер заказа при этом всё равно лежит
в нагрузке — иначе процессору нечего было бы обрабатывать.

## Рассмотренные варианты

### A. Оставить оба — отвергнуто

Дублирование в чистом виде: две колонки, два индекса, два способа найти одно и то же. Потребителю
пришлось бы понимать, когда какой применять, а нам — объяснять разницу, которой нет.

### B. Оставить только бизнес-ключ — отвергнуто

Дешевле по индексам, но работает лишь для одного значения на строку и не покрывает поиск
по нескольким полям сразу. Белый список умеет и то и другое.

### C. Оставить только поиск по нагрузке — выбрано

## Решение

**Колонки `business_key` нет ни у одной сущности.** Перегрузка `emit(businessKey, payload)`
не существует; `Emitter<T>` — один интерфейс с единственным методом:

```java
public interface Emitter<T> {
    void emit(T payload);
}
```

`expand(Task<P>, Emitter<B>)`, `expandBatch(TaskBatch<B>, Emitter<U>)` — обе сигнатуры симметричны.

Расщепление на `Emitter` и `UnitEmitter`, введённое в [0031](0031-batch-addressing.md), **отменяется**:
оно существовало только ради ключа, а ключа больше нет.

## Последствия

- Контракты процессоров **перестают расходиться** на этом месте. Цена, названная в 0031, исчезла
  вместе с причиной.
- Механизм адресации ровно один: объявленные поля нагрузки. Меньше API, меньше объяснений
  в документации, меньше поводов ошибиться.
- **Идентификатор бизнес-объекта обязан лежать в самой нагрузке и быть объявлен в белом списке.**
  Иначе подзадачу не найти вообще ничем, кроме внутреннего идентификатора. Раньше это было
  желательно, теперь это требование к потребителю, и оно должно быть в
  [consumer-contract.md](../consumer-contract.md).
- **Потеря: исчезает дешёвый мост «номер заказа → строка лога».** В MDC пишутся `taskId`,
  `batchId`, `unitId` ([0015](0015-observability.md)) — бизнес-значений там нет. Найти работу
  по номеру заказа в логах напрямую больше нельзя: сначала REST-поиск по нагрузке, оттуда
  идентификатор, и уже по нему грепать логи. Два шага вместо одного.
- Из списка индексов уходит неуникальный индекс по бизнес-ключу.

## Связанные решения

- [0031](0031-batch-addressing.md) — расщепление `Emitter`, отменённое здесь.
- [0016](0016-payload-search.md) — единственный оставшийся механизм адресации.
