# 0069. Фаза родителя — явная колонка `phase`

- **Дата:** 2026-10-07
- **Статус:** принято
- **Изменено:** [0070](0070-cancellation-on-any-entity.md) — у отменённой сущности и у сущности с отменённым предком сборка
  не запускается: когда незавершённых потомков не осталось, сущность сразу становится терминальной.

## Контекст

[0048](0048-collect-phase.md) ввёл сборку: «дети закончились — родитель возвращается в захват
и получает попытку вида `COLLECT`». Как именно он туда возвращается, не описано, и при сверке
документов вскрылись три пробела:

- **кто и куда переводит родителя**, когда дети закончились. Первая ветка захвата
  ([0046](0046-lease-in-attempt.md)) берёт только `PENDING`, а родитель стоит
  в `AWAITING_CHILDREN`;
- **какой у него статус во время сборки.** `RUNNING` по [0023](0023-parent-statuses.md) означает
  «плоская задача выполняется, задача с детьми раскрывается»;
- **куда он уходит после неудачной сборки, ожидая повтора.** Если в `PENDING`, то при следующем
  захвате воркеру придётся вычислять, какую попытку открыть — `EXPAND` или `COLLECT`. Это ровно тот
  косвенный вывод, который 0048 запретил для вида попытки. Неудачное раскрытие уходит в тот же
  `PENDING`, и снаружи два случая неотличимы.

## Рассмотренные варианты

### A. Своя пара статусов для сборки — отвергнуто

`AWAITING_COLLECT` — готов к сборке или ждёт её повтора, `COLLECTING` — сборка захвачена.
Состояние читается из одного статуса, и по правилу [0068](0068-expansion-children-statuses.md)
статусы допустимы: состояния исключают остальные.

Отвергнуто из-за асимметрии. `PENDING` и `RUNNING` по-прежнему обслуживают и обработку плоской
задачи, и раскрытие, а сборка получает отдельную пару. Фаза оказывается размазанной по статусам
неравномерно: у двух фаз она в статусе не видна, у третьей видна. Плюс статусов становится десять
у задачи и двенадцать у группы.

### B. Явная колонка фазы — выбрано

Статус отвечает на вопрос «где в цикле попытки»: ждёт, захвачено, ждёт детей, завершено. Фаза —
на вопрос «какая работа». У раскрытия и у сборки одинаково есть «ждёт» и «работает», то есть фаза —
самостоятельное измерение состояния, и выражается оно своим явным признаком.

### C. Захватывать `AWAITING_CHILDREN` без незавершённых детей — отвергнуто

Захват сам проверяет `NOT EXISTS` по детям. Отвергнуто дважды: подзапрос по детям на каждом
кандидате в самом горячем запросе, и фаза снова выводится косвенно — из сочетания статуса
и состояния детей.

### Раскрытие вернуло ноль детей

#### Сразу `SUCCEEDED`, без сборки — отвергнуто

Экономит один захват, но появляется ветка, и у такой сущности результата не будет никогда.

#### Сборка с пустым потоком — выбрано

Правило «есть `expand` — есть и `collect`» ([0048](0048-collect-phase.md)) действует без
исключений. Потребитель получает свод и для «заказов за март не было».

## Решение

### Колонка

`phase` в `tc_task` и `tc_task_batch`: `text` с `CHECK (phase IN ('PROCESS', 'EXPAND', 'COLLECT'))`
([0036](0036-enumerated-columns.md)). Словарь тот же, что у вида попытки, и колонка вида попытки
в `tc_task_attempt` называется так же — `phase`. Слово уже занято тем же смыслом в конфигурации:
`taskcomm.task.types.<тип>.phases.expand` ([0060](0060-retry-and-lease-configuration.md)).

**Значение — вид текущей или следующей попытки сущности.** У терминальной сущности — вид
последней. У подзадачи колонки нет: её фаза всегда `PROCESS`.

**До первого захвата у задачи `phase` пуст** — по той же причине, по которой пуст `contract_shape`
([0026](0026-contract-shape-marking.md)): форма контракта фиксируется при первом захвате, и ещё
не начатая задача обрабатывается по актуальному контракту. Обе колонки проставляются вместе. Это
не косвенный признак: пустая форма контракта и пустая фаза означают одно и то же, явно названное
состояние «ещё не захватывалась». У группы фаза известна при рождении — `EXPAND`: её порождает
`BatchTaskProcessor`.

### Переходы

| Событие | `status` | `phase` |
|---|---|---|
| Постановка задачи | `PENDING` | пусто |
| Рождение группы | `AWAITING_PARENT` ([0068](0068-expansion-children-statuses.md)) | `EXPAND` |
| Первый захват задачи | `RUNNING` | `PROCESS` у `FLAT`, `EXPAND` у `UNIT` и `BATCH` |
| Захват | `RUNNING` | без изменений; вид попытки = `phase` |
| Неуспех с повтором, любая фаза | `PENDING` | без изменений |
| Раскрытие успешно, дети есть | `AWAITING_CHILDREN` | `COLLECT` |
| Раскрытие успешно, детей нет | `PENDING` | `COLLECT` |
| Незавершённых детей не осталось | `PENDING` | `COLLECT` |
| Сборка успешна | терминальный по агрегату детей | `COLLECT` |
| Сборка неуспешна, повторов не осталось | `FAILED` | `COLLECT` |
| Обработка плоской задачи завершена | терминальный по исходу | `PROCESS` |

В `AWAITING_CHILDREN` фаза уже `COLLECT`: следующая попытка у родителя — сборка, и значение
колонки остаётся верным своему определению.

**Переход «незавершённых детей не осталось»** делает тот, кто это обнаружил: воркер, закрывший
последнего ребёнка, — проверкой `EXISTS` по своей ссылке `parent_attempt_id`
([0047](0047-children-belong-to-attempt.md)), — либо подстраховочный поллер. Переход условен
по текущему статусу `AWAITING_CHILDREN` и потому идемпотентен. `next_attempt_at = now()`,
`claim_order_at` пересчитывается ([0063](0063-claim-ordering-and-pollers.md)).

**Терминальный статус ставит только сборка.** Раньше родителя закрывал воркер последнего ребёнка;
теперь он лишь отдаёт родителя в захват. После успешной сборки статус определяется агрегатом детей
по прежним правилам ([0023](0023-parent-statuses.md), [0024](0024-skipped-outcome.md)); неуспешная
сборка без оставшихся повторов — `FAILED` с причиной «сборка неуспешна», даже при полностью
успешных детях ([0048](0048-collect-phase.md)).

**Пропуск на раскрытии сборку не запускает.** Раскрытие, завершившееся исходом `SKIPPED`
([0024](0024-skipped-outcome.md)), — не успех: сущность становится `SKIPPED`, а её дети, если
процессор успел их отдать, — `ABANDONED` ([0068](0068-expansion-children-statuses.md)). Сборка
запускается после каждого **успешного** раскрытия, включая раскрытие с нулём детей.

### Перезапуск

По [0049](0049-restart-semantics.md):

- перезапуск **ребёнка** возвращает родителя в `AWAITING_CHILDREN`; фаза остаётся `COLLECT`;
- перезапуск **группы или задачи** — новая попытка раскрытия: `PENDING`, фаза `EXPAND`.

## Последствия

- **Воркер ничего не вычисляет**: вид открываемой попытки — значение `phase`. Неудачное раскрытие
  и неудачная сборка, ждущие повтора, различимы в `psql` и в REST без чтения таблицы попыток.
- **`RUNNING` остаётся одним статусом на три фазы**: «захвачено и работает над фазой `phase`».
  Интерфейс, показывающий только статус, обязан показывать и фазу — иначе сборка выглядит как
  раскрытие.
- **Пофазные настройки ([0061](0061-processor-configuration-annotations.md)) берутся по этой
  колонке** — тем же значением, которым назван ключ в `yaml`.
- **Колонка на `tc_task` и `tc_task_batch`, но не на `tc_task_unit`.** Миллионная таблица
  не расширяется.
- **Состояние родителя теперь двумерно**, и правило из [0068](0068-expansion-children-statuses.md)
  надо читать точнее. `phase` — не факт вроде `cancel_requested_at`, совместимый с любым статусом,
  а второе измерение, определённое при любом статусе. Новое состояние выражается статусом, если
  исключает другие статусы; колонкой-фактом — если совместимо с любым; отдельной колонкой-измерением —
  если отвечает на другой вопрос, чем статус.
- **Закрытие родителя перестаёт быть делом воркера последнего ребёнка.** Ответ «чем кончилась
  задача» всегда появляется через ещё один захват — на такт поллера позже, чем раньше.
- **Пустая сборка — лишний захват** у каждого раскрытия с нулём детей. Цена правила без исключений.
- **Отмена родителя в `AWAITING_CHILDREN` здесь не решается**: запускать ли сборку у отменённой
  задачи, определяется вместе с механизмом отмены детей.
