# 0030. Один частичный индекс по активным статусам

- **Дата:** 2026-08-27
- **Статус:** принято
- **Изменено:** [0046](0046-lease-in-attempt.md) — этот индекс обслуживает только первую ветку
  запроса захвата («свежие»). Вторая ветка — переподхват по истёкшей аренде — идёт от строк
  попыток и ведётся своим частичным индексом по `locked_until`.
- **Изменено:** [0063](0063-claim-ordering-and-pollers.md) — «один частичный индекс» стало **три**:
  под каждую форму захвата свой, и держатся они все, потому что форма выбирается конфигурацией,
  а индексы создаются миграцией. Принцип «терминальные строки в индекс не попадают» в силе
  у всех трёх.

## Контекст

Партиционирование не даёт отсечения для запроса захвата: он фильтрует по `status`
и `next_attempt_at`, ключа партиционирования в нём нет ([0020](0020-partitioning.md)). Значит
планировщик пойдёт по всем партициям, и без частичных индексов это будет последовательное
сканирование.

Запросов, работающих по активным строкам, два:

- **захват** — `PENDING` с наступившим `next_attempt_at` и `RUNNING` с истёкшей арендой
  ([0006](0006-lease-based-claiming.md));
- **подстраховочный поллер** — родители в `AWAITING_CHILDREN` без незавершённых детей
  ([0023](0023-parent-statuses.md)).

## Рассмотренные варианты

### A. Один частичный индекс на все активные статусы — выбрано

```sql
CREATE INDEX ... ON tc_task_unit (status, next_attempt_at)
 WHERE status IN ('PENDING', 'RUNNING', 'AWAITING_CHILDREN');
```

### B. Два отдельных частичных индекса — отвергнуто

Под захват и под подстраховочный поллер по отдельности. Точнее по селективности.

Отвергнуто: удваивает стоимость записи, а пишем мы много — раскрытие вставляет подзадачи пачками,
и каждая смена статуса задевает индекс. При этом выигрыш второго порядка: главная экономия
не в различении активных статусов между собой, а в том, что терминальные строки в индекс
не попадают вовсе.

### C. Обычный индекс без частичности — отвергнуто

`(status, next_attempt_at)` целиком. По мере накопления истории терминальные строки составят
подавляющее большинство, и индекс будет в основном состоять из строк, которые никогда не нужны
ни одному из двух запросов.

## Решение

**Один частичный индекс на все активные статусы**, на каждой из партиционированных таблиц.

Индекс объявляется на партиционированной таблице целиком: PostgreSQL создаёт его на всех
существующих партициях и автоматически на всех будущих. Отдельно сопровождать его при создании
партиций стартеру не нужно.

## Последствия

- **Запросы обязаны формулировать условие так, чтобы планировщик мог применить частичный индекс:**
  условие запроса должно быть логическим подмножеством предиката индекса. `status = 'PENDING'`
  и `status IN ('PENDING', 'RUNNING')` подходят, `status <> 'SUCCEEDED'` — нет. Это неочевидно
  и легко ломается при рефакторинге SQL.
- **Добавление нового активного статуса требует пересоздания индекса на всех партициях** — то есть
  блокировок на живых таблицах. Это вторая, независимая причина держаться правила «восемь статусов —
  потолок» ([0023](0023-parent-statuses.md)): новое состояние дешевле выразить фактом-колонкой.
- Терминальные строки по статусу не индексируются вовсе. Значит **REST-выдача по завершённым
  задачам опирается на отсечение партиций** и должна нести диапазон дат, иначе запрос пойдёт
  по всей истории. Это ограничение на дизайн REST, а не деталь реализации.
- Индекс покрывает оба запроса ценой чуть худшей селективности для каждого. Если один из них
  окажется горячее ожидаемого, разделение на два индекса — обратимое изменение, не ломающее
  ничего, кроме плана.
