# 0111. Форма публичного API задач: интерфейсы сущностей, постановка, чтения

- **Дата:** 2026-10-24
- **Статус:** принято
- **Изменено:** [0119](0119-submit-of-unknown-type-rejected.md) — постановка по строке типа без
  процессора в реестре отвергается исключением.

## Контекст

Этап 2 заводит публичные типы задач. Принятые решения задают смысл — постановка в транзакции
потребителя ([0017](0017-task-creation-transaction.md), [0094](0094-creation-always-in-transaction.md)),
необязательное дело ([0056](0056-execution-ref.md)), отсрочка ([0050](0050-deferred-start.md)),
приоритет при создании ([0063](0063-claim-ordering-and-pollers.md)), чтение состава дела
([0110](0110-execution-composition-reads-in-subsystems.md)), — но не форму методов и типов.
Форма публичного API после выпуска не меняется без мажорной версии.

## Рассмотренные варианты

### Сущности

- **A. Интерфейсы `Task<T>`, `TaskBatch<B>`, `TaskUnit<U>` с внутренней реализацией — выбрано.**
  Новое поле — новый метод, без поломки совместимости. Необязательный указатель на создателя
  отдаётся как `Optional<Origin>` — возвращаемое значение, что правилу об `Optional` не противоречит.
- **B. `record`, как направления коммуникации — отвергнуто.** Любое новое поле меняет канонический
  конструктор, а им пользуется код потребителя хотя бы в тестах процессоров — ломающее изменение.

### Постановка

- **A. Значение-запрос с одним методом сервиса — отвергнуто.** Единообразно, но частый случай
  «тип и нагрузка» становится длиннее.
- **B. Перегрузки для частых случаев и значение опций для редких — выбрано.**
- **C. Перегрузка на каждое сочетание — отвергнуто.** Дело, отсрочка и приоритет по двум способам
  указать тип дают десятки методов, и каждый новый параметр удваивает их число.

### Чтения и результат

- По строке типа и по классу процессора — **оба**, как у постановки.
- Результат по классу процессора с выводом типа одним методом невозможен: тип результата стоит
  в трёх контрактах на разных позициях, и три перегрузки дают одинаковое стирание. Три метода
  с разными именами отвергнуты как лишние; выбрано **чтение по классу результата** с проверкой
  при вызове.

## Решение

- **`Task<T>`, `TaskBatch<B>`, `TaskUnit<U>` — интерфейсы** в `task.api`. Состав: идентификатор,
  `ExecutionRef`, тип задачи, нагрузка, приоритет, статус, описание статуса, время создания;
  у задачи — `Optional<Origin>`, у группы — идентификатор задачи, у подзадачи — идентификаторы
  задачи и группы (группы нет у задач без групп). **Статус — снимок на момент чтения.** Отмена,
  «не раньше», фаза и форма контракта в состав не входят и добавляются методами, когда понадобятся.
  Публичная фабрика для тестов процессоров потребителя — отдельным шагом.
- **Постановка — `submit`**, шесть перегрузок: по строке типа и по классу процессора, каждая
  в трёх формах — только нагрузка; с `ExecutionRef`; со значением опций `TaskSubmitOptions`
  (дело или новое дело, «не раньше» как `Instant`, приоритет). Новый параметр постановки —
  новое поле опций, а не новые перегрузки.
- **Форма по классу процессора** — `submit(Class<? extends TaskProcessor<T>>, T)`: компилятор
  сверяет тип нагрузки с дженериком процессора. Тип задачи берётся из реестра по классу;
  класса нет в реестре — исключение.
- **Постановка возвращает `Task<T>`** — только что созданную задачу в статусе `PENDING`.
- **Чтения состава дела** — `findInExecution(ExecutionRef, String)` → `List<Task<?>>`
  и `findInExecution(ExecutionRef, Class<? extends TaskProcessor<T>>)` → `List<Task<T>>`.
- **Результат задачи** — `result(Task<?>)` → `Optional<Object>` и `result(Task<?>, Class<RT>)` →
  `Optional<RT>`. Несовпадение класса с типом результата процессора — исключение при вызове.
  Текущий результат — по правилу [0058](0058-task-result-storage.md).
- **Отмена и перезапуск** в `TaskService` появляются на этапе REST — аддитивно.

## Последствия

- Потребитель пишет в частом случае `taskService.submit("order-sync", period)` или
  `taskService.submit(OrderSyncProcessor.class, period)`, в редком — с опциями.
- Добавить поле в сущность или параметр в постановку можно без мажорной версии.
- Сущности потребитель сам не собирает; до появления тестовой фабрики тесты процессоров пишутся
  на заглушках интерфейсов.
- Проверка типа результата и класса процессора — при вызове, а не при компиляции; это цена одного
  имени метода вместо трёх.
