# 0066. Имена аннотаций настроек процессора

- **Дата:** 2026-10-07
- **Статус:** принято

## Контекст

[0061](0061-processor-configuration-annotations.md) разрешил задавать настройки процессора
аннотацией на классе и на методе, но имени аннотации не дал. Без имени её не написать ни в коде,
ни в документации: первый же пример в статье о порядке разрешения настроек пришлось снабдить
оговоркой «имя условное».

Ограничения, которые нельзя обойти:

- **Аннотация — публичный API навсегда** ([0061](0061-processor-configuration-annotations.md)):
  переименование после первого релиза — мажорная версия. Имя выбирается один раз.
- **Общего кода у подсистем нет** ([0010](0010-separate-engines.md)). Общий публичный тип в `api`
  одной из подсистем, которым пользуется другая, — это и есть общий код.
- **Правило именования** ([0003](0003-domain-naming.md)): имя проверяется на коллизии с `java.lang`,
  `java.util.concurrent` и `org.springframework.*` до попадания в публичный API.
- **Набор настроек у подсистем разный.** У задач — фазы, приоритет, аренда, повторы. У коммуникаций
  фаз нет, зато есть ограничение скорости, отказные статусы и список исключений размыкателя
  ([0065](0065-communication-circuit-breaker.md)).

## Рассмотренные варианты

### Сколько аннотаций

#### A. Одна общая, `@ProcessorSettings` — отвергнуто

Короче и симметричнее. Отвергнуто дважды. Это общий тип двух подсистем, то есть то, что запрещает
[0010](0010-separate-engines.md). И половина её атрибутов была бы бессмысленна для каждого
конкретного процессора: приоритет у коммуникации, список исключений размыкателя у задачи. Ошибку
«задал не тот атрибут» компилятор не поймал бы.

#### B. По аннотации на подсистему — выбрано

Каждая лежит в `api` своей подсистемы и несёт только свои атрибуты. Подсистемы меняются
независимо, как и положено.

### Имя

#### C. `@TaskSettings` / `@CommunicationSettings` — отвергнуто

Коротко, но «task» в Spring — это задача пула потоков: `spring.task.execution.*`,
`spring.task.scheduling.*`, `TaskExecutor`, `TaskScheduler`. Читатель потребителя, увидевший
`@TaskSettings` рядом с Spring-конфигурацией, прочтёт его как настройку пула. Вдобавок имя
не говорит, на что аннотация вешается.

#### D. `@TaskProcessorConfig` / `@CommunicationProcessorConfig` — отвергнуто

Суффикс `Config` в Spring-приложении означает класс `@Configuration`. Аннотация с таким именем
на процессоре читается как «это конфигурационный класс».

#### E. `@TaskProcessorSettings` / `@CommunicationProcessorSettings` — выбрано

Имя = тип, который аннотация настраивает, плюс `Settings`. Сразу видно, на что она вешается и
к какой подсистеме относится. Слово `Settings` не занято ни стереотипом Spring, ни суффиксом
конфигурационных классов.

## Решение

Две аннотации:

| Аннотация | Пакет | Вешается на |
|---|---|---|
| `@TaskProcessorSettings` | `xyz.avasilev.taskcomm.task.api` | класс или метод любого из трёх наследников `TaskProcessor` |
| `@CommunicationProcessorSettings` | `xyz.avasilev.taskcomm.communication.api` | класс или метод наследника `CommunicationProcessor` |

Смысл и порядок разрешения — по [0061](0061-processor-configuration-annotations.md) без изменений:
любое значение из `yaml` сильнее любой аннотации, метод перекрывает класс.

**Состав атрибутов здесь не решается.** Он определяется при заведении типов на этапе публичного API
и следует за деревом настроек каждой подсистемы ([0060](0060-retry-and-lease-configuration.md),
[0063](0063-claim-ordering-and-pollers.md), [0065](0065-communication-circuit-breaker.md)).

## Последствия

- **Имена длинные.** `@CommunicationProcessorSettings` — 31 символ. Это цена однозначности, и она
  платится один раз на процессор.
- **Две аннотации развиваются раздельно.** Атрибут, нужный обеим подсистемам, заводится в обеих
  отдельно, и синхронизировать их приходится руками — так же, как остальной код подсистем
  ([0010](0010-separate-engines.md)).
- **Проверка коллизий по [0003](0003-domain-naming.md)** сделана по известным именам; окончательно
  она выполняется при заведении типов, когда имя впервые попадает в код.
- Применение не к тому типу ловится не компилятором, а стартером: `@Target` не умеет ограничить
  аннотацию наследниками конкретного интерфейса. `@TaskProcessorSettings` на процессоре
  коммуникаций — падение при старте с внятным сообщением.
