# 0022. Данные батча материализуются в подзадачу

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

Батч существует ради одного: сходить во внешнюю систему один раз за данными для всей группы
подзадач, а не дёргать её на каждый объект ([0007](0007-processor-contracts.md)). Сбор происходит
в `expandBatch`. Обработка — в `process`. Между ними данные должны где-то оказаться.

Вопрос возник из ошибочной формулировки в [0009](0009-retry-and-progress.md), где было записано,
что данные батча не хранятся и при повторе собираются заново. Это неверно: ни при каком варианте
размещения повтор одной подзадачи не требует повторного сбора.

## Рассмотренные варианты

### A. Материализуются в нагрузку каждой подзадачи — выбрано

`expandBatch` вкладывает всё необходимое в `U` каждой порождённой подзадачи. `process(unit)`
самодостаточен.

### B. Хранятся один раз на батче, `process(unit, batch)` — отвергнуто

Нет дублирования, батч остаётся содержательной сущностью на всё время выполнения.

Отвергнуто: контракты процессоров расходятся сильнее (у одного `process(unit)`, у другого
`process(unit, batch)`), а выигрыш нужен не всем — только тем, у кого общие данные объёмные.

### C. Потребитель выбирает — отвергнуто

Расширяет публичный API ради случая, который решается за его пределами.

## Решение

Данные **материализуются в нагрузку подзадачи**. `process(unit)` одинаков во всех контрактах,
подзадача самодостаточна.

Явный не-goal: **стартер не предоставляет хранилища для общих данных батча.** Потребителю, которому
дублирование дорого — например, если на всю группу приходится один объёмный прайс-лист, — ничто
не мешает завести собственную таблицу вида `(batch_id, batch_data)`: заполнить её при раскрытии
батча и читать при обработке подзадачи, хоть первичной, хоть повторной.

## Последствия

- **`TaskUnit` обязан нести `taskId` и `batchId` в публичном API.** Без них сценарий с собственным
  хранилищем потребителя невозможен: не по чему обращаться.
- Подзадача самодостаточна: её повтор не требует ни батча, ни задачи. Это подтверждает уже принятое
  «повторяются только упавшие `TaskUnit`» ([0009](0009-retry-and-progress.md)) и делает его дешёвым.
- Семантика параметров типа уточняется: **`B` — это параметры группы** (какие объекты в неё входят,
  к какому контрагенту относятся), а не собранные из внешней системы данные. Собранное живёт в `U`.
- Дублирование данных по числу подзадач — принятая цена. Для типичного случая, где на подзадачу
  приходятся её собственные данные, дублирования нет вовсе; оно возникает только когда часть
  нагрузки общая для группы.
- После раскрытия батч остаётся единицей группировки и прогресса, но собственных данных
  для обработки не несёт.
- **Время жизни собственного хранилища потребителя не связано с нашей ретенцией.** Партиционирование
  ([0020](0020-partitioning.md)) удалит наши строки по расписанию, а его таблица останется
  и продолжит расти. Об этом надо предупредить в документации для потребителей.

## Связанные решения

- [0009](0009-retry-and-progress.md) — исправляет ошибочную формулировку о пересборе данных батча.
- [0007](0007-processor-contracts.md) — три контракта, из которых только `BatchTaskProcessor`
  имеет `expandBatch`.
- [0020](0020-partitioning.md) — ретенция, которая не распространяется на данные потребителя.
