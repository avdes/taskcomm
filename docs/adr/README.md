# Журнал архитектурных решений (ADR)

Каждый файл — одно решение: что решили, какие были варианты, почему выбрали этот и чем за это
платим. Файлы отвечают на вопрос **«почему оно так»**, а не «как это работает».

## Правила ведения

- Один файл — одно решение. Номер присваивается по порядку и никогда не переиспользуется.
- **Принятый ADR не редактируется по существу.** Передумали — пишем новый и помечаем старый как
  заменённый, со ссылкой. История решений так же ценна, как само решение: она не даёт вернуться
  к отвергнутому варианту по кругу.
- Единственная допустимая правка содержания принятого ADR — **добавление строки в шапку**
  (оформление шапки — см. ниже). Без этого механизм замены не работал бы вовсе: читатель
  старого файла не узнал бы, что его отменили.
  - `**Изменено:**` — новое решение меняет часть старого, а не всё целиком. Со ссылкой.
  - `**Поправка:**` — в тексте ADR обнаружена фактическая ошибка, не затрагивающая само решение.
    Тело не переписывается: ошибочная формулировка остаётся, рядом появляется верная. Переписать
    молча значило бы скрыть, что документ какое-то время вводил в заблуждение.
- **Оформление шапки править можно, не меняя слов**: разбить склеенную строку, вернуть недостающую
  метку `**Изменено:**`, расставить строки по порядку номеров решений. Шапка — оглавление
  изменений, а не текст решения; разбивка и порядок историю не переписывают. Слова строк шапки
  и тело ADR — нельзя.
- Статус: `принято` | `заменено ADR-NNNN` | `отложено`.
- Раздел «Рассмотренные варианты» обязателен и должен содержать отвергнутые. ADR без них
  бесполезен — именно они объясняют, почему нельзя «просто сделать проще».
- Раздел «Последствия» тоже обязателен, включая неприятные. Решение без цены — это не решение.

## Шаблон

```markdown
# NNNN. Заголовок решения

- **Дата:** ГГГГ-ММ-ДД
- **Статус:** принято

## Контекст
Что заставило принимать решение. Ограничения, которые нельзя обойти.

## Рассмотренные варианты
### A. Название
Суть. Плюсы. Минусы.
### B. Название
...

## Решение
Что выбрали и почему именно это.

## Последствия
Что теперь обязаны делать, что стало нельзя, чем платим.

## Связанные решения
[NNNN](NNNN-slug.md) — как связаны.
```

- [0064](0064-entity-origin-links.md) — поиск по нагрузке **коммуникаций** не сделан: белый список
  полей объявлен только для задач. Сценарий пока обходится фильтром по `source` / `destination`
  внутри дела.

Размыкатель, стоявший здесь с [0011](0011-communication-model.md), **закрыт** решением
[0065](0065-communication-circuit-breaker.md). Отложенными внутри него остались синхронизация
состояния между экземплярами и ручное управление через REST — они появятся вместе.

Таблица связей сущностей, стоявшая здесь с [0038](0038-execution-aggregate.md), **закрыта**
решением [0064](0064-entity-origin-links.md), и вместе с ней — доступ процессора к данным
породившей его коммуникации. Closure table не понадобился: ни один из сценариев не оказался
обходом графа, а `Execution` и есть замыкание.

Хранение результатов обработки, стоявшее здесь с [0044](0044-attempt-log.md)
и [0048](0048-collect-phase.md), **закрыто целиком**. Предсказание 0044 о том, что механизм
у подсистем окажется разным, подтвердилось: у коммуникаций обмен разложен по колонкам попытки
([0055](0055-communication-exchange-storage.md)), у задач результат живёт в своей таблице
([0058](0058-task-result-storage.md)), и одно из другого не выводится.

Вопрос «что означает „здоров“ для движка», стоявший здесь с 0015, закрыт
решением [0051](0051-engine-health.md).
