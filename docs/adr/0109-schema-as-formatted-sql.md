# 0109. Схема — один файл Liquibase formatted SQL на версию

- **Дата:** 2026-10-24
- **Статус:** принято

## Контекст

[0013](0013-database-schema.md) обязал стартер везти схему двумя путями: Liquibase-changelog
для потребителей на Liquibase и голый DDL для остальных. Голый DDL нужен и самому стартеру:
`taskcomm.schema.initialize` работает через `DataSourceScriptDatabaseInitializer`, а тот
выполняет только SQL-скрипты; зависимости на Liquibase у стартера нет
([0092](0092-jackson-3-liquibase-compatibility.md)).

Правило в schema.md требовало в changelog комментарии через `remarks` у колонки — то есть
структурный `createTable`. Тогда каждое определение колонки и каждый комментарий (двенадцать
таблиц, порядка ста семидесяти колонок) пишутся дважды, в двух форматах, и расходятся при первой
же правке одного файла без другого. Структурный changelog при этом ничего не даёт: партиционирование
и частичные индексы Liquibase всё равно задаёт сырым SQL, а база у стартера одна — PostgreSQL.

## Рассмотренные варианты

### A. Один файл formatted SQL — выбрано

Liquibase читает `.sql` с разметкой changeSet'ов в SQL-комментариях
(`--liquibase formatted sql`, `--changeset автор:id`). Для Liquibase это changelog, для
`initialize`, Flyway и `psql` — обычный SQL: разметка — просто комментарии. Источник один,
расходиться нечему. Формат поддерживают и Liquibase 4, и Liquibase 5.

### B. XML с `remarks` и отдельный `.sql`, сверка тестом — отвергнуто

Как требовало прежнее правило. Тест, накатывающий оба пути в разные схемы и сравнивающий каталог,
ловил бы расхождение, но текста вдвое больше, и каждая правка — в двух местах.

### C. XML подключает `.sql` через `<sqlFile>` — отвергнуто

Источник тоже один, но появляется лишний слой: changeSet в XML, тело — в другом файле.
Formatted SQL даёт то же без посредника.

## Решение

- Схема каждой версии — **один файл Liquibase formatted SQL** в
  `taskcomm-autoconfigure/src/main/resources/db/changelog/taskcomm/`. `master.xml` в том же
  каталоге подключает файлы версий по порядку; потребитель на Liquibase по-прежнему включает
  только его.
- **Комментарии к таблицам и колонкам — `COMMENT ON` в том же файле**, а не `remarks`. Требование
  «каждая колонка с комментарием на русском» не меняется.
- Тот же файл — голый DDL для потребителей на других инструментах и скрипт для
  `taskcomm.schema.initialize`.
- Операторы создания — **`IF NOT EXISTS`**: `initialize: always` на постоянной локальной базе
  выполняет скрипт при каждом старте, и повторный запуск не должен падать.

## Последствия

- **Выпущенный файл неприкосновенен целиком**, а не только его changeSet'ы: его текст и есть
  контрольная сумма у потребителей на Liquibase. Новая версия схемы — новый файл.
- В текстах комментариев не ставится `;`: разбиение на операторы у Liquibase и у
  `DataSourceScriptDatabaseInitializer` идёт по точке с запятой.
- Отката (`rollback`) в changeSet'ах нет — как не было бы и у структурного changelog
  с партиционированием на сыром SQL; миграции только аддитивные ([0013](0013-database-schema.md)).
