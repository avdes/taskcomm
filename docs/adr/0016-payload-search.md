# 0016. Ограничение поиска по нагрузке: белый список полей

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

Поиск по содержимому нагрузки входит в состав REST API ([0014](0014-rest-api.md)), а нагрузка
хранится в `jsonb` ([0012](0012-payload-storage.md)), то есть технически искать по ней можно как
угодно. Ограничение нужно по одной причине: запрос по неиндексированному пути кладёт
последовательным сканированием таблицу на миллион строк, и сделать это может любой, у кого есть
доступ к API.

Отдельное требование от сценария использования: нужно уметь найти всё, что делалось с конкретной
бизнес-сущностью, **не зная типа задачи**. Изменение заказа и отмена заказа — разные типы, но
искать по номеру заказа хочется одним запросом.

## Рассмотренные варианты

### Чем ограничить

#### A. Ничем, произвольный JSON-запрос — отвергнуто

Максимум гибкости и прямая возможность положить БД потребителя одним HTTP-запросом.

#### B. GIN на всю колонку нагрузки + `statement_timeout` — отвергнуто

Гибко и без объявлений со стороны потребителя. Отвергнуто: GIN на всю нагрузку — толстый индекс,
заметно замедляющий вставку, а вставки у нас массовые — раскрытие задачи порождает подзадачи
пачками ([0008](0008-expansion-emitter.md)).

#### C. Белый список полей — выбрано

Процессор объявляет, по каким путям в нагрузке разрешён поиск. Поиск по необъявленному полю
отвергается сразу, до обращения к БД.

### Как определяется, в каких типах задач искать

#### D. `taskType` обязателен в каждом запросе — отвергнуто

Первоначальное предложение: раз у разных типов нагрузка разной формы, требовать явного указания
типа, иначе не применится ни один индекс.

**Отвергнуто:** ломает основной сценарий. Пользователь ищет по номеру заказа и не обязан знать,
какими типами задач этот заказ обрабатывался.

#### E. Тип выводится из имени поля — выбрано

Стартер держит реестр «имя поля → типы задач, объявившие это поле». Запрос по `order_id`
разворачивается в поиск по всем типам, у которых `order_id` есть в белом списке. `taskType`
остаётся **необязательным фильтром** для сужения.

## Решение

Ограничение — **белый список полей**, объявляемый процессором. Тип задачи в запросе
**не обязателен**: он выводится из реестра по имени поля.

Объявление:

```java
public record SearchableField(String name, String jsonPath, FieldType type) {
    public static SearchableField string(String name, String jsonPath) { ... }
    public static SearchableField number(String name, String jsonPath) { ... }
}
```

```java
default List<SearchableField> searchableTaskFields() { return List.of(); }
default List<SearchableField> searchableUnitFields() { return List.of(); }
```

Уровни объявляются раздельно, потому что нагрузки уровней — разных типов
([0003](0003-domain-naming.md)): в задаче лежат параметры операции, в подзадаче — бизнес-объект.
Поиск по задачам и поиск по подзадачам — разные эндпоинты.

Пример у потребителя:

```java
@Override
public List<SearchableField> searchableUnitFields() {
    return List.of(
            SearchableField.string("order_id", "$.orderId"),
            SearchableField.string("customer_inn", "$.customer.inn"));
}
```

Запрос:

```
GET /api/taskcomm/units?payload.order_id=A-1024
```

разворачивается в

```sql
WHERE (task_type = 'order-change' AND payload->>'orderId'      = :v)
   OR (task_type = 'order-cancel' AND payload#>>'{order,id}'   = :v)
```

Каждая ветка попадает в свой частичный индекс; PostgreSQL объединяет их через BitmapOr.

## Последствия

- **Одно имя поля — один `FieldType` во всём реестре.** Разные `jsonPath` у разных типов допустимы
  и нормальны: путь — деталь хранения. А разный тип значения означал бы, что один и тот же запрос
  значит разное в разных типах, и объяснить это пользователю нельзя. Конфликт — **падение при
  старте приложения**, как и дубль `taskType` ([0007](0007-processor-contracts.md)).
- Несколько полей в запросе сужают множество типов: ищем только в тех, кто объявил **все**
  указанные поля. Тип, не объявивший одно из них, удовлетворить условию не может.
- Поле не объявлено ни одним типом — `400` со списком известных имён, а не медленный запрос
  и не пустой результат.
- Чем больше типов объявили поле, тем шире `OR` в запросе. Это прямая цена отказа от обязательного
  `taskType`, и она признана приемлемой: каждая ветка индексирована, а сузить поиск можно, передав
  `taskType` как необязательный фильтр.
- Имена полей живут в **общем** пространстве имён поиска, а не внутри типа задачи. Это делает
  выбор имени в белом списке решением, затрагивающим весь проект потребителя, а не один процессор.
- Индексы под объявленные поля стартер **в проде сам не создаёт** — это блокировки на живой
  таблице в момент старта. При старте он проверяет их наличие и при отсутствии пишет **WARN
  с готовым DDL**, который потребитель применит своей миграцией. Уровнем мягче, чем проверка схемы
  ([0013](0013-database-schema.md)): без индекса поиск работает, просто медленно, и падать нельзя.
- Индексы частичные, по типу задачи — так они остаются компактными при двух десятках типов:
  `CREATE INDEX ... ON tc_task_unit ((payload->>'orderId')) WHERE task_type = 'order-change'`.
- SQL собирается из объявленных `jsonPath` и `FieldType`. Пользовательский ввод в SQL
  не конкатенируется никогда.
- Белый список — часть публичного контракта процессора у потребителя. Убрать оттуда поле,
  по которому уже ищут, — ломающее изменение, но его собственное: список объявляет он сам.
