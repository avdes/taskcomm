# 0002. Регистрация автоконфигураций и префикс свойств

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

Артефакт называется `taskcomm-spring-boot-starter`, и это имя — обещание: потребитель добавляет
одну зависимость и получает работающую функциональность, без ручных шагов в своём коде. Нужно
выбрать механизм, которым классы конфигурации из [0001](0001-module-layout.md) попадают в контекст
чужого приложения.

Связанный, но отдельный вопрос — как называются свойства в `application.yml` потребителя. Он решается
здесь же, потому что вместе с механизмом активации образует то, что потребитель видит первым.

## Рассмотренные варианты

### Механизм активации

#### A. `AutoConfiguration.imports` — выбран

Файл `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, по одному
полному имени класса на строку; классы помечаются `@AutoConfiguration`. Порядок задаётся через
`@AutoConfiguration(after = ..., before = ...)`.

Единственный штатный механизм в Spring Boot 3.

#### B. `META-INF/spring.factories`, ключ `EnableAutoConfiguration`

Механизм Spring Boot 2. **Удалён в Spring Boot 3.0** — рассматривать нечего. Сам файл
`spring.factories` при этом жив и остаётся законным для других типов расширений
(`EnvironmentPostProcessor`, `FailureAnalyzer`, `ApplicationListener`), поэтому его присутствие
в проекте само по себе не является ошибкой.

#### C. Собственная аннотация `@EnableTaskcomm` + `@Import`

Потребитель явно ставит аннотацию на свою конфигурацию.

Плюс: полная явность, ничего не включается само.

Минус: это уже не стартер. Артефакт с именем `*-spring-boot-starter`, требующий ручного шага,
нарушает ожидание, которое сам же и создаёт.

Отвергнут **как основной механизм**, но не запрещён как дополнение: если позже понадобится режим
«всё выключено по умолчанию, включается явно», такую аннотацию можно добавить поверх A.

#### D. `ImportSelector` / `ImportBeanDefinitionRegistrar`

Программная регистрация определений бинов. Это инструмент для динамики, а не механизм активации,
и для нашей задачи он не нужен: процессоры потребителя Spring находит сам, а стартер собирает их
инъекцией `List<TaskProcessor<?>>` — см. [0007](0007-processor-contracts.md).

### Префикс свойств

#### A. `xyz.avasilev.taskcomm.*`

Reverse-domain, как у Java-пакетов. Коллизия исключена полностью.

#### B. `taskcomm.*` — выбран

Так устроены свойства всех известных сторонних стартеров: `springdoc.*`, `resilience4j.*`,
`liquibase.*`, и всех собственных механизмов Spring: `spring.datasource`, `management.endpoints`.
Reverse-domain — конвенция для имён пакетов Java, а не для конфигурационных свойств.

## Решение

Активация — вариант **A**, файл `AutoConfiguration.imports`. По сути выбора не было: это
единственный поддерживаемый механизм в Spring Boot 3, а обещание, заложенное в имени артефакта,
исключает вариант C.

Префикс свойств — **`taskcomm.*`**. Риск коллизии в пространстве имён верхнего уровня признан
пренебрежимо малым и обменян на читаемость `application.yml` у потребителя.

## Последствия

Главное последствие автоматической активации: **потребитель никогда не давал явного согласия**.
Он добавил зависимость — и получил бины, планировщики и HTTP-эндпоинты, о которых мог не знать.
Отсюда набор обязательств, каждое из которых существует именно потому, что выбран вариант A:

- **Каждый бин объявляется явным `@Bean`-методом под `@ConditionalOnMissingBean`.** Не согласившись
  явно, потребитель обязан иметь возможность заменить любой наш бин своим.
- **Каждая подсистема выключается свойством** `@ConditionalOnProperty(prefix = "taskcomm.<подсистема>",
  name = "enabled", matchIfMissing = true)`. Выключение должно быть доступно без удаления
  зависимости.
- **`@ComponentScan` в автоконфигурациях запрещён**, как и стереотипные аннотации (`@Component`,
  `@Service`, `@Repository`) на внутренних классах. Сканирование подхватывает бины в порядке,
  который потребитель не контролирует и не может предсказать.
- **Глобальные механизмы Spring не включаются за потребителя**: `@EnableScheduling`, `@EnableAsync`,
  `@EnableTransactionManagement` меняют поведение всего приложения, а не нашей подсистемы. Нужен
  планировщик — создаём собственный бин.

Прочее:

- Подключён `spring-boot-configuration-processor`, чтобы свойства `taskcomm.*` автодополнялись
  в IDE потребителя.
- `spring.factories` не используется для автоконфигураций. Его появление в проекте допустимо
  только для `EnvironmentPostProcessor` и подобных расширений.
- Префикс `taskcomm.*` занят нами в глобальном пространстве имён свойств. Если когда-нибудь
  случится коллизия с другой библиотекой, переименование префикса будет ломающим изменением.
