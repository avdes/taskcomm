# 0012. Хранение нагрузки: `jsonb`, Jackson, `ResolvableType`

- **Дата:** 2026-08-27
- **Статус:** принято
- **Изменено:** [0055](0055-communication-exchange-storage.md) — у коммуникаций рядом с доменной
  формой появляются сырые тела запроса и ответа в `text` (двоичные форматы — base64), а сама
  колонка называется `request_payload`. Доменных форм две: `R` восстанавливается из дженерика
  процессора тем же способом, что `P`.

## Контекст

Полезная нагрузка — единственная часть модели, о которой стартер ничего не знает: это бизнес-объект
потребителя, параметр типа. Её нужно записать в БД и прочитать обратно, восстановив исходный
Java-тип.

Второй вопрос вытекает из первого: дженерики стираются, из `TaskUnit<U>` тип `U` в рантайме
не достать.

## Рассмотренные варианты

### Формат хранения

#### A. `jsonb` + Jackson — выбрано

Содержимое видно в БД, ищется обычным SQL, поддерживает GIN и функциональные индексы.
Jackson уже присутствует в любом Spring Boot приложении.

#### B. `bytea` + сериализатор потребителя — отвергнуто

Максимум гибкости, но в БД оказывается непрозрачный набор байт. Любой разбор инцидента становится
возможен только через приложение — а инциденты как раз и разбирают, когда приложение ведёт себя
не так, как ожидалось.

#### C. Java-сериализация — отвергнуто

Не рассматривалось всерьёз: хрупкость к изменениям классов и известные проблемы безопасности.

### Восстановление Java-типа

#### D. Из дженерика процессора — выбрано

`ResolvableType.forClass(UnitTaskProcessor.class, processor.getClass()).getGeneric(1)`.
Процессор для типа задачи уже найден, его конкретный класс известен — тип извлекается
из реализованного интерфейса. От потребителя не требуется ничего.

#### E. Явный метод `Class<U> unitType()` в контракте — отвергнуто

Всегда работает, но добавляет обязательный метод в публичный контракт ради того, что и так
выводится.

#### F. FQCN в колонке — отвергнуто

Не зависит от процессора, но ломается при рефакторинге у потребителя: переименовал класс
или перенёс в другой пакет — старые задачи перестали читаться.

## Решение

Нагрузка хранится в колонке **`jsonb`**, сериализация — **Jackson**. Java-тип восстанавливается
**из дженерика процессора** через `ResolvableType`. FQCN в БД не хранится.

## Последствия

- Выбор `jsonb` — предпосылка для поиска по содержимому нагрузки через REST
  ([0014](0014-rest-api.md)). С `bytea` этой возможности не было бы вовсе.
- Jackson становится фактически обязательной зависимостью подсистемы. В контексте Spring Boot это
  бесплатно, но формально это привязка.
- **Потребитель обязан реализовать интерфейс процессора конкретными типами.** Реализация
  с невыведенным параметром типа (raw type, дженерик, проброшенный дальше) не даст `ResolvableType`
  разрешить `U`. Это должно обнаруживаться **при старте приложения** с внятным сообщением,
  а не при первой попытке прочитать подзадачу.
- Переименование или перенос класса нагрузки у потребителя безопасны — имя класса нигде не хранится.
- А вот **переименование поля внутри класса нагрузки — нет**: в JSON лежат имена полей, и старые
  строки после такого переименования прочитаются с потерей этого поля. Для потребителя это
  неочевидно, и об этом стоит предупредить в документации: класс нагрузки эволюционирует
  по правилам совместимости формата, а не по правилам Java.
- Привязка к PostgreSQL усиливается: `jsonb` — не стандартный SQL
  ([0005](0005-persistence-spi.md)).
