# 0024. Статус `SKIPPED` и канал пропуска

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

Нужен исход, который не является ни успехом, ни ошибкой: работа не выполнялась, и это нормально.
Считать такое успехом нельзя — метрики пропускной способности начнут врать; считать ошибкой тем
более нельзя.

Источников у него два, и они разной природы:

- **Движок.** Отмена задачи переводит её батчи и подзадачи в `SKIPPED`; отмена батча — его
  подзадачи.
- **Процессор.** При раскрытии задачи или при выполнении плоской задачи выяснилось, что делать
  нечего.

Первый источник API не затрагивает. Второй требует канала, которым процессор об этом сообщит.

## Рассмотренные варианты (канал)

### A. Возврат `Outcome` (`Done` | `Skipped`) — отвергнуто

`expand` и `process` перестают быть `void` и возвращают запечатанный тип.

Отвергнуто по существу: **`Done` не несёт информации.** Успех уже выражен тем, что метод вернулся
без исключения, а завершённость раскрытия — полем `expanded_at`. Введение `Done` создаёт второй
канал для того же факта, а два канала для одного сигнала рано или поздно разойдутся. Вдобавок
общий путь облагается налогом: `return Outcome.done()` пришлось бы писать в каждом процессоре ради
случая, который у большинства не встретится никогда.

### B. Исключение `SkipException` — отвергнуто

Однозначно, немедленно, противоречивое состояние невозможно, а стектрейс показывает, где принято
решение.

Отвергнуто из-за чужого кода: потребители пишут `try { ... } catch (Exception e) { log.error(...); }`
вокруг своей логики. Такой `catch` **молча проглотит** маркер, и вместо `SKIPPED` получится
`SUCCEEDED` или `FAILED`. Библиотека не может полагаться на то, что этого не случится.

### C. Метод контекста `skip(reason)` — выбрано

Контекст выполнения уже существует — он введён в [0018](0018-cooperative-cancellation.md), чтобы
процессор мог проверить, не отменили ли его. Добавляется один метод в существующее место,
`void` сохраняется, общий путь не меняется.

## Решение

`expand` и `process` остаются **`void`**. Пропуск сообщается методом контекста `skip(reason)`.

Правила, снимающие неоднозначность:

- Пропуск засчитывается, **только если метод вернулся нормально**.
- **Исключение перебивает пропуск**: ошибка важнее.
- `reason` **обязателен**. Пропуск без объяснения выглядит в интерфейсе как баг, и первый же
  вопрос будет «а почему пропустили?».

Агрегат по детям:

- есть `SKIPPED`, остальные успешны — родитель `SUCCEEDED`;
- **все** дети `SKIPPED` — родитель `SKIPPED`;
- собственная отмена родителя перебивает агрегат ([0023](0023-parent-statuses.md)).

## Последствия

- Процессор, вызвавший `skip()` и продолживший работу с побочными эффектами, получит `SKIPPED`
  при фактически выполненной работе. Это его ошибка, и она должна быть описана в Javadoc метода
  явно — контракт допускает такое состояние, значит обязан о нём предупредить.
- `reason` хранится в БД и отдаётся через REST. Это не отладочная строка, а часть данных.
- **`SKIPPED` считается в метриках отдельно** и не смешивается с `SUCCEEDED`
  ([0015](0015-observability.md)) — иначе смысл введения статуса теряется.
- Не путать с уже принятым в [0008](0008-expansion-emitter.md): раскрытие, честно вернувшее ноль
  детей, — это `SUCCEEDED` («заказов за март не было»). `SKIPPED` — это явное «выполнять не надо».
  Разница в намерении процессора, а не в количестве порождённых детей.
- Пропуск на уровне подзадачи процессором не предусмотрен: там `SKIPPED` ставит только движок
  при отмене родителя. Если понадобится, добавление — аддитивное изменение контекста подзадачи.
- Перманентная ошибка «не повторяй» — **другая** нужда и сюда не относится. Ошибка выражается
  исключением, и специальный тип для неповторяемой ошибки можно добавить позже, ничего не ломая.
