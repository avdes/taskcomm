# 0106. Стартер не экспортирует BOM Spring Boot

- **Дата:** 2026-10-23
- **Статус:** принято

## Контекст

`taskcomm-spring-boot-starter` объявлял `api platform(libs.spring.boot.bom)`. В опубликованных
артефактах это выглядело так:

- **Gradle Module Metadata** содержала зависимость на платформу `spring-boot-dependencies`
  с `requires 4.1.1`. У Gradle-потребителя все ограничения BOM входят в разрешение версий
  и поднимают его зависимости до наших — не только Spring Boot, но и Jackson, Micrometer, драйвер
  PostgreSQL, Tomcat и всё остальное из BOM;
- **POM** содержал `<dependencyManagement>` с импортом BOM. Maven такой импорт из зависимостей
  не наследует, и Maven-потребителя это не задевало.

Вредит это Gradle-потребителю на более старой версии Spring Boot: опускать версии `requires`
не умеет, поднимать — умеет. Поднятие сторонних библиотек ради стартера — то навязывание
поведения, которое правила стартера в CLAUDE.md запрещают. Штатные стартеры Spring Boot свой BOM
в зависимости не экспортируют.

Отдельный BOM самого taskcomm [0001](0001-module-layout.md) уже отложил; здесь речь о чужом.

## Рассмотренные варианты

### A. Не экспортировать BOM, версии зависимостей — явные из каталога — выбрано

Потребитель получает только прямые зависимости стартера, каждую с минимальной версией, — обычное
поведение библиотеки. Минимум Spring Boot 4.1 приходит через `spring-boot-starter 4.1.1`
и согласуется с базовой линией [0088](0088-java-25-spring-boot-4.md).

### B. `enforcedPlatform` вместо `platform` — отвергнуто

Gradle тогда ещё и опускал бы версии у потребителя на более новом Spring Boot.

### C. Оставить и описать в документации — отвергнуто

Правило «не навязывать» нарушалось бы сознательно и без выгоды: управление версиями внутри сборки
стартера не требует экспорта.

## Решение

- **Ни один модуль не публикует платформу.** В `taskcomm-spring-boot-starter` нет
  `api platform(...)`; зависимости стартера объявляются с явными версиями из каталога версий.
  В `taskcomm-autoconfigure` `compileOnly platform(...)` и `testImplementation platform(...)`
  остаются — они не публикуются.
- **Проверка — задача сборки `verifyNoExportedPlatform`** у каждого модуля, в составе `check`.
  Она читает сгенерированные `.module` и `.pom`, а не `build.gradle`, и падает, если в метаданных
  есть зависимость категории `platform` или `enforced-platform` или в POM есть
  `<dependencyManagement>`. Платформа может прийти и не из явной строки, поэтому проверяется
  результат.

## Последствия

- **Подключение стартера не поднимает у Gradle-потребителя библиотеки, не нужные стартеру.**
- **Каждая новая транзитивная зависимость стартера — с явной версией из каталога**, иначе
  опубликованный POM останется без версии и Maven-потребитель не соберётся.
- **Проверка ловит возврат платформы** — проверено: с возвращённой строкой задача падает
  и называет `spring-boot-dependencies` в обоих вариантах публикации.
- Минимальные версии прямых зависимостей по-прежнему поднимаются у потребителя на более старом
  Spring Boot — это неизбежно для любой библиотеки и совпадает с базовой линией.
