# 0084. Приоритет задаётся только на уровне типа

- **Дата:** 2026-10-20
- **Статус:** принято

## Контекст

[0061](0061-processor-configuration-annotations.md) разрешил аннотации настроек задавать всё, что
`yaml` задаёт на уровне типа, — включая приоритет по умолчанию
([0063](0063-claim-ordering-and-pollers.md)), — **и на классе, и на методе**, с перекрытием
класса методом. В `yaml` у задач есть уровень фазы `phases.<фаза>`, повторяющий набор типа.

Приоритет при этом — свойство **сущности**, а не попытки: задаётся при создании, наследуется
детьми, ручным перезапуском не меняется. У задачи нет момента, когда приоритет «для `collect`»
или «для `expand`» на что-то повлиял бы: сборку захватывают по той же строке задачи с её
`priority`, подзадачи берут приоритет группы, а не настроек `process`. У коммуникаций то же —
приоритет на методе `process` или на методе ключей дедупликации ничего не значит.

Значит, `@TaskProcessorSettings(priority = 10)` на методе и `phases.collect.priority` в `yaml`
**молча ничего не делают** — ровно та ловушка, от которой 0061 защищался правилом «`yaml`
сильнее аннотации»: настройку поменяли, она не применилась, никто не узнал.

## Рассмотренные варианты

### A. Падение при старте — выбрано

### B. Предупреждение при старте, значение игнорируется — отвергнуто

Настройка, которая молча не действует, остаётся; отличие — одна строка лога.

### C. Придать приоритету на фазе смысл — отвергнуто

Например, приоритет на `expand` задаёт приоритет детей, на `collect` — захват сборки. Новое
поведение без запроса на него, и оно ломает простое правило «дети наследуют приоритет родителя».

## Решение

- **Приоритет по умолчанию задаётся только в аннотации на классе процессора и в `yaml`
  на уровне типа** — `types.<тип>.priority` у задач, `systems.<имя>.priority` у коммуникаций.
- **Приоритет в аннотации на методе или в `yaml` на уровне фазы — падение при старте**, с именем
  процессора и метода либо путём свойства. Аннотация одна на класс и метод
  ([0066](0066-processor-settings-annotation-names.md)), поэтому компилятор этого не поймает —
  ловит старт.
- Остальные настройки аннотации на методе — аренда, предел обработки, повторы — действуют, как
  решил 0061: они про попытку, и у каждой фазы они свои.

## Последствия

- **Настройки, которая молча не действует, не остаётся**: приоритет либо применяется, либо
  приложение не стартует.
- **Аннотация на методе и аннотация на классе теперь различаются по составу**, хотя тип один.
  Javadoc атрибута `priority` обязан сказать, что на методе он запрещён.
- Печать итоговых настроек при старте ([0061](0061-processor-configuration-annotations.md))
  показывает приоритет по типу, без разбивки по фазам.
