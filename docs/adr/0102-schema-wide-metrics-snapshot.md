# 0102. Метрики на всю схему считает один экземпляр в снимок; просрочка вместо разбивки по приоритету

- **Дата:** 2026-10-21
- **Статус:** принято

## Контекст

Часть метрик описывает не экземпляр, а всю схему: длина очереди, `delayed`
([0050](0050-deferred-start.md)), `oldest_claimable_age`, незавершённые и осиротевшие по типу
([0015](0015-observability.md), [0026](0026-contract-shape-marking.md)). Каждый экземпляр получал
бы их своим запросом к базе. Отсюда две беды:

- **сумма врёт.** Каждый экземпляр публикует одно и то же значение, а `sum()` по экземплярам —
  самое естественное действие в Prometheus и Grafana — умножает его на их число. Алерт «очередь
  больше 10 000» на двадцати экземплярах сработал бы при пятистах;
- **нагрузка растёт с числом экземпляров.** Счёт `PENDING` при миллионе подзадач — проход
  по миллиону записей частичного индекса. Граница активных партиций
  ([0101](0101-active-partition-horizon.md)) убирает лишние партиции, но не лишние строки.

Отдельно — разбивка по приоритету. [0063](0063-claim-ordering-and-pollers.md) потребовал разбивать
длину очереди и `oldest_claimable_age` по поллеру и приоритету: при `deadline` самая старая строка
может быть низкоприоритетной и ждать законно. Но приоритет — `smallint`, задаваемый при создании
любым значением, и метка с потенциально тысячами значений раздувает число рядов у потребителя.

## Рассмотренные варианты

### Кто считает метрики на всю схему

#### A. Каждый экземпляр сам, по такту, с оговоркой «агрегировать `max()`» — отвергнуто

Просто и без таблиц. Отвергнуто: нагрузка растёт ровно вместе с горизонтальным масштабированием,
ради которого стартер и пишется.

#### B. Один экземпляр за такт считает и пишет снимок, публикуют все из снимка — выбрано

Тяжёлые подсчёты — один раз на систему за такт. Ряды не пропадают при смене считающего
экземпляра: снимок читают все.

#### C. Считает и публикует только один экземпляр — отвергнуто

Таблица не нужна, но при смене экземпляра ряд пропадает с одного и появляется на другом,
а разрывы рядов ломают алерты.

### Разбивка по приоритету

#### D. Корзины приоритета — отвергнуто

Метка — диапазон, границы задаются свойством. Отвергнуто: новое свойство и умолчание, ни на чём
не основанное.

#### E. Просрочка относительно `claim_order_at` вместо разбивки — выбрано

При форме `deadline` у каждой строки уже есть свой срок с поправкой на приоритет —
`claim_order_at = next_attempt_at + priority × K`. Наибольшая просрочка
`max(now() − claim_order_at)` по захватываемым строкам отвечает ровно на вопрос 0063 — опаздывает
ли кто-то сверх своей законной форы — одним рядом на тип и поллер.

#### F. Убрать разбивку без замены — отвергнуто

Вопрос 0063 остался бы без ответа.

## Решение

### Снимок метрик на всю схему

- **Справочник `tc_metrics_snapshot`**, непартиционированный: строка на сочетание метрики
  и её меток — имя метрики, подсистема, тип задачи или внешняя система, поллер, причина у
  `delayed` — плюс значение и `computed_at`.
- **Считает один экземпляр за такт** — взявший `pg_try_advisory_xact_lock` по постоянному ключу,
  по образцу обслуживания партиций ([0078](0078-partition-maintenance.md)); не взял — такт
  пропускает. Снимок пишется одной транзакцией: строки этого такта вставляются или обновляются,
  строки, не обновлённые в этом такте (тип исчез), удаляются. Читатель видит снимок целиком.
- **Публикуют все экземпляры**: каждый по своему такту читает снимок и отдаёт значения из памяти.
  Опрос метрик в базу не ходит.
- **Такт — `taskcomm.metrics.interval`**, по умолчанию `30s`; не положительный — падение при старте.
  Подсчёты идут с границей активных партиций (0101).
- **Возраст снимка** — отдельная метрика каждого экземпляра: `now() − computed_at`. Снимок,
  который никто не обновляет, виден по ней, а не по застывшим значениям.
- **В снимок идут только метрики на всю схему**: длина очереди, `delayed` по причине,
  `oldest_claimable_age`, просрочка, незавершённые и осиротевшие по типу. Метрики того, что
  сделал сам экземпляр, — время выполнения, доля ошибок, число повторов, такт захвата, состояние
  размыкателей ([0065](0065-communication-circuit-breaker.md)) — остаются локальными; их сумма
  по экземплярам верна.

### Агрегация

- Описание каждой метрики из снимка говорит: значение на всю схему, по экземплярам агрегировать
  `max()`, не `sum()`. То же — в документации потребителя.

### Просрочка вместо разбивки по приоритету

- **Метки приоритета нет ни у одной метрики.**
- **Новая метрика — просрочка**: `max(now() − claim_order_at)` по захватываемым строкам,
  не меньше нуля, с разбивкой по типу задачи или внешней системе и по поллеру. Считается только
  для поллеров с формой `deadline`.
- Для форм `priority` и `quota` сигналом остаётся `oldest_claimable_age` по типу и поллеру:
  при строгом приоритете низкие ждут законно, и просрочка там не определена.
- Длина очереди и `oldest_claimable_age` разбиваются по типу и поллеру, как раньше, но без
  приоритета.

## Последствия

- **Тяжёлый подсчёт — один на систему за такт**, а не на каждый экземпляр и каждый опрос.
- **Значения запаздывают до одного такта** и ещё до одного такта чтения снимка.
- **Тринадцатая таблица**, четвёртый непартиционированный справочник; её строки обновляются
  каждый такт, и мёртвые версии убирает autovacuum — таблица на десятки строк.
- **Неверная агрегация остаётся возможной**: все экземпляры публикуют одно значение. Описание
  метрики и документация — единственная защита.
- **Число рядов ограничено числом типов, систем и поллеров** — конечным и известным из реестра
  процессоров и настроек, плюс осиротевшие типы.
- **Просрочка не определена для строгих форм захвата**: потребитель на `priority` видит только
  возраст.
