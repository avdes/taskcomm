# 0095. Ключи дедупликации при создании — только в транзакции `READ COMMITTED`

- **Дата:** 2026-10-21
- **Статус:** принято

## Контекст

Ключ дедупликации, заданный при создании коммуникации, проверяется в транзакции потребителя
([0076](0076-communication-deduplication.md)): `pg_advisory_xact_lock` по хешу ключа, затем поиск
по всем партициям `tc_communication_dedup`, затем вставка. Глобальность держит не индекс,
а блокировка, и рассчитана она на то, что поиск после неё видит всё закоммиченное до неё.

Это верно только при `READ COMMITTED`, где каждый оператор берёт свежий снимок. При
`REPEATABLE READ` и `SERIALIZABLE` снимок берётся на первом операторе транзакции — до ожидания
блокировки:

1. первая транзакция вставила ключ и закоммитила, отпустив блокировку;
2. вторая дождалась блокировки и ищет ключ в снимке, сделанном до коммита первой;
3. ключа не видно, дубликат проходит без единой ошибки.

`SERIALIZABLE` от этого не защищает: advisory-блокировки он не отслеживает, а одной зависимости
«чтение раньше записи» для отказа ему мало.

Уровень изоляции транзакции потребителя стартеру не подвластен: его выбирает
`@Transactional(isolation = ...)` или умолчание базы `default_transaction_isolation`.
Ключи из метода перед `process` и из `process` проверяются транзакциями стартера, и их уровень
стартер выставляет сам; проблема только у ключей при создании.

## Рассмотренные варианты

### A. Проверять уровень изоляции при создании с ключами и бросать исключение — выбрано

Один запрос `current_setting('transaction_isolation')` в той же транзакции и только при наличии
ключей. Механизм 0076 не меняется, молчаливый пропуск становится явной ошибкой.

### B. Проверять ключ при создании не в транзакции потребителя, а при захвате — отвергнуто

Изоляция потребителя перестаёт иметь значение. Отвергнуто: пропадает обещание 0076, что метод
создания возвращает идентификатор совпавшей коммуникации и контроллеру есть на что сослаться
в ответе отправителю. Ключ при создании превратился бы во второй «метод перед `process`».

### C. Строка-замок в своей таблице вместо advisory-блокировки — отвергнуто сейчас

Непартиционированная таблица с заранее созданными строками, хеш ключа по модулю их числа.
Проверка начинается с `UPDATE` своей строки: при `READ COMMITTED` поведение прежнее, при
`REPEATABLE READ` PostgreSQL сам отказывает «could not serialize access due to concurrent update»,
и тихого пропуска нет ни на каком уровне. Отвергнуто сейчас: двенадцатая таблица, горячие
обновления одних и тех же строк и их очистка, ложные отказы при совпадении строки у разных
ключей. Переход на C — внутреннее изменение, и он возможен позже, если потребителей на
`REPEATABLE READ` окажется много.

### D. Только описать в документации — отвергнуто

Требование «транзакция с ключами обязана быть `READ COMMITTED`» без проверки оставляет ошибку
молчаливой.

## Решение

- **Создание коммуникации с ключом дедупликации** проверяет уровень изоляции текущей транзакции
  запросом `current_setting('transaction_isolation')` — фактическим уровнем в базе, а не
  объявленным в Spring: умолчание бывает задано и в самой базе.
- Уровень **выше `READ COMMITTED`** — исключение до записи чего-либо, наследник
  `TaskcommException`. Сообщение называет уровень и два обходных пути: задать ключ методом
  процессора перед `process` или создать коммуникацию вне своей транзакции.
- Создание **без ключей** уровень не проверяет и работает при любом.
- **Собственные транзакции стартера** — создание вне транзакции потребителя
  ([0094](0094-creation-always-in-transaction.md)), проверка ключей перед `process` и из `process`
  — открываются с явным `READ COMMITTED`, не полагаясь на умолчание базы.

## Последствия

- **Потребитель на `REPEATABLE READ` или `SERIALIZABLE` не может задавать ключи при создании.**
  Обходной путь — метод перед `process`, но тогда метод создания не вернёт идентификатор
  совпавшей коммуникации: дубликат обнаружится позже и станет `SKIPPED` при захвате.
- **Лишний запрос** на каждое создание с ключами. Без ключей цены нет.
- **База с `default_transaction_isolation = 'repeatable read'`** уронит создание с ключами даже
  без `@Transactional(isolation = ...)` в коде потребителя. Это верно: при таком умолчании
  дедупликация и правда не работала бы.
- Переход на строку-замок (C) остаётся подготовленной альтернативой.
