# 0009. Повторы, прогресс агрегатом, статус `WARNING`

## Контекст

Задача из тысячи подзадач редко завершается однозначно: часть выполнится, часть упадёт и повторится,
часть исчерпает попытки. Нужно решить три связанных вопроса: что перезапускается при ошибке, как
считается прогресс и какой у задачи итоговый статус при частичном сбое.

## Рассмотренные варианты

### Что перезапускается

#### A. Весь батч целиком — отвергнуто

Проще для bulk-вызовов, но требует идемпотентности от **всей** обработки батча, включая уже
успешные подзадачи.

#### B. Только упавшие `TaskUnit` — выбрано

Идемпотентность требуется только от обработки одной подзадачи.

### Как считается прогресс

#### C. Денормализованные счётчики — отвергнуто

Колонки `total` / `succeeded` / `failed` на задаче, обновляются атомарно.

Быстро читаются, но создают конкуренцию за строку задачи: множество воркеров, завершающих подзадачи
одного батча, одновременно бьются за один и тот же счётчик.

#### D. Вычислять агрегатом — выбрано

`COUNT ... GROUP BY status` по подзадачам. Всегда точно, нечему рассогласоваться.

### Итог при частичном сбое

#### E. `FAILED` целиком — отвергнуто

Одна упавшая подзадача из тысячи хоронит результат остальных.

#### F. `WARNING` — выбрано

Задача доходит до конца, статус сообщает, что часть не удалась, упавшие перезапускаются через REST.

## Решение

Повторяются **только упавшие `TaskUnit`**. Прогресс **вычисляется агрегатом**. При частичном сбое
задача завершается в статусе **`WARNING`**, и через REST можно перезапустить только упавшие
подзадачи.

Набор статусов `TaskUnit` — минимальный:

```
PENDING ──захват──> RUNNING ──> SUCCEEDED
   ^                   │
   └──повтор───────────┼──> FAILED      (попытки исчерпаны, терминальный)
                       └──> CANCELLED
```

Отдельных статусов `RETRYING` / `SCHEDULED` **нет**: «ждёт повтора» — это `PENDING`
с `next_attempt_at` в будущем. Чем меньше статусов, тем меньше невозможных переходов, которые
пришлось бы защищать.

## Последствия

- Обязателен индекс `(task_id, status)`, и проверка «все ли подзадачи завершены» делается через
  `EXISTS`, а не `COUNT ... GROUP BY`. Без этого выбор в пользу агрегата обошёлся бы дорого:
  полный пересчёт после завершения каждой подзадачи из миллиона.
- Данные, собранные процессором на батч, **в БД не хранятся** и при повторе собираются заново.
- Отсюда неприятный частный случай: из батча в тысячу подзадач упала одна, и ради неё процессор
  снова тянет данные на всю группу. Вопрос, стоит ли группировать повторные подзадачи в новый
  батч, остаётся открытым.
- Backoff экспоненциальный и **обязательно с джиттером**. Без джиттера тысяча подзадач, упавших
  из-за недоступности внешней системы, проснётся одновременно и положит её повторно — то есть
  механизм повторов превратится в механизм отказа в обслуживании.
- `WARNING` — терминальный статус, но не финальный по смыслу: он существует ровно для того, чтобы
  человек или автоматика могли вернуться и перезапустить упавшее. Это делает операцию перезапуска
  в REST API не удобством, а обязательной частью продукта.
- Полный набор статусов `Task` и `TaskBatch` не описан. Известны только исходы: часть детей
  упала — `WARNING`, все упали — `FAILED`, ноль детей — `SUCCEEDED`. Промежуточные состояния
  и переходы остаются открытым вопросом.
