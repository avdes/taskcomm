# 0028. Миграция контракта через новый тип задачи

- **Дата:** 2026-08-27
- **Статус:** принято
- **Изменено:** [0029](0029-processor-never-deleted.md) — пятый шаг «удалить старый процессор»
  отменён. Процессор не удаляется никогда; удаление — ломающее изменение у потребителя.
- **Изменено:** [0061](0061-processor-configuration-annotations.md) — `@Deprecated` больше
  не единственная аннотация, читаемая с класса процессора: там же живут настройки аренды, повторов
  и приоритета. При клонировании процессора под новый `taskType` их надо переносить вручную —
  ничто об этом не напомнит.

## Контекст

[0026](0026-contract-shape-marking.md) закрыл смену **формы** контракта, но оставил дыру: потребитель
может не менять форму, а поменять смысл нагрузки. Раньше в `U` лежал идентификатор заказа, теперь
весь заказ. Форма та же, поле то же, старые незавершённые подзадачи невалидны, и никакая автоматика
этого не заметит.

Нужен способ менять контракт, не ломая незавершённую работу.

## Рассмотренные варианты

### A. Версия контракта — отвергнуто

`contractVersion()` в контракте процессора, версия пишется в запись задачи, стартер сопоставляет.

Отвергнуто по существу, а не по стоимости. Версия требует, чтобы **один процессор понимал несколько
форматов нагрузки** — то есть внутри него всё равно появился бы `switch` по версии, только теперь
с нашим участием в схеме и в реестре. При этом стартер брал бы на себя роль, которую исполнить
не может: он не знает, совместимы форматы или нет, и вынужден верить числу.

### B. Новый `taskType` вместо новой версии — выбрано

Потребитель клонирует процессор под новым типом. Старые задачи выполняет буквально старый класс,
никто ничего не интерпретирует.

### C. Ничего, миграция целиком руками — отвергнуто

Оставляет дыру открытой.

## Решение

Смена контракта выполняется **заведением нового типа задачи**. Порядок:

1. Клонировать процессор под новым `taskType` с суффиксом версии (`order-sync-v2`).
2. Переключить постановку задач на новый тип.
3. Пометить старый процессор `@Deprecated` — новые задачи на него больше не принимаются.
4. Дождаться, пока счётчик незавершённых задач старого типа обнулится.
5. Удалить старый процессор следующим релизом.

Стартер поддерживает эту практику тремя вещами:

- **`@Deprecated` на классе процессора** блокирует постановку новых задач этого типа. Существующие
  выполняются как обычно.
- **Метрика незавершённых с разбивкой по типу** и **REST-сводка по типам** — чтобы шаг 4 был
  проверяемым, в том числе автоматически из CI перед выкладкой.
- **Страховка из [0026](0026-contract-shape-marking.md)**: если процессор удалили слишком рано,
  оставшиеся задачи не берутся в работу, но и не гибнут — вернули процессор, они доигрывают.

## Последствия

- **`@Deprecated` получает доменный смысл сверх стандартного.** В Java она означает «не используйте
  это в коде», а у нас — ещё и «не принимай новые задачи». Кто-то пометит процессор «планируем
  убрать в следующем квартале» и сломает постановку в проде. Смягчение: список устаревших типов
  **громко печатается при старте**, чтобы неожиданность обнаружилась при деплое, а не при первой
  постановке. Аннотация ищется на классе процессора, не на `@Bean`-методе.
- Постановка задачи устаревшего типа **отвергается исключением**; через REST — ошибка клиента
  с внятным текстом. Иначе признак не имел бы смысла.
- **Версия контракта не нужна ни для чего.** Дыра, оставленная в [0026](0026-contract-shape-marking.md),
  закрыта практикой, а не механизмом в стартере. Это лучше: механизма, который надо поддерживать,
  не появилось вовсе.
- Цена — расползание имён типов: `order-sync`, `order-sync-v2`, `order-sync-v3`. Дисциплина шага 5
  обязательна, иначе через два года в реестре будет зоопарк.
- Откат релиза безопасен на всех шагах, кроме последнего: старый процессор ещё на месте.
- Метрика незавершённых по типам полезна не только здесь — она же основа для алертов на рост
  очереди ([0015](0015-observability.md)).
