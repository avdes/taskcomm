# 0121. Сборка читает детей страницами по ключу

- **Дата:** 2026-10-24
- **Статус:** принято

## Контекст

`collect` и `collectBatch` получают ленивый поток всех терминальных детей последней успешной
попытки раскрытия ([0059](0059-collect-contract.md)); детей бывает миллион, материализовать поток
нельзя ([0048](0048-collect-phase.md)). Процессор при этом работает вне транзакции и соединения
из пула не держит ([0006](0006-lease-based-claiming.md)). Сборка может идти долго: это код
потребителя.

## Рассмотренные варианты

### A. Один запрос с курсором в транзакции на всё время сборки — отвергнуто

Один проход по индексу, снимок согласован, нового индекса не нужно. Отвергнуто: код потребителя
держит соединение из пула и открытый снимок всё время сборки, а открытый снимок задерживает
vacuum по всей базе. Это ровно то, что запрещает правило «процессор работает вне транзакции».

### B. Страницы по ключу — выбрано

Каждая страница — свой короткий запрос `parent_attempt_id = :a AND id > :last ORDER BY id LIMIT n`.

Снимок между страницами не нужен: к началу сборки незавершённых детей у попытки нет — это условие
запуска сборки ([0069](0069-parent-phase-column.md)), а перезапуск ребёнка во время сборки
отвергается ([0097](0097-no-restart-during-collect.md)). Набор детей на время сборки неподвижен.

Существующий индекс `(parent_attempt_id, status)` порядка по `id` не даёт: каждая страница
перебирала бы и сортировала всех детей попытки, и сборка миллиона детей стала бы квадратичной.

## Решение

- Поток сборки читается страницами по 1000 детей, каждая отдельным запросом без транзакции
  стартера. Ключ страницы — `id` ребёнка.
- На `tc_task_batch` и `tc_task_unit` заводится индекс **`(parent_attempt_id, id)`** —
  `*_collect_idx`. Индекс `(parent_attempt_id, status)` остаётся: на нём держатся `EXISTS`
  «незавершённых детей не осталось» и агрегат.
- Результат подзадачи читается прямым соединением, результат группы — `LATERAL` по её последней
  попытке ([0058](0058-task-result-storage.md)).
- План страницы проверяется тестом: индекс `(parent_attempt_id, id)` без узла сортировки.
- Тот же обход по ключу детей использует удаление их результатов
  ([0122](0122-child-results-discard-sweep.md)).

## Последствия

- Код потребителя в `collect` не держит ни соединения, ни снимка; поток можно читать сколько
  угодно долго.
- На таблицах детей на один индекс больше: каждая вставка ребёнка пишет и его. Таблица подзадач —
  самая большая в схеме, и это заметная цена записи.
- Поток идёт в порядке `id`, то есть примерно в порядке вставки детей (UUIDv7). Обещанием
  контракта этот порядок не является.
