# 0005. Хранилище: SPI, Spring JDBC, PostgreSQL, без JPA

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

Стартер обещает потребителю «не думать о персистентности и горизонтальном масштабировании». Значит
хранилище — не деталь реализации, а часть продукта, и выбор технологии доступа к данным влияет
на всех потребителей сразу.

Два требования формируют выбор:

1. Несколько экземпляров приложения делят между собой единицы работы, и захват должен быть
   корректным без внешней инфраструктуры.
2. Библиотека не имеет права навязывать потребителю тяжёлый транзитив.

## Рассмотренные варианты

### Технология доступа

#### A. Spring Data JPA / Hibernate — отвергнуто

Привычно и быстро пишется.

Отвергнуто: Hibernate приезжает транзитивом каждому потребителю, включая тех, у кого его нет и не
планировалось. Кроме того, захват через `SELECT ... FOR UPDATE SKIP LOCKED` с точным контролем
над блокировками через JPA выражается плохо, а он у нас центральный механизм.

#### B. Spring JDBC (`JdbcClient`) — выбран

SQL пишется руками. Полный контроль над блокировками, транзакциями и планами запросов;
никакого тяжёлого транзитива.

### Форма хранилища

#### C. Конкретная реализация без абстракции — отвергнуто

Проще, но потребитель не может ничего подменить, и in-memory хранилище для тестов пришлось бы
имитировать поднятием реальной БД.

#### D. SPI + реализация — выбран

Интерфейсы (`TaskRepository`, `CommunicationRepository`) в `api`, реализация на Spring JDBC
и PostgreSQL — в `internal`.

### Механизм захвата

#### E. `SELECT ... FOR UPDATE SKIP LOCKED` — выбран

Очередь живёт в той же БД, что и состояние. Никакой дополнительной инфраструктуры.

#### F. Брокер (Kafka / RabbitMQ) — отвергнуто

Требует инфраструктуры у **каждого** потребителя стартера. Для библиотеки это неприемлемая цена:
мы бы обязали всех, кто хочет таск-менеджмент, поднять брокер.

#### G. ShedLock / лидер-выборы — отвергнуто

Даёт «работает только один экземпляр», тогда как нам нужно «работают все, но над разными
единицами».

## Решение

Хранилище объявлено как **SPI**: интерфейсы в `api`, реализация на **Spring JDBC + PostgreSQL**
в `internal`. Захват — **`SELECT ... FOR UPDATE SKIP LOCKED`**. In-memory реализация планируется
как вторая реализация того же SPI.

## Последствия

- SQL пишется руками, в text blocks. Hibernate и JPA в проекте нет — **не добавлять**.
- Реализация репозитория объявляется под `@ConditionalOnMissingBean`, поэтому потребитель может
  подставить свою. Это не декоративная возможность: она же обеспечивает будущее in-memory
  хранилище без изменений в остальном коде.
- Распределённых локов, ShedLock и брокеров в проекте нет и не должно появиться.
- Привязка к PostgreSQL реальная: `SKIP LOCKED`, `jsonb` и `ON CONFLICT` — не стандартный SQL.
  Поддержка другой СУБД потребует отдельной реализации SPI, а не «правки диалекта».
- Раз SPI публичный, его сигнатуры подчиняются правилам совместимости
  из [0004](0004-public-api-boundary.md): добавить метод в интерфейс репозитория без
  `default`-реализации — ломающее изменение.
