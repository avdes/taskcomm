# 0089. Хранилище без публичного SPI, заменяемы только бины публичных типов

- **Дата:** 2026-10-20
- **Статус:** принято
- **Изменено:** [0096](0096-no-foreign-type-beans.md) — бины чужих типов стартер не регистрирует вовсе;
  точки замены — бины потребителя с квалификатором стартера, а не `@ConditionalOnMissingBean`;
  `RequestMatcher` и классы свойств из точек замены убраны.

## Контекст

Два правила стартера обещают больше, чем можно сдержать.

**«Потребитель может заменить любой наш бин своим»** — каждый бин под `@ConditionalOnMissingBean`
([0002](0002-autoconfiguration-registration.md)). Условие срабатывает по типу бина. Чтобы
заменить, например, поллер, потребитель объявляет бин этого типа — наследует или реализует класс
из `internal`. После этого любая правка внутреннего класса ломает его, хотя
[0004](0004-public-api-boundary.md) обещает, что за `internal` обязательств совместимости нет.
Одно правило обещает заменяемость того, совместимость чего другое явно не гарантирует.

**Хранилище — публичный SPI** ([0005](0005-persistence-spi.md)): `TaskRepository`,
`CommunicationRepository`, `ExecutionRepository` в `api`, «in-memory реализация планируется».
За последние решения в SPI вошли захват двумя ветками со `SKIP LOCKED`, аренда и переподхват,
перевод детей пачками, сборка, дедупликация под advisory-блокировкой, обслуживание партиций,
поиск. Всё это завязано на PostgreSQL — 0005 сам это признаёт, — второй реализации нет,
а заморозится SPI на 2.0.0: новый метод требует `default`-реализации, правка существующего —
мажорной версии. Заморожена оказалась бы самая подвижная часть проекта.

In-memory реализация честно невозможна: в памяти нет партиций, `SKIP LOCKED` между экземплярами
и advisory-блокировок. Для тестов её место заняли Testcontainers
([0085](0085-tests-on-real-postgres.md)).

## Рассмотренные варианты

### SPI хранилища

#### a. Убрать в `internal` — выбрано

В 2.0.0 публичного SPI нет. Появится вторая реализация — тогда SPI и проектируется, по двум
примерам: интерфейс, выведенный из одной реализации, почти всегда неудачен.

#### b. Оставить публичным, как в 0005 — отвергнуто

Заморозка самой подвижной части.

#### c. Публичный с пометкой `@ApiStatus.Experimental` — отвергнуто

Честнее b, но потребитель, реализовавший SPI, всё равно ломается на каждом минорном выпуске.
Пометка переносит цену на него, а не убирает её.

### Заменяемость бинов

#### d. Заменяемы только бины публичных типов, список точек замены ведётся явно — выбрано

#### e. Оставить «заменяем любой» — отвергнуто

Внутренние типы становятся фактическим API без обязательств, которые к нему положены.

## Решение

- **Интерфейсы хранилища — `TaskRepository`, `CommunicationRepository`, `ExecutionRepository` —
  живут в `internal` своих подсистем.** Публичного SPI хранилища в 2.0.0 нет. Реализация одна —
  Spring JDBC и PostgreSQL. Интерфейс внутри остаётся ради тестов и чистоты слоёв, а не как
  точка расширения.
- **In-memory реализации нет и в планах нет.** Тесты идут на PostgreSQL в Testcontainers.
- **`@ConditionalOnMissingBean` — только у бинов публичных типов**: из `api` стартера или чужих
  библиотек — например, `ObjectMapper` для нагрузки, планировщик или пул воркеров,
  `RequestMatcher`. **Список точек замены ведётся явно** — в CLAUDE.md и в документации
  потребителя — и пополняется вместе с бинами.
- **Бины внутренних типов объявляются без `@ConditionalOnMissingBean`.** Выключить подсистему
  целиком по-прежнему можно её `enabled: false`.
- Тест «бин потребителя перекрывает наш» пишется **для каждой точки замены из списка**,
  а не для каждого бина.

## Последствия

- **Механику хранилища можно менять в минорных выпусках**: захват, аренда, партиции — внутренние.
- **Потребитель не может подставить своё хранилище.** Нужна другая СУБД — это запрос на вторую
  реализацию и на проектирование SPI, а не замена бина.
- **Замена внутреннего компонента невозможна штатно.** Нужна — это запрос на новую точку
  замены с публичным типом, и она проектируется как API.
- Правило 0002 «каждый бин — под `@ConditionalOnMissingBean`» сужено; запрет `@ComponentScan`,
  стереотипов и глобальных механизмов Spring в силе.
- `execution.api` теряет `ExecutionRepository`; `ExecutionService` остаётся.
