# 0003. Именование доменных типов

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

Имена типов библиотеки попадают в чужие файлы — туда, где уже импортированы Spring, JPA и половина
`java.lang`. Поэтому цена неудачного имени для библиотеки выше, чем для приложения: коллизию
разгребает не автор, а потребитель, и разгребает полными именами классов.

Второе ограничение: переименование публичного типа — ломающее изменение, то есть мажорная версия.
Имя выбирается один раз.

Третье, содержательное: стартер **не знает и не должен знать**, какие бизнес-объекты обрабатывает
потребитель. Значит доменные имена обязаны оставаться абстрактными и ничего не утверждать
про содержимое.

Исходные рабочие имена были `TaskItem`, `TaskBatch`, `TaskHandler`. Предлагалась замена на
`TaskEntity`, `TaskPackage`, `TaskExecutor`.

## Рассмотренные варианты

### `Entity` вместо `Item` — отвергнуто

В Java слово читается однозначно: либо строка таблицы (`jakarta.persistence.Entity`), либо объект
с идентичностью в терминах DDD. Три отдельные проблемы:

1. Персистентность в проекте на Spring JDBC, и `TaskEntity` — самое естественное имя для типа,
   отображающего строку БД. Отдав его подзадаче, мы забираем имя у другой сущности.
2. У потребителя, где рядом есть JPA, `import ...taskcomm...Entity` и `jakarta.persistence.Entity`
   в одном файле конфликтуют.
3. Главное: имя нарушает собственное требование абстрактности. «Entity» утверждает про объект две
   вещи — что у него есть идентичность и что он персистентный, — а мы про бизнес-объекты
   потребителя не знаем ничего.

### `Package` вместо `Batch` — отвергнуто

`package` — зарезервированное слово Java: переменную так не назвать, останутся `pkg`, `taskPackage`,
`aPackage`. А `Package` без префикса — это `java.lang.Package`, неявно импортированный
в **каждый** файл проекта; собственный класс с таким именем его затеняет.

### `Executor` вместо `Handler` — отвергнуто

`org.springframework.core.task.TaskExecutor` — существующий интерфейс Spring, живущий ровно в нашей
предметной области: пул потоков, исполняющий задачи. Мы сами будем его инжектить для поллера.
Столкновение не теоретическое: в одном файле понадобятся оба типа, и один придётся писать
полным именем.

### `Subtask` — рассмотрено, не выбрано

Имя точное: называет отношение к задаче, а не содержимое. Оговорка — `java.util.concurrent.
StructuredTaskScope.Subtask`, появившийся в Java 21 как preview. Коллизия сработает только в файлах
со структурной многопоточностью, но со временем этот API перестанет быть preview.

### `TaskItem` / `TaskUnit` — финалисты

Оба абстрактны и свободны от коллизий. `Item` — максимально нейтральное «один из многих», привычная
пара к `Batch` (ср. `ItemReader` / `ItemProcessor` в Spring Batch). `Unit` — «единица работы»,
устоявшийся термин ровно для того, что происходит: минимальный неделимый кусок, который либо
выполнился, либо будет повторён.

## Решение

Приняты имена **`TaskUnit`**, **`TaskBatch`**, **`TaskProcessor`**.

`Handler` заменён осознанно: слово описывает обработку событий и колбэки, а у нас объект, который
выполняет работу. `Processor` точнее и даёт очевидную пару `CommunicationProcessor`.

`Item` заменён на `Unit` по вкусовым соображениям при равенстве по существу — оба удовлетворяли
требованию абстрактности.

Сформулировано общее правило именования: **доменные типы называют единицу работы и её место
в иерархии, а не содержимое.** Полезная нагрузка — параметр типа, непрозрачный для стартера.

## Последствия

- Запрещены имена, утверждающие что-либо про полезную нагрузку: `Entity`, `Record`, `Document`,
  `Object`. Любое из них будет врать, потому что содержимое у каждого потребителя своё.
- Запрещены имена, сталкивающиеся с ключевыми типами платформы и Spring: `TaskExecutor`, `Package`.
- Нагрузки на уровнях иерархии — **разных типов**: `Task<P>` несёт параметры задачи, `TaskBatch<B>` —
  данные, собранные на всю группу, `TaskUnit<U>` — один бизнес-объект. Одинаковый параметр типа
  на всех уровнях был бы ошибкой моделирования.
- Правило именования распространяется на будущие типы: любое новое имя проверяется на коллизию
  с `java.lang`, `java.util.concurrent` и `org.springframework.*` до того, как попадёт
  в публичный API.
