# 0036. Перечислимые колонки: `text` с `CHECK`, а не нативный enum

- **Дата:** 2026-08-28
- **Статус:** принято

## Контекст

В схеме несколько колонок с фиксированным набором значений: статусы задачи, батча, подзадачи
и коммуникации ([0023](0023-parent-statuses.md), [0009](0009-retry-and-progress.md)), форма
контракта `FLAT`/`UNIT`/`BATCH` ([0026](0026-contract-shape-marking.md)), направление коммуникации
и `FieldType` в белом списке поиска ([0016](0016-payload-search.md)).

Привычный выбор для таких колонок — нативный enum PostgreSQL. Три наших решения меняют расклад.

## Рассмотренные варианты

### A. Нативный enum — отвергнуто

Даёт четыре байта на строку вместо семнадцати, невозможность вставить мусор, сортировку по порядку
объявления и самодокументируемость через `\dT+`.

Отвергнуто по трём причинам, и все три специфичны для нас:

- **Мы не владеем `DataSource`.** По [0017](0017-task-creation-transaction.md) стартер работает
  в пуле потребителя, значит не может выставить `stringtype=unspecified` на соединении. Без него
  драйвер отправляет строковый параметр как `varchar`, и PostgreSQL отвечает `column "status" is
  of type tc_task_status but expression is of type character varying`. Лечится явным кастом
  `?::tc_task_status` в **каждом** запросе со статусом либо привязкой через `Types.OTHER`
  в каждом таком параметре. SQL у нас пишется руками, статус участвует в захвате, продлении,
  завершении, закрытии родителя, подстраховочном поллере и фильтрах REST — забытый каст даёт
  ошибку времени выполнения, а не компиляции.
- **Мы отдаём Liquibase-changelog в чужой changelog** ([0013](0013-database-schema.md)).
  `ALTER TYPE ... ADD VALUE` имеет особые правила относительно транзакций, и changeSet под него
  придётся помечать `runInTransaction="false"` — особенность, с которой столкнётся потребитель,
  а не мы.
- **Из enum нельзя удалить значение.** Переименовать можно, удалить — только пересозданием типа
  с перезаписью колонки.

Главный довод за enum — компактность — у нас слабый: в каждой строке лежит `jsonb` с нагрузкой,
сотни байт или килобайты. На этом фоне разница между четырьмя байтами и семнадцатью — шум.
Компактность enum окупается на узких таблицах, а наши узкими не будут.

### B. `text` с `CHECK` — выбрано

### C. `text` без ограничения — отвергнуто

Проще всего эволюционировать, но БД пропустит любое значение. Опечатка в коде превратится
в строку, которую никто не найдёт и которая не попадёт ни в один частичный индекс по статусу.

### D. Числовые коды `smallint` — отвергнуто

Компактно, но нечитаемо при разборе инцидента в `psql`. Это тот же принцип, по которому нагрузка
хранится в `jsonb`, а не в `bytea` ([0012](0012-payload-storage.md)): содержимое должно быть видно
глазами прямо в SQL.

## Решение

Перечислимые колонки — **`text` с ограничением `CHECK`**. Единообразно для всех: статусы всех
четырёх сущностей, форма контракта, направление коммуникации, `FieldType`.

Значения хранятся ровно так, как называются в Java-перечислении: `PENDING`, `AWAITING_CHILDREN` —
верхний регистр, подчёркивания. Тогда то, что видно в `psql`, совпадает с тем, что видно в логах
и в ответах REST.

Добавление значения — аддитивная миграция: `ADD CONSTRAINT ... NOT VALID`, затем
`VALIDATE CONSTRAINT`. Валидация берёт мягкую блокировку и проходит онлайн даже на больших
партиционированных таблицах.

## Последствия

- Кастов в SQL нет, привязка параметров обычным `setString` работает везде.
- **`CHECK` дублирует Java-перечисление.** Это вторая копия одного списка, и копии могут разойтись:
  добавили статус в Java, забыли в DDL — получите ошибку вставки в рантайме. Нужен тест, сверяющий
  значения перечисления с содержимым ограничения; это дешевле, чем расширять стартовую проверку
  схемы ([0013](0013-database-schema.md)).
- Ограничение объявляется на партиционированной таблице и наследуется партициями — отдельно
  на каждую его вешать не надо.
- **Убрать значение из `CHECK` можно только после того, как в таблицах не осталось таких строк.**
  Практически это означает, что статус, вышедший из употребления, останется в ограничении ради
  истории — до дропа последней партиции с ним. Из enum значение не удалить вовсе, так что здесь
  мы всё же в лучшем положении, но не в свободном.
- Цена в объёме — около тринадцати лишних байт на строку против enum. Принята сознательно.
- Сортировка по статусу становится алфавитной, а не по порядку объявления. Нам это безразлично:
  по статусу мы не сортируем, порядок захвата — по `next_attempt_at` ([0019](0019-claim-ordering.md)).
