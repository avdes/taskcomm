# 0008. Раскрытие через `Emitter` и признак `expanded_at`

- **Дата:** 2026-08-27
- **Статус:** принято
- **Изменено:** [0047](0047-children-belong-to-attempt.md) — правило «повтор раскрытия начинается
  с удаления ранее порождённых детей» **отменено целиком**: дети принадлежат попытке раскрытия,
  новая попытка порождает своих. Колонка `expanded_at` исчезает — её заменяет исход попытки.
- **Изменено:** [0032](0032-no-business-key.md) — перегрузки `emit(businessKey, payload)` нет вовсе.
  `Emitter<T>` остаётся единственным интерфейсом с единственным методом `emit(payload)`.
- **Изменено:** [0031](0031-batch-addressing.md) — перегрузка `emit(businessKey, payload)` доступна
  только при порождении подзадач. `Emitter` расщеплён: базовый `Emitter<T>` без ключа
  и `UnitEmitter<U>` с ключом.

## Контекст

Задача «синхронизировать заказы за март» может породить миллион подзадач. Надо решить два вопроса:
кто эти подзадачи создаёт и в какой форме отдаёт.

Ограничения: миллион бизнес-объектов нельзя протащить через REST при постановке задачи, и его же
нельзя держать в памяти воркера целиком.

## Рассмотренные варианты

### Кто создаёт подзадачи

#### A. Потребитель передаёт коллекцию при постановке — отвергнуто

Требует, чтобы вызывающая сторона уже располагала всеми объектами. Для задачи, которая сама должна
сходить во внешнюю систему и выяснить, что обрабатывать, это неприменимо.

#### B. Процессор раскрывает задачу — выбрано

Через API задача ставится параметрами. Процессор получает `Task` и порождает подзадачи сам,
асинхронно. Каскад:

```
Task ──expand──> TaskBatch[] ──expandBatch──> TaskUnit[] ──process──> готово
Task ──expand──> TaskUnit[]  ──process──────> готово
Task ──process──────────────────────────────> готово        (плоский контракт)
```

### В какой форме отдаёт

#### C. Возвращает `List<U>` — отвергнуто

Простейший контракт для потребителя. Отвергнуто: миллион объектов оказывается в памяти целиком.

#### D. Возвращает `Stream<U>` / `Iterator<U>` — отвергнуто

Лениво, но перекладывает на потребителя обязанность правильно закрывать ресурсы, а библиотека
не может рассчитывать на дисциплину чужого кода.

#### E. Пишет в `Emitter<T>` — выбрано

Процессор вызывает `emit(payload)`; стартер копит в буфере и вставляет пачками. Память под
контролем стартера, потребителю ничего закрывать не нужно.

## Решение

Подзадачи создаёт **процессор**, отдавая их в **`Emitter`**.

Выбор `Emitter` порождает проблему, которой у `List` не было: **раскрытие перестаёт быть атомарным**.
Процессор может выдать 500 подзадач из 1000 и упасть — подзадачи есть, но раскрытие не закончено.

Решение — колонка **`expanded_at`** на задаче и на батче. Это не статус, а факт: «раскрытие дошло
до конца». Она же чинит второй случай: раскрытие может успешно вернуть **ноль** подзадач (заказов
в марте не было), и признак «подзадач нет» отличить эти два случая не позволяет.

### Идемпотентность повторного раскрытия

Рассматривался ключ идемпотентности: процессор отдаёт для каждого объекта стабильный бизнес-ключ,
уникальный индекс `(task_id, unit_key)`, вставка `ON CONFLICT DO NOTHING`.

**Отвергнуто.** Решающим оказалось смежное решение: обработка не начинается, пока у родителя не
проставлена `expanded_at`. Значит частично раскрытые подзадачи гарантированно никем не тронуты,
и их можно просто удалить.

Дополнительный довод: ключ покупает меньше, чем кажется. Процессор при повторе перечисляет источник
с самого начала — возобновиться с середины он не умеет. То есть `ON CONFLICT` экономит вставки,
а не работу потребителя. Взамен ключ навсегда добавляет обязательство в публичный контракт.

Принятое правило: **любая попытка раскрытия начинается с удаления ранее порождённых детей этого
родителя.** На первой попытке это no-op, на повторной — очистка. Идемпотентность по построению.

## Последствия

- У задачи и батча есть `expanded_at`. «Упало на раскрытии» определяется по `expanded_at IS NULL`,
  **а не по отсутствию детей**.
- Каждый сброс буфера эмиттера — своя короткая транзакция. Ни миллион строк в памяти, ни миллион
  строк в одной транзакции.
- Порядок в конце раскрытия строгий: сначала финальный сброс, потом `expanded_at`.
- **Дети доступны для работы только после `expanded_at` своего непосредственного родителя.**
  Подзадачи батча идут в работу, как только раскрыт этот батч, — ждать соседних батчей не нужно.
- `Emitter` действителен только внутри вызова `expand` и не потокобезопасен. Вызов после
  возврата — `IllegalStateException`. Сохранение ссылки в поле — классическая ошибка при работе
  с чужими библиотеками, и ловить её надо явно, а не загадочным поведением.
- Сигнатура — `emit(payload)`. Перегрузка `emit(businessKey, payload)` необязательна и нужна только
  для поиска в REST и логах: индекс есть, уникальности нет, на идемпотентность не влияет.
- Раскрытие, вернувшее ноль детей, — это `SUCCEEDED`, а не ошибка и не `WARNING`.
- Плата за отказ от ключа: при повторе выбрасывается вся работа предыдущей попытки раскрытия.
  Признано приемлемым, поскольку процессор всё равно перечисляет источник заново.
