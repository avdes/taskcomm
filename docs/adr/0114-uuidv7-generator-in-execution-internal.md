# 0114. Генератор UUIDv7 — в `execution.internal`

- **Дата:** 2026-10-24
- **Статус:** принято

## Контекст

Генератор UUIDv7 — свой, в `internal`, не публичный API
([0035](0035-uuidv7-identifiers.md), [0079](0079-database-clock.md)). Нужен он трём местам:
делу (`execution.internal`), задачам (`task.internal`) и, с этапа 5, коммуникациям
(`communication.internal`). В каком пакете он лежит, правило не говорило.

Общего кода у подсистем нет ([0010](0010-separate-engines.md)), а единственный пакет, доступный
обеим, — `execution.internal`. Это исключение заведено ради общего держателя текущего дела
([0087](0087-architecture-rules.md)) и молча не расширяется.

## Рассмотренные варианты

- **A. В `execution.internal` — выбрано.** Один класс рядом с `ExecutionRepository`, которому
  генератор нужен и самому. Пакетная граница ArchUnit не меняется, меняется смысл исключения:
  теперь оно не только ради держателя дела.
- **B. Копия в каждом `internal`** — отвергнуто. Тридцать строк, но с тонким местом —
  монотонностью внутри миллисекунды; три копии разошлись бы на первой правке. И это не механика
  движка, ради независимости которой дублирование и разрешено.
- **C. В корневом пакете** — отвергнуто: корневой пакет — публичный API, а генератор не API.

## Решение

Генератор `UuidV7` живёт в `execution.internal`. Исключение «`execution.internal` доступен
внутренним пакетам обеих подсистем» теперь существует ради двух вещей: держателя текущего дела
и генератора идентификаторов. Список закрытый: что-то третье — новое решение.

## Последствия

- Один генератор на приложение. Монотонность — внутри одного экземпляра генератора; стартер
  создаёт его один и раздаёт компонентам.
- Формулировка исключения в CLAUDE.md и в ArchUnit-тесте называет оба основания.
- Разросшийся `execution.internal` начал бы становиться общим кодом подсистем, который запрещает
  0010. Отсюда закрытый список.
