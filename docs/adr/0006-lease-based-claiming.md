# 0006. Захват работы по аренде

- **Дата:** 2026-08-27
- **Статус:** принято
- **Изменено:** [0046](0046-lease-in-attempt.md) — `locked_by`, `locked_until` и токен аренды
  живут в строке попытки, а не в строке сущности; колонки `attempt` на сущности больше нет.
  На сущности из перечисленного здесь остаётся только `next_attempt_at`.
- **Изменено:**
  [0021](0021-execution-time-limit.md) — к перечню колонок аренды добавлен `lease_token`, без
  которого запись результата не защищена от вытесненного воркера.
- **Изменено:** [0063](0063-claim-ordering-and-pollers.md) — `ORDER BY` в запросе захвата больше
  не один: форм три, и выбираются они настройкой поллера. Поллер тоже больше не один — типы задач
  и внешние системы можно выделять в отдельные, и основной их не берёт.
  [0025](0025-lease-mechanics.md) — описана механика heartbeat (отдельный поток на инстанс)
  и поведение при потере аренды.

## Контекст

Несколько экземпляров приложения читают одну и ту же таблицу подзадач. Чтобы двое не взяли одну
строку, используется `SELECT ... FOR UPDATE SKIP LOCKED`: первый воркер блокирует строку, второй её
не видит.

Ограничение, которое нельзя обойти: **блокировка в PostgreSQL живёт ровно столько, сколько живёт
транзакция**. Значит надо решить, когда транзакцию закрывать — и оба варианта имеют цену.

Важная деталь контекста: между захватом и завершением работает `TaskProcessor` — **код потребителя
неизвестной длительности**. В плоском контракте (задача целиком, без подзадач) он может работать
минутами.

## Рассмотренные варианты

### A. Транзакция держится всё время выполнения

```
BEGIN
  SELECT ... FOR UPDATE SKIP LOCKED
  <работает процессор потребителя>
  UPDATE status = 'SUCCEEDED'
COMMIT
```

Плюс: восстановление после падения бесплатное. Процесс убили — соединение оборвалось, транзакция
откатилась, блокировка снята, строка снова доступна. Писать для этого не надо ничего.

Минус: соединение из пула занято всё время работы чужого кода. Пул на 20 соединений означает
максимум 20 одновременно выполняемых подзадач, сколько бы потоков ни было выделено. Дополнительно
долгие транзакции мешают autovacuum.

### B. Аренда (lease)

```
BEGIN
  SELECT ... FOR UPDATE SKIP LOCKED
  UPDATE status = 'RUNNING', locked_until = now() + аренда
COMMIT                                  -- соединение сразу вернулось в пул
<работает процессор>
BEGIN  UPDATE status = 'SUCCEEDED'  COMMIT
```

Плюс: соединение свободно во время работы процессора, параллелизм не упирается в размер пула.

Минус: транзакции нет — падение воркера нечему откатывать, и строка навсегда останется в `RUNNING`.
Нужен механизм возврата: колонка `locked_until` и поллер, который забирает не только `PENDING`,
но и `RUNNING` с истёкшей арендой. Долгие подзадачи обязаны продлевать аренду (heartbeat).

## Решение

Выбран вариант **B, аренда**.

Решающий довод: процессор — чужой код неизвестной длительности. Связывать его с соединением БД
означает сделать пул соединений потолком параллелизма для всей системы. Это ровно та проблема,
из-за которой в проекте ограничено использование виртуальных потоков: увеличивать число потоков
бессмысленно, если узкое место — пул соединений.

Вариант A остаётся честно работающим при заведомо коротких подзадачах, но библиотека не может
рассчитывать на то, что подзадачи потребителя будут короткими.

## Последствия

- В таблицах появляются `locked_by`, `locked_until`, `attempt`, `next_attempt_at`.
- Поллер обязан подбирать `RUNNING` с истёкшим `locked_until` — без этого падение воркера
  навсегда теряет подзадачу.
- Нужен heartbeat для долгих единиц работы **и верхний предел на выполнение**: иначе зависший
  процессор будет продлевать аренду бесконечно.
- Длительность аренды становится настраиваемым параметром с двусторонним риском: слишком короткая
  даёт двойное выполнение, слишком длинная — простой после падения.
- **Главное следствие: гарантия становится at-least-once, а не exactly-once.** У живого, но
  медленного воркера аренда может истечь, и подзадачу подберёт другой. Значит обработка обязана
  быть идемпотентной — это требование к коду потребителя, и оно должно быть написано
  в Javadoc каждого интерфейса процессора явным текстом, а не подразумеваться.
