# 0007. Три контракта процессора и запечатанная иерархия

- **Дата:** 2026-08-27
- **Статус:** принято
- **Изменено:** [0045](0045-flat-task-processor.md) — `SimpleTaskProcessor` переименован
  в **`FlatTaskProcessor`**, чтобы имя интерфейса совпадало со значением `contract_shape` = `FLAT`.
  В теле ниже сохранено прежнее имя, оно встречается в четырёх местах.
- **Изменено:** [0059](0059-collect-contract.md) — параметры типа расширены результатами
  и переименованы: `FlatTaskProcessor<T, RT>`, `UnitTaskProcessor<T, U, RU, RT>`,
  `BatchTaskProcessor<T, B, U, RU, RB, RT>`. Буква совпадает с уровнем: `Task<P>` стал `Task<T>`.
  Запечатанность и разбор без ветки `default` в силе.

## Контекст

Задачи бывают разной формы, и это не вариации одного сценария, а три разных:

1. Задача выполняется целиком — подзадач нет.
2. Задача разбивается на подзадачи, каждая обрабатывает один бизнес-объект.
3. Задача разбивается на группы подзадач, чтобы один раз сходить во внешнюю систему за данными
   сразу для всей группы, а не дёргать её на каждый объект.

Форму выбирает потребитель, по типу задачи. Нужно решить, как это выражается в API.

## Рассмотренные варианты

### A. Один контракт с необязательными методами — отвергнуто

`TaskProcessor` с методами `process`, `expand`, `expandBatch`, из которых часть имеет пустую
реализацию по умолчанию.

Отвергнуто: контракт перестаёт быть контрактом. По сигнатуре нельзя понять, что обязан реализовать
потребитель, а ошибка — забытый `expand` у задачи с подзадачами — обнаруживается в рантайме,
на первой задаче, а не при компиляции.

### B. Три независимых интерфейса — отвергнуто

`SimpleTaskProcessor`, `UnitTaskProcessor`, `BatchTaskProcessor` без общего предка.

Отвергнуто: не остаётся типа, которым можно объявить реестр. Воркер получает `List<Object>`
и разбирает его через `instanceof` с обязательной веткой «неизвестный тип», которая по построению
недостижима, но написать её придётся.

### C. Запечатанная иерархия — выбрано

```java
sealed interface TaskProcessor<P>
        permits SimpleTaskProcessor, UnitTaskProcessor, BatchTaskProcessor
```

Общий тип для реестра есть, при этом множество наследников закрыто, и компилятор это знает.

## Решение

Выбран вариант **C**. Воркер разбирает иерархию через pattern matching **без ветки `default`**:

```java
switch (processor) {
    case SimpleTaskProcessor<?> p -> ...
    case UnitTaskProcessor<?, ?> p -> ...
    case BatchTaskProcessor<?, ?, ?> p -> ...
}
```

Отсутствие `default` — не стилистика, а механизм: добавление четвёртого контракта должно **ломать
компиляцию** во всех местах, которые надо дописать. Для библиотеки, где забытая ветка проявится
у потребителя, а не у нас, это правильный размен.

Реестр процессоров строится при старте приложения из `List<TaskProcessor<?>>`. Два процессора
с одинаковым `taskType()` — **падение при старте**, а не при первой задаче через неделю.

## Последствия

- Потребитель реализует **одного из наследников**, а не базовый `TaskProcessor`: он запечатан.
- Параметры типа различаются по контрактам: `SimpleTaskProcessor<P>`, `UnitTaskProcessor<P, U>`,
  `BatchTaskProcessor<P, B, U>`. Это прямое следствие того, что нагрузки на уровнях иерархии
  разного типа ([0003](0003-domain-naming.md)).
- Добавление четвёртого контракта — заведомо заметное изменение, требующее правки всех мест
  разбора. Это плата за отсутствие `default` и она принята сознательно.
- Регистрация процессоров не требует `ImportBeanDefinitionRegistrar` и сканирования classpath:
  потребитель объявляет процессор обычным бином, Spring его находит, стартер собирает инъекцией
  списка ([0002](0002-autoconfiguration-registration.md)).
- Проверка на дублирующийся `taskType()` при старте обязательна. Без неё конфликт двух процессоров
  проявится как случайный выбор одного из них — худший вид ошибки.
