# 0088. Базовая линия — Java 25 и Spring Boot 4.1

- **Дата:** 2026-10-20
- **Статус:** принято
- **Изменено:** [0092](0092-jackson-3-liquibase-compatibility.md) — ветка Jackson и целевая
  версия Liquibase выбраны.

## Контекст

Скелет проекта собран на Java 21 и Spring Boot 3.5. Кода, кроме пустой автоконфигурации, ещё нет,
и стартер никуда не опубликован — только `publishToMavenLocal`. Значит, сейчас базовую линию можно
поднять, ничего не сломав ни одному потребителю; после первого релиза это станет мажорной версией.

Нижняя граница задана явно: **JDK 25.0.4** и **Spring Boot 4.1.1**.

Ограничения, которые нельзя обойти:

- Lombok `1.18.32` на JDK 25 не работает: поддержка начинается с `1.18.40`.
- Gradle toolchain требует только мажорную версию Java; граница патча им не выражается.
- `palantir-java-format` надёжен, только когда Gradle daemon запущен на той же версии JDK,
  что и toolchain (CLAUDE.md, «Каталог версий»).

## Рассмотренные варианты

### A. Java 25 и Spring Boot 4.1 — выбрано

Обе — актуальные ветки: Java 25 — LTS, Boot 4.1 — текущий выпуск, Boot 3.5 — последняя ветка
3.x и дальше не развивается. Стартер пишется сейчас и будет жить годами; начинать его на уходящей
ветке — значит сразу запланировать миграцию.

Минус — **потребители на Boot 3 и Java 21 подключить стартер не смогут.** Spring Boot 4 сам
требует от приложения миграции, и стартер становится доступен только тем, кто её прошёл.

### B. Остаться на Java 21 и Spring Boot 3.5 — отвергнуто

Шире круг потребителей сегодня, но переход на Boot 4 после первого релиза — мажорная версия
стартера и вторая ветка сопровождения. Поднимать базовую линию дешевле всего до релиза.

### C. Java 21 и Spring Boot 4.1 — отвергнуто

Boot 4 работает на Java 17+, так что сочетание возможно. Но LTS 25 даёт то, что пригодится
движку (виртуальные потоки без pinning на `synchronized`, JEP 491; scoped values, JEP 506),
а потребитель на Boot 4 почти наверняка уже на свежей Java. Выигрыш в охвате мал.

### Как держать границу патча

#### i. Проверка версии JVM daemon в `settings.gradle` — выбрано

Сборка падает с внятным сообщением, если Gradle запущен на JDK старше 25.0.4. Заодно закрывает
граблю `palantir-java-format`: daemon на другой мажорной версии не пройдёт проверку.

#### ii. Только toolchain `25` — отвергнуто

Пропустит 25.0.0–25.0.3, а daemon на JDK 21 с toolchain 25 соберётся и упадёт в Spotless
на ровном месте.

## Решение

- Toolchain — **Java 25**; Gradle daemon обязан работать на **JDK 25.0.4 или новее**,
  `settings.gradle` проверяет это и валит сборку.
- Spring Boot — **`4.1.1`** в каталоге версий; Spring Framework 7, JUnit Jupiter 6,
  Testcontainers 2, Jackson 3 приходят из его BOM и отдельно не пинятся — как и прежде.
- Lombok поднят до **`1.18.48`** — вынужденно, ради JDK 25. Остальные инструменты (Gradle 9.7.1,
  Checkstyle 14.0.0, Spotless 8.10.0, palantir-java-format 2.97.0, Error Prone 2.50.0,
  ArchUnit 1.5.0, MapStruct 1.6.3) остаются прежними.

## Последствия

- **Стартер требует от потребителя Spring Boot 4 и Java 25.** Это объявляется в README
  и в заметках к первой версии.
- Разработчику нужен JDK 25.0.4+ локально и в CI; JDK 21 больше не годится даже для запуска Gradle.
- **Jackson 3 вместо Jackson 2.** Boot 4 по умолчанию даёт Jackson 3 (`tools.jackson.*`), Jackson 2
  в нём оставлен для совместимости. [0012](0012-payload-storage.md) говорит «Jackson» без ветки;
  какую ветку использует сериализация нагрузки и чей маппер она берёт — решается вместе с первым
  кодом сериализации.
- **Модули Boot 4.** Автоконфигурация разнесена по модулям: JDBC, инициализация схемы
  (`DataSourceScriptDatabaseInitializer`) и Liquibase живут в отдельных `spring-boot-*`
  артефактах. Зависимости `taskcomm-autoconfigure` объявляются по этим модулям, а не одним
  `spring-boot-autoconfigure`.
- **Testcontainers 2**: другие имена артефактов модулей (`testcontainers-postgresql`);
  [0085](0085-tests-on-real-postgres.md) по существу не меняется.
- **Nullability.** Spring Framework 7 размечен JSpecify, у нас в каталоге
  `org.jetbrains:annotations`. Переходить ли — отдельный вопрос, это решение его не закрывает.
- Liquibase в BOM Boot 4.1 — ветка 5. Перед тем как везти changelog, проверить, что лицензия
  этой ветки не создаёт проблем потребителям: Liquibase у нас `optional`, но changelog в jar.
- Привязка `Execution` к потоку ([0038](0038-execution-aggregate.md)) по-прежнему через MDC-подобный
  снимок; scoped values из Java 25 этим решением не вводятся.
