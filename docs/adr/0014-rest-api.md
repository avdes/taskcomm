# 0014. REST API: состав и границы со Spring Security

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

Стартер даёт потребителю готовый REST API для управления задачами и коммуникациями. Главный вопрос,
требующий решения, — как этот API соотносится с конфигурацией безопасности потребителя: любое наше
действие здесь меняет поведение чужого приложения.

> Механизм ограничения поиска по содержимому нагрузки вынесен в отдельное решение —
> [0016](0016-payload-search.md). Здесь фиксируется только то, что такой поиск входит
> в состав API.

## Рассмотренные варианты

### A. Стартер объявляет `SecurityFilterChain` — отвергнуто

Дал бы защиту «из коробки». Отвергнуто: цепочка, объявленная стартером, либо перекрывает
конфигурацию потребителя, либо конфликтует с ней по порядку. Разбираться в этом будет человек,
который наш код не читал. Это тот же принцип, по которому запрещены `@EnableScheduling`
и `@ComponentScan` ([0002](0002-autoconfiguration-registration.md)): не менять за потребителя то,
о чём он не просил.

### B. Готовая цепочка за выключенным по умолчанию свойством — отвергнуто

Мягче варианта A, но добавляет в публичный контракт конфигурацию безопасности, которую потом
нельзя менять без мажорной версии.

### C. Не трогать Security, отдать `RequestMatcher` — выбрано

Стартер публикует бин `RequestMatcher` со своими путями. Потребитель вписывает его в свою
конфигурацию одной строкой и сам решает, кого пускать.

## Решение

Стартер **не объявляет `SecurityFilterChain` и не трогает Spring Security**, а отдаёт
`RequestMatcher` со своими путями.

Состав API: чтение (списки и детали задач, батчей, подзадач, коммуникаций с фильтрами по статусам),
поиск по содержимому нагрузки, создание задач и коммуникаций, перезапуск упавших подзадач, отмена.

**WebSocket-подписка на события отложена.** Когда дойдёт очередь: события best-effort, UI дочитывает
состояние через REST при подключении и после разрыва. Хранения недоставленных событий не будет —
это вторая очередь внутри очереди.

## Последствия

- Из коробки API **не защищён**. Потребитель, забывший вписать `RequestMatcher` в свою
  конфигурацию, откроет управление задачами наружу. Это должно быть написано в документации крупно,
  и это прямая цена варианта C.
- Пути живут под `taskcomm.rest.base-path`, вся подсистема выключается `taskcomm.rest.enabled`.
- Перезапуск упавших подзадач — не удобство, а обязательная часть продукта: статус `WARNING`
  из [0009](0009-retry-and-progress.md) существует именно ради того, чтобы к упавшему можно было
  вернуться.
- Наличие поиска по нагрузке в составе API создаёт зависимость от формата хранения: с `bytea`
  такой поиск был бы невозможен ([0012](0012-payload-storage.md)).
- Пользовательский ввод не конкатенируется в SQL — независимо от того, какой механизм ограничения
  поиска будет выбран.
