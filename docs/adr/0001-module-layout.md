# 0001. Структура модулей: autoconfigure + starter

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

`taskcomm` — не приложение, а библиотека: её подключают чужие приложения, и её главная заявленная
ценность — обратная совместимость (в [CLAUDE.md](../../CLAUDE.md): мажорная версия поднимается
только при её потере, и этого стараемся не допускать).

Отсюда требование, которого нет у обычного сервиса: должна существовать различимая граница между
**публичным API**, который потребитель видит и на который опирается, и **инфраструктурой**, которую
мы вправе переписать в любой момент. Без такой границы публичным API становится всё подряд: любой
класс, до которого потребитель дотянулся, превращается в обязательство.

Второе обстоятельство: проект начинается с нуля. Где именно пройдут границы между подсистемами
(задачи, коммуникации, REST), из проектных намерений видно лишь приблизительно — они проявятся
в коде.

## Рассмотренные варианты

### A. Один модуль

Всё в артефакте `taskcomm`: домен, реализация, REST, автоконфигурации.

Плюс: самый простой старт, один `build.gradle`, никакой Gradle-церемонии.

Минус: нет ни одной компиляторной границы. Потребитель, которому нужна только логика, всё равно
получает наш набор транзитивных зависимостей. И, что важнее, отсутствует само место, где можно
сказать «вот это публичное, а это нет».

### B. Пара `autoconfigure` + `starter` — выбран

Официальная конвенция Spring Boot, по которой устроены все стартеры самого фреймворка.

- `taskcomm-autoconfigure` — весь код и классы `@AutoConfiguration`; зависимости объявлены
  `compileOnly` / `optional`, чтобы не навязывать транзитивы.
- `taskcomm-spring-boot-starter` — модуль **без единого класса**, только список зависимостей.

Плюс: потребителю, которому нужна логика без нашего набора транзитивов, доступен `autoconfigure`;
всем остальным — стартер одной строкой. Конвенция знакома любому Spring-разработчику.

Минус: граница «публичное / внутреннее» модулями не обеспечивается — её придётся проводить
пакетами и проверять отдельно.

### C. `core` + `autoconfigure` + `starter`

То же, что B, плюс отдельный `taskcomm-core` с доменной моделью и публичными интерфейсами,
не зависящий от Spring Boot autoconfigure.

Плюс: граница публичного API становится границей артефакта, то есть проверяется компилятором
и системой сборки, а не соглашением.

Минус: лишний артефакт и лишняя церемония в момент, когда ещё неизвестно, что именно в него класть.

### D. Многомодульный по доменам

`core`, `task`, `communication`, `rest`, `autoconfigure`, `starter` — шесть артефактов.

Плюс: максимальные границы, подсистемы подключаются по отдельности.

Минус: много Gradle-церемонии на старте. Разрезать монолитный модуль на части дёшево в любой
момент; собирать шесть модулей обратно — дорого.

### Отдельно: BOM

BOM (`platform`) нужен, когда потребитель зависит напрямую от нескольких наших артефактов и должен
держать их версии согласованными. У нас потребитель берёт один стартер, который сам объявляет
версии через `api`. BOM сейчас не нужен; вернуться к нему стоит, когда появится второй независимо
подключаемый артефакт.

## Решение

Выбран вариант **B**: два модуля, `taskcomm-autoconfigure` и `taskcomm-spring-boot-starter`.
BOM не заводим.

Вариант C был предложен как компромисс (граница API проверяется сборкой), но отвергнут в пользу
меньшей церемонии на старте. Плата за это — граница публичного API держится на пакетах и на
автоматической проверке, см. [0004](0004-public-api-boundary.md).

Вариант D отвергнут по асимметрии стоимости: разделить модуль позже дёшево, объединить — дорого.

## Последствия

- **`taskcomm-spring-boot-starter` не содержит ни одного класса.** Класс, попавший в этот модуль, —
  ошибка, а не мелочь: смысл модуля в том, что он представляет собой только набор зависимостей.
- Зависимости в `taskcomm-autoconfigure` объявляются `compileOnly` / `optional`; реальные
  транзитивы собираются в стартере через `api`. Нарушение этого правила навязывает зависимость
  всем потребителям молча.
- Граница публичного API проходит **по пакетам, а не по модулям**. Это делает
  [0004](0004-public-api-boundary.md) не украшением, а необходимостью: без пакета `internal`
  и проверки границы автоматическим тестом границы не существует вообще.
- SPI хранилища живёт в `autoconfigure` вместе со всем остальным. Потребитель, которому нужны
  только интерфейсы, всё равно получает модуль целиком.
- Выделение `core` позже возможно, но это **перемещение публичных типов между артефактами** —
  ломающее изменение для всех, кто зависел от `autoconfigure` напрямую. То есть отложенный
  вариант C дешевле сегодня, но дороже завтра, и это осознанный размен.
