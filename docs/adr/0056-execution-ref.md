# 0056. Явная передача текущего `Execution`

- **Дата:** 2026-08-31
- **Статус:** принято

## Контекст

[0038](0038-execution-aggregate.md) передаёт текущий `Execution` только неявно: сервис создания
берёт его из потока, в котором работает процессор. В последствиях там же записана ловушка: задача
или коммуникация, созданная из другого потока — своего пула, `CompletableFuture`, — молча попадает
в новое дело, и связь не возникает.

[consumer-contract.md](../consumer-contract.md) при этом советует «передайте дело явно», но API
под этим советом нет: процессору неоткуда взять текущий `Execution`, а метода создания,
принимающего его, не существует.

## Рассмотренные варианты

### A. Оставить только неявную передачу — отвергнуто

Правило «создавайте сущности в потоке вызова» остаётся единственным. Дёшево, но совет «передайте
дело явно» так и остаётся ничем не обеспеченным обещанием.

### B. Переносить привязку в дочерние потоки автоматически — отвергнуто

`InheritableThreadLocal` и подобные механизмы. Пул переиспользует потоки, и унаследованная привязка
пережила бы вызов, который её породил: созданное позже тихо попадало бы в чужое дело. Это хуже
текущего состояния — сейчас связь просто не возникает, а так возникала бы неверная.

### C. Явная передача ссылки на дело — выбрано

Процессор берёт из контекста значение-ссылку и сам передаёт его туда, где создаёт.

## Решение

Две части.

**`ProcessingContext` и `CommunicationContext` получают метод `executionRef()`.** Он возвращает
`ExecutionRef` — маленькое неизменяемое значение из двух полей: `id` дела и его `createdAt`.
Второе поле не украшение: это ключ партиционирования ([0039](0039-execution-partitioning.md)),
без него строку в подчинённую таблицу не вставить. Тип живёт в `execution/api`.

**Методы создания в `TaskService` и `CommunicationService` принимают необязательный
`ExecutionRef`.** Передали — созданная сущность попадает в указанное дело, в каком бы потоке
ни происходило создание; явно переданное дело побеждает неявную привязку потока. Не передали —
всё работает по правилам [0038](0038-execution-aggregate.md).

Пример — та же ловушка из [consumer-contract.md](../consumer-contract.md), но с исправлением:

```java
@Override
public void process(TaskUnit<OrderRef> unit, ProcessingContext context) {
    // ссылка на текущее дело — обычное значение, его можно унести в другой поток
    ExecutionRef execution = context.executionRef();

    CompletableFuture.runAsync(() ->
            // передаём дело явно — коммуникация попадёт в дело текущей подзадачи,
            // хотя создаётся из другого потока
            communicationService.send("supplier-b", request, execution));
}
```

В отличие от контекста обработки, который живёт один вызов, `ExecutionRef` — обычное значение
без срока годности: дело не завершается, а старые партиции остаются записываемыми
([0039](0039-execution-partitioning.md)). Ссылку можно не только унести в другой поток,
но и сохранить у себя и передать позже.

## Последствия

- Ловушка из [0038](0038-execution-aggregate.md) сужается, но не исчезает: неявная привязка
  по-прежнему не переживает смену потока, а явную передачу можно забыть. Меняется другое —
  у совета «передайте дело явно» появляется конкретный способ.
- `ProcessingContext` целиком переносимым не становится и не станет: `skip(reason)` и признак
  «продолжать ли» принадлежат конкретной попытке и аренде и вне своего вызова смысла не имеют.
  Переносится только ссылка на дело.
- Сохранённый `ExecutionRef` может пережить свою партицию: если дело уже удалено очисткой,
  вставка по такой ссылке упадёт. Это громкая ошибка при создании, а не тихая потеря связи.
- В методах создания появляется ещё один необязательный параметр, и его придётся объяснять
  потребителю вместе с правилом «явное побеждает неявное».

## Связанные решения

- [0038](0038-execution-aggregate.md) — неявная передача и ловушка со сменой потока, которую
  это решение сужает.
- [0039](0039-execution-partitioning.md) — партиционирование: откуда в ссылке второе поле
  `createdAt`.
- [0040](0040-communication-correlation.md) — соседний механизм связи через время: для колбэков
  извне, у которых ссылки быть не может.
