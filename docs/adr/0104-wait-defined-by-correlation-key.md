# 0104. Ожидание ответа определяет ключ корреляции той же системы

- **Дата:** 2026-10-21
- **Статус:** принято

## Контекст

[0086](0086-async-response-in-outbound.md) решил, кто ждёт асинхронного ответа: исходящая
в Kafka — по умолчанию, REST, SOAP и RAW — только по явному вызову метода контекста. Вариант
«Kafka не ждёт по умолчанию» в разделе рассмотренных вариантов не разобран, а последствия 0086
признаёт сам:

- **шум.** Большая часть исходящего в Kafka — публикация событий, на которые никто не отвечает.
  Без ключа корреляции ждать нечего, и каждое такое сообщение даёт `SUCCEEDED` и WARN —
  «шумно, зато сразу видно». На потоке событий это сотни WARN в секунду, и их перестают читать
  вместе со всеми остальными;
- **повторные отправки.** Ключ зарегистрирован, «не ждать» забыто — сообщение уходит повторно
  по `response-timeout` до `max-attempts` раз;
- **асимметрия.** Один и тот же процессор, переписанный с REST на Kafka, ведёт себя иначе без
  единой правки в своём коде.

При этом 0086 же установил, что ожидание без зарегистрированного ключа невозможно в принципе:
колбэку нечем найти коммуникацию. Ключ и есть выраженное намерение получить ответ.

## Рассмотренные варианты

### A. Никто не ждёт по умолчанию, ожидание — явным методом — отвергнуто

Шума нет, правило одно для всех транспортов. Отвергнуто: забывший попросить ожидание снова
не видит неполученный ответ — дыра, которую закрывал 0086, хотя ключ он при этом завёл.

### B. Оставить как в 0086 — отвергнуто

Шум, повторные отправки по забытому «не ждать» и транспортная асимметрия остаются.

### C. Ожидание определяет зарегистрированный ключ той же системы — выбрано

Ожидание следует из действия, которое потребитель и так обязан сделать, а не из транспорта.

## Решение

- **Исходящая ждёт ответа, если у неё зарегистрирован хотя бы один ключ корреляции той же
  системы**, что её `destination`, — при создании или из `process`. Правило одно для всех
  транспортов.
- **Ключа нет — не ждёт**: успешная отправка даёт `SUCCEEDED`, без WARN.
- **Ключ зарегистрирован только под другой системой** ([0075](0075-correlation-key-scoped-by-system.md)) —
  не ждёт. Такой колбэк в исходящую не дописывается, а становится отдельной входящей в деле
  якоря (0086); ожидание кончилось бы только повторной отправкой по сроку.
- **Метод контекста один — «не ждать»**: ключ нужен, а ответа не будет. Метода «ждать» нет:
  без ключа ожидание невозможно, с ключом наступает само. Имя метода условное.
- Решение принимается по итогу `process`: исключение перебивает ожидание, как в 0086.
- Правило касается исходящих. Ключ, зарегистрированный на входящей, ожидания не включает:
  входящая ответа не ждёт.

## Последствия

- **Публикация событий в Kafka без ключа не шумит.**
- **Неполученный ответ виден у всех, кто настроил корреляцию**, независимо от транспорта.
- **Связь «зарегистрировал ключ — включил ожидание» неочевидна** и обязана быть громко описана
  в Javadoc метода регистрации ключа и в документации потребителя. Регистрация ключа «на всякий
  случай», без ответа, даёт повторные отправки по сроку — но только у тех, кто ключ правда завёл.
- **Контракт контекста проще**: один метод вместо двух, и его смысл не зависит от транспорта.
- Правило 0086 «ожидание включено, а ключ не зарегистрирован — `SUCCEEDED` и WARN» исчезает:
  такого состояния больше нет.
