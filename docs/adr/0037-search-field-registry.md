# 0037. Реестр полей поиска живёт в БД

- **Дата:** 2026-08-29
- **Статус:** принято

## Контекст

[0016](0016-payload-search.md) сделал белый список полей поиска целиком оперативным: при старте
стартер собирает `searchableTaskFields()`, `searchableBatchFields()` и `searchableUnitFields()`
со всех процессоров, проверяет на конфликты и держит результат в памяти. Реестр существует ровно
столько, сколько работает эта версия приложения.

Отсюда три следствия, все три записаны в [consumer-contract.md](../consumer-contract.md) как
ломающие изменения на стороне потребителя:

- убрать поле из белого списка — запросы по нему начинают отвергаться с `400`;
- изменить `jsonPath` или `FieldType` — поиск перестаёт находить старые записи, **молча**;
- поиск по истории работает, только пока жив объявивший её процессор.

Корень у всех трёх один. **Реестр описывает данные, которые уже записаны, а живёт в jar-нике,
который выкачен сейчас.** Описание не может быть моложе описываемого: нагрузка, записанная год
назад, лежит в форме годовой давности, и никакая правка кода этого не меняет.

Ровно эта таблица уже рассматривалась — [0029](0029-processor-never-deleted.md), вариант B,
с той же схемой `(task_type, level, name, json_path, field_type)`. Она была отвергнута
по двум причинам, и **одна из них с тех пор помечена в шапке 0029 как ошибочная**: запрет менять
`json_path` и `field_type` существует независимо от таблицы. Отказавшись от неё, мы получили тот же
запрет, только молчаливый. Вариант B этого запрета не создавал — он его **обнаруживал**.

Устояла одна причина: новая сущность в схеме ради справочника на десятки строк. Это цена,
а не возражение.

## Рассмотренные варианты

### A. Оставить реестр только в памяти — отвергнуто

Статус-кво. Ничего не стоит и оставляет все три следствия, включая молчаливое.

### B. Таблица как журнал рядом с реестром в памяти — отвергнуто

Строки пишутся, но запросы по-прежнему разрешаются по реестру в памяти. Изменения стало бы видно
при старте — и только. Убранное поле так же отвечает `400`, старые записи так же не находятся.
Запрет на удаление строк при этом ничего не охраняет: удаляй или не удаляй, на поиск это не влияет.
Механизм, который умеет пожаловаться, но не умеет помочь.

### C. Ключ записи — `(уровень, тип задачи, имя поля)`, изменения обновляют строку — отвергнуто

Естественное первое прочтение: путь и тип значения — это «значение» при ключе из имени.

Отвергнуто, потому что обновление **затирает описание уже записанных данных описанием ещё
не записанных**. Поменяли `$.orderId` на `$.order.id` — строка одна, путь в ней новый, и миллион
старых нагрузок перестаёт находиться. Это ровно та молчаливая поломка, ради устранения которой
таблица и заводится. Громкий WARN при обновлении делает её шумной, но не устраняет.

### D. Запись отождествляется сигнатурой объявления — выбрано

Всё, что определяет **как данные находятся**, — `(name, jsonPath, type)` — отождествляет запись
целиком, всеми тремя сразу. Разделения на «ключ» и «значение» внутри сигнатуры нет.

Тогда смена пути или типа значения — не правка записи, а **новое объявление**. Старое остаётся,
потому что старые нагрузки ему по-прежнему соответствуют.

Обновление при этом не исчезает — оно перемещается туда, где безопасно: на атрибуты, которые
про данные ничего не утверждают. Подпись и описание поля для UI можно править сколько угодно,
и правка не порождает новой записи (см. «Сигнатура и оформление» ниже).

## Решение

Реестр полей поиска — **таблица `tc_searchable_field`**, непартиционированная, как
`tc_communication_dedup` ([0020](0020-partitioning.md)): справочник на десятки строк, временного
измерения у него нет и дропать в нём нечего.

```sql
CREATE TABLE tc_searchable_field (
    id                 uuid        NOT NULL PRIMARY KEY,
    created_at         timestamptz NOT NULL,
    updated_at         timestamptz NOT NULL,
    level              text        NOT NULL CHECK (level IN ('TASK', 'BATCH', 'UNIT')),
    task_type          text        NOT NULL,
    field_name         text        NOT NULL,
    field_type         text        NOT NULL CHECK (field_type IN ('STRING', 'NUMBER')),
    json_path          text        NOT NULL,
    field_title        text,
    field_description  text,
    last_declared_at   timestamptz NOT NULL,
    UNIQUE (level, task_type, field_name, field_type, json_path)
);
```

`level` и `field_type` — `text` с `CHECK`, а не нативный enum
([0036](0036-enumerated-columns.md)).

### Сигнатура и оформление — разные части строки

Уникальный индекс покрывает `level`, `task_type`, `field_name`, `field_type` и `json_path`
и **намеренно не покрывает** `field_title` и `field_description`. Граница проходит по вопросу,
на который отвечает колонка:

- **Сигнатура — всё, что определяет, как данные находятся.** Меняется только вместе с данными,
  поэтому неизменяема: другое значение — другое объявление, старая строка остаётся.
- **Оформление — то, как поле показывают человеку.** Про уже записанные нагрузки не утверждает
  ничего, поэтому **обновляется на месте**: исправленная опечатка в описании не должна порождать
  вторую строку с тем же путём и вторую одинаковую ветку в поиске.

Заполняет их потребитель, для своего UI: `field_title` — подпись поля в форме поиска,
`field_description` — пояснение. Обе колонки **необязательны**; не заполнили — UI показывает
`field_name`.

```java
public record SearchableField(
        String name, String jsonPath, FieldType type, String title, String description) {

    public static SearchableField string(String name, String jsonPath) { ... }
    public static SearchableField string(String name, String jsonPath, String title) { ... }
    public static SearchableField string(String name, String jsonPath,
                                         String title, String description) { ... }
    // то же для number(...)
}
```

Перегрузки нарастают по одной, а не «всё или ничего»: подпись без описания — самый частый случай
(форме нужна метка, пояснение нужно не всякому полю), и заставлять писать `null` третьим
аргументом ради этого не за что.

Чтобы оформление было чем прочитать, REST отдаёт **список полей, доступных для поиска**, — иначе
эти колонки некому показать и они были бы write-only.

### Порядок при старте

1. Стартер собирает объявления всех процессоров **в памяти**. Конфликтовать им больше не о чем:
   два объявления с разными путями или разными типами значения — это просто два объявления.
   Проверяется только форма самого объявления: непустое имя, разбираемый путь. Дубль `taskType`
   по-прежнему роняет приложение, но это проверка реестра процессоров, а не полей
   ([0007](0007-processor-contracts.md)).
2. Реестр синхронизируется в таблицу.
3. Реестр в памяти **перестаёт существовать**. Дальше единственный источник истины — таблица.

Реестр *процессоров* при этом остаётся в памяти навсегда: он нужен для диспетчеризации по
`taskType` и для восстановления Java-типа нагрузки из дженерика ([0012](0012-payload-storage.md)).
В БД уезжает только белый список полей.

### Правила синхронизации

- **Нашли строку по сигнатуре** — обновляем `last_declared_at`, а `field_title`
  и `field_description` приводим к тому, что объявлено сейчас. `updated_at` двигаем **только
  если оформление действительно изменилось** ([0033](0033-audit-timestamps.md)): колонка, свежая
  после каждого старта, не значит ничего. `last_declared_at` при этом двигается всегда — он ровно
  про «видели живым», а не про изменение.
- **Не нашли** — вставляем.
- **Не удаляем.** Строка, которую больше не объявляет ни один процессор, продолжает обслуживать
  поиск по старым записям.

Исключение — свойство:

```yaml
taskcomm:
  search:
    remove-undeclared-fields: false   # по умолчанию
```

Включённое, оно удаляет ровно те строки, которых нет в текущем реестре, и печатает каждую удалённую
строку отдельным WARN. Выключено по умолчанию по той же причине, что и удаление партиций
([0020](0020-partitioning.md)): удаление чужих данных не должно происходить оттого, что кто-то
обновил версию зависимости.

### Разбор поискового запроса

Имя поля разрешается по таблице, а не по реестру в памяти, — запросом на каждый поиск, без кеша.
Таблица маленькая, лишний roundtrip теряется на фоне самого поиска, зато правка реестра руками
действует сразу, без перезапуска приложения.

Запрос по имени разворачивается в `OR` по **всем** строкам с этим именем — по всем типам задач
и всем путям, которые когда-либо объявлялись:

```sql
WHERE (task_type = 'order-change' AND payload->>'orderId'    = :v)
   OR (task_type = 'order-change' AND payload#>>'{order,id}' = :v)   -- прежний путь того же типа
   OR (task_type = 'order-cancel' AND payload->>'orderId'    = :v)
```

Ветка, чей `field_type` не принимает переданное значение, отбрасывается. Отброшены все — `400`.

## Последствия

- **Правило «одно имя поля — один `FieldType`» снято целиком**, а не сужено до реестра в памяти.
  Реестр описывает данные, записанные в разное время и в разной форме; правило, запрещающее
  у одного имени два типа значения, запрещало бы описывать то, что уже лежит в БД. Ронять
  приложение при старте на этом больше не за что.
- Практически расхождение типов будет редким: `payload->>'x'` отдаёт `text`, а поиск по
  идентификатору — сравнение строк, так что подавляющее большинство объявлений окажется `STRING`.
  `NUMBER` нужен там, где сравнение действительно числовое. Именно поэтому запрет, снятый здесь,
  почти ничего и не охранял.
- `FieldType` при этом **не становится декоративным**: он задаёт и вид сравнения в SQL,
  и выражение индекса. Индекс по `((payload->>'amount'))` не обслужит ветку с приведением
  к `numeric` — это разные индексы, и в печатаемом DDL они разные.
- **У одного имени поля может быть разная подпись в разных типах задач.** Это не конфликт,
  а данные: строки принадлежат разным типам, и потребитель назвал их так, как назвал. Стартер
  победителя не выбирает — отдаёт строки как есть, а как их сгруппировать в форме поиска, решает
  UI. Молча взять «последнюю объявленную» было бы хуже: подпись менялась бы от порядка старта.
- **Локализации нет** — одна подпись и одно описание, на том языке, на котором их написали.
  Колонка на локаль превратила бы справочник в таблицу переводов; кому нужен i18n, тот ключует
  свой словарь по `field_name`, который для этого и стабилен.
- **Оформление строк, которые больше никто не объявляет, замирает** на последнем объявленном
  значении. Живого объявления нет, брать новое неоткуда — а поиск по такой строке работает
  по-прежнему.
- Появляется REST-эндпоинт со списком полей, доступных для поиска. Без него `field_title`
  и `field_description` были бы write-only, а форму поиска потребителю пришлось бы верстать
  по исходникам своих процессоров.
- **Реестр растёт монотонно.** Опечатка в `jsonPath`, замеченная через день, оставляет строку
  навсегда — если не включить удаление. Тот же характер, что у монотонно растущего реестра
  процессоров ([0029](0029-processor-never-deleted.md)), и та же природа: справочник описывает
  историю, а история не сокращается.
- **`remove-undeclared-fields` делает ровно то, что написано, и это ответственность потребителя.**
  Строка описывает уже записанные нагрузки, поэтому её удаление означает одно: поиск по этому полю
  перестаёт находить старые записи. Сами нагрузки не трогаются — удаляется описание, а не данные,
  и вернуть строку дёшево: снова объявить поле в процессоре и перезапуститься, сигнатура та же.
  Выключено по умолчанию не потому, что операция опасна, а потому, что удаление не должно
  происходить оттого, что кто-то обновил версию зависимости — тот же принцип, что у выключенного
  удаления партиций ([0020](0020-partitioning.md)).
- **Циклического удаления при rolling update не возникает.** Инстансы старой версии только
  гасятся, а удаление происходит при старте: первый новый инстанс вычищает лишнее один раз, для
  остальных таблица уже актуальна. Внутри окна выкатки есть короткая несогласованность — строки
  уже удалены, а инстансы старой версии ещё живы и разрешают поиск по той же таблице, поэтому
  по удалённым полям отвечают `400` до конца выкатки. Постоянное расхождение возможно там, где
  два набора объявляются подолгу: canary, blue-green и два приложения на одной схеме
  ([0027](0027-schema-ownership.md)).
- **[0027](0027-schema-ownership.md) «одна схема — одно приложение» становится несущим для
  удаления.** Приложение с урезанным набором процессоров, стартующее на общей схеме, вычистит
  чужие строки. Нарушение 0027 по-прежнему не обнаруживается автоматически, а цена ошибки выросла.
- **Каждому уникальному пути нужен свой частичный индекс, навсегда.** Проверка индексов при старте
  теперь идёт по таблице, а не по реестру в памяти, и печатает DDL в том числе для путей, которых
  уже никто не объявляет. Это шумно, и это правильно: без индекса поиск по истории пойдёт
  последовательным сканированием.
- **Ветки запроса шире.** На одно имя теперь приходится столько веток, сколько было объявлений,
  а не типов задач. Цена та же, что признана приемлемой в 0016, только множитель больше.
- **`updated_at` в этой таблице почти неподвижен**: строка после вставки не меняется.
  «Когда это объявление видели живым» — отдельная колонка `last_declared_at`, ровно по тому же
  соображению, по которому heartbeat не трогает `updated_at` ([0033](0033-audit-timestamps.md)):
  колонка, которая свежая всегда, не значит ничего.
- **Стартер начинает писать в БД при старте.** Раньше он на старте только читал — проверял схему
  и индексы. Права на запись у него и так есть (партиции, [0020](0020-partitioning.md)),
  но точка отказа новая.
- **Из [consumer-contract.md](../consumer-contract.md) уходят два ломающих изменения из восьми.**
  Убрать поле из белого списка больше не ломает поиск; сменить `jsonPath` или `FieldType` — тоже,
  и это перестаёт быть молчаливым. Взамен появляется одно новое обязательство: не включать
  `remove-undeclared-fields`, не понимая последствий.
- **[0029](0029-processor-never-deleted.md) сохраняет решение и теряет одно из двух дополнительных
  обоснований.** Поиск по истории живого процессора больше не требует. Главная причина не менялась
  и здесь ни при чём: процессор — исполнитель, без него незавершённую задачу некому доработать,
  а упавшую подзадачу некому перезапустить. Восстановление Java-типа нагрузки
  ([0012](0012-payload-storage.md)) остаётся второй, производной причиной.
- Новая сущность в схеме ради справочника на десятки строк — единственное уцелевшее возражение
  варианта B из 0029. Принимается как цена.

## Связанные решения

- [0016](0016-payload-search.md) — механизм белого списка, чей носитель здесь меняется.
- [0029](0029-processor-never-deleted.md) — где эта таблица была отвергнута как вариант B.
- [0012](0012-payload-storage.md) — Java-тип нагрузки из дженерика: вторая причина не удалять
  процессор, после главной — что выполнять задачу иначе некому.
- [0027](0027-schema-ownership.md) — одна схема на одно приложение, предпосылка удаления строк.
- [0033](0033-audit-timestamps.md) — почему `last_declared_at` отдельно от `updated_at`.
- [0036](0036-enumerated-columns.md) — `text` с `CHECK` для `level` и `field_type`.
- [0020](0020-partitioning.md) — непартиционированная таблица-справочник и выключенное
  по умолчанию удаление.
