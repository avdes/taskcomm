# 0040. Реестр корреляции коммуникаций

- **Дата:** 2026-08-29
- **Статус:** принято

## Контекст

Сценарий асинхронной интеграции, ради которого заведён [0038](0038-execution-aggregate.md):
отправили исходящую коммуникацию, получили синхронный ответ «принято в обработку», результат
прилетает через час в REST-контроллер потребителя.

Родительской ссылки для этого недостаточно. Ссылка предполагает, что тот, кто создаёт новую
сущность, знает родителя, — а контроллер, принявший колбэк, не знает ничего, кроме содержимого
сообщения. Единственное, что у него есть, — идентификатор, по которому внешняя система связала
запрос и ответ. Значит нужен **поиск по этому идентификатору**, то есть реестр.

Искать по самой `tc_communication` нельзя. Она партиционирована по `execution_created_at`
([0039](0039-execution-partitioning.md)), а в запросе колбэка ключа партиционирования нет
и взяться ему неоткуда: мы как раз и пытаемся выяснить, к какому агрегату относится сообщение.
Отсечение партиций не сработает, и лукап пойдёт по всем партициям сразу — по таблице
в сотни миллионов строк.

## Рассмотренные варианты

### A. Колонка `correlation_id` в `tc_communication` — отвергнуто

Самое дешёвое: одна колонка и индекс по ней.

Отвергнуто дважды. Лукап по партиционированной таблице без ключа партиционирования обходит все
партиции — та же причина, по которой дедупликация не живёт в `tc_communication`
([0020](0020-partitioning.md)). И уникальность на партиционированной таблице требует включить
ключ партиционирования в индекс, после чего уникальность исчезает полностью.

### B. Расширить `tc_communication_dedup` вторым назначением — отвергнуто

Обе таблицы выглядят одинаково — «внешний ключ → коммуникация», обе непартиционированы, и соблазн
слить их велик.

Отвергнуто, потому что механизмы **противоположны по действию**. Дедупликация существует, чтобы
второй строки **не появилось**: повторная доставка гасится через `ON CONFLICT DO NOTHING`
([0011](0011-communication-model.md)). Корреляция существует, чтобы вторая строка **обязательно
появилась** и встала на своё место. В общем пространстве имён колбэк был бы проглочен как дубль
исходного запроса — то есть ровно тот сценарий, ради которого всё затевалось, сломался бы молча.

### C. Отдельная непартиционированная таблица — выбрано

## Решение

Таблица **`tc_communication_correlation`**, непартиционированная:

```sql
CREATE TABLE tc_communication_correlation (
    id                    uuid        NOT NULL PRIMARY KEY,
    created_at            timestamptz NOT NULL,
    updated_at            timestamptz NOT NULL,
    correlation_id        text        NOT NULL UNIQUE,
    communication_id      uuid        NOT NULL,
    execution_id          uuid        NOT NULL,
    execution_created_at  timestamptz NOT NULL
);
```

`execution_created_at` хранится здесь намеренно: он даёт ключ отсечения партиций и для перехода
к якорной коммуникации, и для вставки новой. Одного индексного доступа хватает, чтобы узнать
и родителя, и агрегат, — заходить в партиционированную таблицу за этим не нужно вовсе.

Колонка названа `correlation_id`, а не `correlation_key`: в API потребителя это `correlationId`,
и имя должно совпадать через все слои. Сосед `dedup_key` остаётся как есть — его в публичном API
нет.

### Регистрация ключа

Два пути, оба у потребителя:

1. **При создании коммуникации** — необязательным параметром, когда ключ известен заранее
   (мы сами его сгенерировали и положили в исходящее сообщение).
2. **Из процессора по ходу обработки** — когда ключ вернула внешняя система в синхронном ответе
   («принято, ref=Y»). Это самый частый случай в реальных интеграциях.

**Реестр накапливает.** Регистрация нового ключа не снимает прежние: колбэк, уже улетевший наружу
со старым ключом, обязан найти дорогу обратно. У одной коммуникации может быть несколько ключей,
и это нормальное состояние.

**Колонки `correlation_id` на самой коммуникации нет.** Она была бы вторым источником истины
о том же факте. Побочный, но важный эффект: без колонки «перетереть ключ» вырождается в «добавить
ещё один» — то есть в безопасное действие. Перетирать нечего.

### Приём коммуникации с ключом

- Ключ **известен** — новая коммуникация становится дочерней от найденной и попадает **в её**
  `Execution`.
- Ключ **неизвестен** — обычное создание, новый `Execution`.
- Ключ известен, но якорная строка не найдена (партиция дропнута) — новый `Execution` и WARN
  ([0039](0039-execution-partitioning.md)).
- Тот же ключ регистрирует другая коммуникация — якорь **не меняется**, пишется WARN. Первая
  регистрация выигрывает: переезд якоря увёл бы уже улетевшие колбэки в другой агрегат.

## Последствия

- **«Текущего ключа» у коммуникации не существует.** REST отдаёт список ключей, а не значение.
  Потребителю, привыкшему к одному полю, это придётся объяснить.
- **Дедупликация и корреляция остаются двумя таблицами**, и сливать их нельзя, как бы похоже они
  ни выглядели. Это первое «улучшение», которое предложит любой, кто увидит схему впервые.
- **Реестр не чистится сам по себе**, но обязан чиститься вместе с дропом партиции — иначе
  накопит записи, указывающие в пустоту. Это единственное место, где непартиционированная таблица
  зависит от жизненного цикла партиционированной.
- Ключ приходит из внешней системы, то есть это **чужой** идентификатор в нашем уникальном
  индексе. Внешняя система, переиспользующая номера, склеит несвязанные агрегаты. Защититься
  от этого нельзя — можно только не молчать: отсюда WARN на повторную регистрацию.
- Регистрация из процессора — ещё одна операция, которую потребитель может забыть. Забыл —
  колбэк приедет в собственный `Execution`, и связь не возникнет. Ошибки не будет.
- **Ограничения скорости и порядка это не касается.** Порядок коммуникаций по-прежнему
  не гарантирован ([0011](0011-communication-model.md)): колбэк может опередить завершение
  исходящей коммуникации, и обработчик обязан быть к этому готов.
