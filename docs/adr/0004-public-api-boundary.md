# 0004. Граница публичного API: пакет `internal` + ArchUnit

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

В [0001](0001-module-layout.md) выбрана двухмодульная структура, где `core` не выделен. Значит
граница между публичным API и внутренней реализацией **не обеспечивается системой сборки** — её надо
провести чем-то другим.

Без такой границы публичным API становится всё: любой класс, до которого дотянулся потребитель,
превращается в обязательство, а его изменение — в мажорную версию. Для библиотеки, чья главная
ценность — обратная совместимость, это неприемлемо.

## Рассмотренные варианты

### A. Пакет `internal`

`xyz.avasilev.taskcomm.task.internal.*`. Граница видна прямо в строке импорта у потребителя.

Плюс: дёшево, читаемо, не требует зависимостей.
Минус: сама по себе — только договорённость, компилятор её не проверяет.

### B. ArchUnit-тест

Тест, который падает, если кто-то импортировал `internal` извне своей подсистемы.

Плюс: превращает договорённость в падающий билд.
Минус: защищает только нас от самих себя — потребителя ничто не останавливает.

### C. `@ApiStatus.Internal` из `org.jetbrains:annotations`

IDE потребителя подсвечивает использование предупреждением.

Плюс: единственный вариант, который вообще что-то говорит потребителю.
Минус: только подсказка, плюс лишняя зависимость в публичном API.

### D. Package-private видимость

Настоящая защита компилятором.

Минус: требует, чтобы классы лежали в одном пакете, что конфликтует со слоистой структурой.
Применимо точечно, не как общий механизм.

### E. `module-info.java` (JPMS) — отвергнуто

Единственный вариант с настоящей изоляцией на уровне JVM.

Отвергнут по двум причинам сразу. Первая: Lombok, MapStruct, Hibernate и Spring Boot fat-jar
уживаются с JPMS плохо. Вторая, решающая: подавляющее большинство потребителей запускается
с classpath, а не с module path, и изоляция там просто не включается. То есть мы заплатили бы
полную цену за защиту, которая не сработает.

## Решение

Приняты **A + B**: пакет `internal` как соглашение, ArchUnit-тест как его принудительное
исполнение.

Вариант C не принят, но и не запрещён: если однажды понадобится сделать публичным класс, который
по-хорошему должен был остаться внутренним, `@ApiStatus.Internal` — разумный способ пометить
исключение.

## Последствия

- Структура пакетов фиксирована: `<подсистема>/api` и `<подсистема>/internal`.
  **Публичный API — это всё, что лежит вне `internal`.**
- ArchUnit-тест обязателен и проверяет три правила: пакеты `internal` не импортируются извне своей
  подсистемы; `api` не зависит от `internal`; в `internal` нет стереотипных аннотаций Spring
  (последнее — из [0002](0002-autoconfiguration-registration.md)).
- Javadoc обязателен для всего вне `internal` — если тип публичный, у него есть контракт,
  а контракт должен быть написан.
- Изменение сигнатуры типа вне `internal` — ломающее изменение. Прежде чем менять, положено
  предложить вариант с сохранением совместимости: перегрузка, `default`-метод, новый тип.
- Ничто не мешает потребителю импортировать `internal` — там нет компиляторной преграды.
  Мы полагаемся на то, что явное слово `internal` в импорте достаточно красноречиво, и **не несём
  обязательств совместимости** перед тем, кто это проигнорировал.
