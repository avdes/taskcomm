# 0075. Ключ корреляции уникален в пределах внешней системы

- **Дата:** 2026-10-15
- **Статус:** принято

## Контекст

[0040](0040-communication-correlation.md) завёл реестр корреляции `tc_communication_correlation`
с уникальным индексом `(correlation_id)` на всю схему. Дедупликация при этом разделена
по системам — `(source, dedup_key)` ([0011](0011-communication-model.md)).

Ключ корреляции — **чужой** идентификатор: номер, который выдала внешняя система. Номера внешних
систем — обычно их собственные последовательности, и у двух поставщиков «12345» совпадёт легко.
Тогда первая регистрация выигрывает: вторая система получит при регистрации WARN, а её колбэк
молча найдёт якорь **первой** системы и встанет в чужое дело. 0040 сам называет этот риск —
«внешняя система, переиспользующая номера, склеит несвязанные агрегаты», — но внутри одной
системы. Между системами коллизия куда вероятнее, а лечится дёшево.

## Рассмотренные варианты

### A. Глобальная уникальность, ключи делает уникальными потребитель — отвергнуто

Схема не меняется, потребитель добавляет к ключу префикс системы. Отвергнуто: забытый префикс —
тихая склейка дел, и WARN получает тот, кто регистрировал вторым, а не колбэк, который потом уходит
не туда.

### B. Уникальность `(система, ключ)`, система — внешняя сторона якоря — отвергнуто

Регистрация пишет `destination` исходящей, лукап колбэка ищет по `source` входящей. Отвергнуто:
ломается, когда колбэк приходит под **другим** именем системы. Отправили по REST, результат пришёл
через Kafka — по [0052](0052-communication-transport-contracts.md) это два процессора, то есть два
имени.

### C. Как B, но пространство ключа можно задать явно — выбрано

## Решение

В `tc_communication_correlation` добавляется колонка **`external_system`** — имя внешней системы,
от которой ожидается колбэк с этим ключом. Уникальный индекс — **`(external_system, correlation_id)`**
вместо `(correlation_id)`.

- **Регистрация** — при создании коммуникации и из процессора ([0040](0040-communication-correlation.md)) —
  принимает необязательное имя системы. Не передали — берётся внешняя сторона якоря: `destination`
  у исходящей, `source` у входящей.
- **Лукап колбэка** идёт по `(source входящей, correlation_id)`. Другого источника имени у колбэка
  нет: контроллер знает, откуда пришло сообщение, и больше ничего.
- Повторная регистрация того же ключа другой коммуникацией **в пределах одной системы** — как
  и раньше: якорь не переезжает, пишется WARN.

## Последствия

- **Одинаковые номера у разных систем не склеивают дела.** Обычный случай — колбэк приходит
  от той же системы, куда ушёл запрос, — не требует от потребителя ничего.
- **Случай «ушло одним транспортом, вернулось другим»** выражается одним параметром при регистрации.
  Забыли его указать — колбэк не найдёт якорь и заведёт новое дело с WARN, как при любом
  ненайденном ключе. Это громче, чем склейка с чужим делом.
- Колонка `correlation_id` больше не уникальна сама по себе. Поиск якоря через REST по одному
  ключу, без системы, может вернуть несколько строк — это данные, а не ошибка.
- Новая колонка в справочнике, который ещё не создан: миграции не требуется.
