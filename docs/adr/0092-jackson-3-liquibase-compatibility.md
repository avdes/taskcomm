# 0092. Jackson 3 из BOM; changelog совместим с Liquibase 4 и 5

- **Дата:** 2026-10-21
- **Статус:** принято
- **Изменено:** [0096](0096-no-foreign-type-beans.md) — `JsonMapper` под квалификатором
  `@TaskcommPayloadMapper` — оговорённое исключение из правила «типы Jackson в публичный API
  не попадают»; для сигнатур Java правило в силе.

## Контекст

[0088](0088-java-25-spring-boot-4.md) подняло базовую линию до Spring Boot 4.1 и оставило
открытыми два вопроса о зависимостях, которые этот подъём поменял.

**Jackson.** [0012](0012-payload-storage.md) выбрало Jackson для нагрузки, не называя ветку:
во времена Boot 3 ветка была одна. Boot 4 по умолчанию даёт Jackson 3 — пакеты `tools.jackson.*`,
в BOM 4.1.1 это `3.1.5`. Jackson 2 (`com.fasterxml.jackson.*`, `2.21.5`) в Boot 4 оставлен только
для совместимости. Это разные пакеты, а не две версии одного API: код пишется под одну ветку.

**Liquibase.** BOM Boot 4.1.1 приводит `liquibase-core 5.0.3`, и ветка 5 распространяется под
**FSL-1.1-ALv2** (Functional Source License, которая через два года переходит в Apache 2.0).
Последний выпуск под Apache 2.0 — `4.33.0`. Стартер везёт changelog в jar
([0013](0013-database-schema.md)), а потребитель применяет его своей версией Liquibase.

Общее у обоих вопросов: зависимости у нас `compileOnly` / `optional`, к потребителю они
не приезжают. Версию, которая работает у потребителя, определяет **его** BOM. Наша версия
определяет только то, против какого API мы компилируем и на чём гоняем свои тесты.

## Рассмотренные варианты

### Jackson

#### A. Jackson 3, версия из BOM — выбрано

Ветка по умолчанию у Boot 4. Версия приходит из BOM, как Micrometer и драйвер PostgreSQL,
и не расходится с BOM потребителя.

#### B. Jackson 3 с явным пином в каталоге — отвергнуто

Ничего не даёт: у потребителя всё равно будет версия из его BOM, а наши тесты шли бы на другой.
Расхождение между тем, что проверено, и тем, что работает, — ровно то, от чего отказались
у Micrometer.

#### C. Jackson 2 — отвергнуто

Подошло бы потребителю, оставшемуся на Jackson 2 под Boot 4, но это ветка, которую Boot 4 держит
только ради миграции. Начинать на ней новый код значит сразу запланировать переход.

### Liquibase

#### i. Changelog совместим с 4.x и 5.x, зависимости нет — выбрано

Changelog пишется по схеме XSD 4.x, без возможностей, появившихся только в 5.x. Зависимости
на Liquibase у `taskcomm-autoconfigure` нет вовсе: changelog — это XML-файл, коду стартера
компилировать против Liquibase не нужно. Лицензию выбирает потребитель — своей версией Liquibase.

#### ii. Пин `4.33.0` (Apache 2.0) — отвергнуто

Понижение относительно BOM (`5.0.3`), а CLAUDE.md запрещает понижать версии зависимостей.
К тому же ничего не решает: потребителю наш пин не приезжает.

#### iii. Ветка 5.x из BOM и её возможности — отвергнуто

Потребитель, который не может принять FSL и остался на 4.x, потерял бы путь через Liquibase,
и у него остался бы только голый DDL.

## Решение

- Сериализация нагрузки и результатов — **Jackson 3** (`tools.jackson.*`). Версия приходит
  из BOM Spring Boot, в каталоге не пинится. Jackson 2 в коде стартера не используется.
- Changelog **совместим с Liquibase 4.x и 5.x**: схема XSD 4.x, без возможностей только из 5.x.
- **У `taskcomm-autoconfigure` нет зависимости на Liquibase** — ни `compileOnly`, ни `optional`.
  В тестах Liquibase подключается только как `testImplementation`, версия из BOM.

## Последствия

- Потребитель, у которого под Boot 4 остался только Jackson 2, стартер не запустит: нужен
  Jackson 3 на classpath. В Boot 4 он есть по умолчанию.
- Типы Jackson в публичный API не попадают: смена ветки снова была бы ломающим изменением.
- Тесты идут на Liquibase 5 из BOM, и совместимость с 4.x ими **не проверяется**. Отказ
  от возможностей 5.x держится на дисциплине и ревью. Понадобится гарантия — отдельный прогон
  на 4.33.0 только в тестах; это не нарушает запрет на понижение, потому что к потребителю
  не приезжает.
- Если Liquibase после 4.x поменяет формат changelog несовместимо, это решение придётся
  пересмотреть.
- Вывод из лицензии FSL делаем мы, а не юрист. Если потребителю нужна определённость, это его
  проверка.
