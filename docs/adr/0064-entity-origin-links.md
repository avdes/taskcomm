# 0064. Связи между сущностями: указатель на создателя

- **Дата:** 2026-09-29
- **Статус:** принято

## Контекст

Вопрос стоял открытым с появления агрегата ([0038](0038-execution-aggregate.md)) и был
единственным, который блокировал схему БД. Формулировался он так: заводить ли closure table
под цепочку `Execution → Communication → Task → TaskBatch → TaskUnit → Communication`, и попадает
ли в неё иерархия задач или только межсущностные связи.

Разбор начали заново, с двух списков — фактических связей и сценариев их использования.

**Кто кого может породить** (всюду `N >= 0`):

| Создатель | Что создаёт |
|---|---|
| `Communication` | `Communication`, `Task` |
| `Task` | `Task`, `TaskBatch`, `TaskUnit`, `Communication` |
| `TaskBatch` | `TaskUnit`, `Task`, `Communication` |
| `TaskUnit` | `Task`, `Communication` |

Плюс связь «брат-брат» у асинхронных коммуникаций: колбэк отвечает на конкретную исходящую.

**Сценарии:**

1. Визуализация всего исполнения — графическая или псевдографическая.
2. Все коммуникации исполнения с заданным `source` / `destination`, по дате — чтобы посмотреть
   результат и решить, нужна ли повторная коммуникация.
3. Коммуникации по параметру **вне зависимости от исполнения**, затем связанные с ними задачи —
   то же решение о повторе.
4. Задача в исполнении по типу или параметрам, по дате — чтобы перезапустить её или взять её
   результат в расчёт другой задачи того же исполнения.

Ключевое наблюдение: **ни один сценарий не является обходом графа.** Все четыре — это фильтр
внутри одного `Execution` либо глобальный поиск, после которого читается `Execution`.
Транзитивных запросов вида «все потомки на любой глубине» нет ни одного.

Причина, по которой вопрос выглядел тяжёлым, — в его формулировке: он спрашивал, как хранить граф,
тогда как хранить надо было ответы на четыре запроса.

## Рассмотренные варианты

### Что вообще хранить

#### A. Closure table со всей иерархией задач — отвергнуто

Транзитивное замыкание всех связей, включая `Task → TaskBatch → TaskUnit`.

Отвергнуто тремя независимыми доводами.

Транзитивность никому не нужна: `Execution` **и есть** замыкание — ради этого он и заводился.
Closure стал бы вторым, более дорогим ответом на вопрос, на который `execution_id` отвечает одним
переходом.

Иерархия задач уже записана **трижды**: `parent_attempt_id` как признак принадлежности актуальному
набору детей ([0047](0047-children-belong-to-attempt.md)), `task_id` и `batch_id` — ради публичного
API и REST-фильтров ([0022](0022-batch-data-placement.md)). Четвёртая копия появилась бы ровно там,
где идёт пачечная вставка при раскрытии.

И цена: closure со self-строками даёт порядка четырёх миллионов связей на миллион подзадач,
а проверка `EXISTS` завершённости детей ушла бы с индекса `(parent_attempt_id, status)` в чужую
таблицу — то есть самый горячий агрегат стал бы дороже.

#### B. Closure table только межсущностных связей — отвергнуто

Иерархия остаётся где была, замыкание строится по остальным связям.

Отвергнуто: у межсущностных связей глубина почти всегда один-два перехода, и обходить это
замыкание всё равно некому — см. довод про сценарии. Платить таблицей за транзитивность,
которой никто не пользуется, не за что.

#### C. Таблица рёбер только межсущностных связей — отвергнуто

Adjacency вместо closure: одна строка на связь, партиционируется по `execution_created_at`
наравне с остальными.

Выигрыши надо назвать, они настоящие: все рёбра исполнения читаются одним запросом, а не
собираются из четырёх наборов строк; предметные таблицы остаются без полиморфного указателя;
и связь N:M становится возможной, если однажды понадобится.

Отвергнуто потому, что **связь функционально N:1**. У каждой сущности ровно один создатель — тот,
чья обработка шла в момент создания; контекст обработки один, двух родителей взяться неоткуда.
Таблица связей — нормальная форма для N:M, а для N:1 она означает лишнюю строку и лишнюю запись
ради факта, который помещается в ту же строку, что уже пишется. Это тот же размен, что
в [0055](0055-communication-exchange-storage.md): обмен лёг колонками в строку попытки именно
потому, что связь 1:1 по построению. Плюс девятая партиционированная таблица, которую надо дропать
согласованно с остальными.

#### D. Указатель на создателя в строке ребёнка — выбрано

Ребёнок хранит, кем создан. Ни новой таблицы, ни новых строк, ни новых записей.

### Куда ставить указатель

#### E. Во все четыре подчинённые таблицы — отвергнуто

Единообразно, но бессмысленно: по [0038](0038-execution-aggregate.md) `TaskBatch` и `TaskUnit`
рождаются **только** внутри `expand` / `expandBatch`, и их создатель уже выражен
`parent_attempt_id`. Колонки на миллионных таблицах хранили бы третью копию того же факта.

#### F. Только в `tc_task` и `tc_communication` — выбрано

Те же две таблицы, где живёт `cancel_requested_at` ([0041](0041-cancellation-on-root.md)), и по той
же причине: только там сущность может появиться сама по себе, вне раскрытия.

### На что указывать

#### G. Только на сущность-создателя — отвергнуто

Задача перезапущена, первая попытка создала одну коммуникацию, вторая — другую. Обе повиснут
на задаче без различия. Это ровно та неоднозначность, которую
[0047](0047-children-belong-to-attempt.md) счёл достойной исправления для детей раскрытия.

#### H. Только на попытку-создателя — отвергнуто

Точно, но недостаточно: чтобы назвать создателя, нужен переход в таблицу попыток, а у колбэка
попытки нет вовсе — его создаёт контроллер потребителя, а не процессор.

#### I. На сущность, с уточнением попыткой — выбрано

Сущность названа прямо, попытка — когда это было.

## Решение

В `tc_task` и `tc_communication` добавляются четыре колонки:

```sql
origin_type       text NULL CHECK (origin_type IN ('TASK', 'BATCH', 'UNIT', 'COMMUNICATION')),
origin_id         uuid NULL,
origin_attempt_id uuid NULL,
origin_relation   text NULL CHECK (origin_relation IN ('SPAWNED', 'RESPONSE'))
```

Значения `origin_type` совпадают с `level` в `tc_task_attempt` ([0044](0044-attempt-log.md))
и дополнены `COMMUNICATION`: словарь уровней в проекте уже есть, второго завести нельзя.

Имя `origin_*`, а не `source_*`: `source` у коммуникации занят внешней системой. И не
`created_by_*`: читается как аудит «кем из пользователей создано».

### Когда заполняется

- **`SPAWNED`** — сущность создана вызовом из процессора. `origin_attempt_id` — попытка, в ходе
  которой это произошло.
- **`RESPONSE`** — входящая коммуникация-колбэк, чей ключ корреляции нашёл якорь
  ([0040](0040-communication-correlation.md)). `origin_type` всегда `COMMUNICATION`,
  `origin_attempt_id` пуст: колбэк создаёт контроллер, попытки за ним нет.
- **Все четыре колонки пусты** — корень: создано из кода потребителя вне процессора.

`origin_type`, `origin_id` и `origin_relation` заполняются и пустуют только вместе.
Детей раскрытия эти колонки не касаются вовсе: у них нет ни одной такой записи.

### Связь не выходит за исполнение

Потребитель отказался от привязки или явно передал `ExecutionRef` другого дела
([0056](0056-execution-ref.md)) — **`origin_*` не заполняется**. Иначе указатель переживал бы дроп
партиции своей цели, а причинной связи между агрегатами в модели нет.

Отсюда инвариант, на который можно опираться: **создатель всегда лежит в той же партиции, что
и ребёнок.** Значит чтение создателя по `(execution_created_at, origin_id)` идёт с отсечением
партиций — в отличие от лукапа по `request_id` ([0055](0055-communication-exchange-storage.md)),
который обходит все.

### Брат-брат — это вид связи, а не вторая структура

В хранении разницы нет: колбэк — направленное ребро к исходной коммуникации, отличается только
значением `origin_relation`. Рисовать его сбоку или снизу — решение отрисовки. Отдельного
механизма под сиблингов не заводится, и `tc_communication_correlation` остаётся тем, чем был
по [0040](0040-communication-correlation.md): поиском якоря по чужому ключу, а не хранилищем ребра.
Само ребро 0040 подразумевал словами «становится дочерней от найденной», но нигде не записывал —
здесь у него появляется колонка.

### Индексов не добавляется

«Задачи, созданные этой коммуникацией» берутся чтением дела и фильтром по `origin_id` в памяти:
в исполнении десятки сущностей кроме детей раскрытия, а у тех `origin_*` пуст. Понадобится —
`(origin_id)` добавляется аддитивной миграцией.

### Что это даёт сценариям

| Сценарий | Чем обслуживается |
|---|---|
| 1. Визуализация | четыре таблицы по `(execution_id)` + `parent_attempt_id` + `origin_*` |
| 2. Коммуникации дела по `source` / `destination` | `WHERE execution_id = ?`, фильтр и сортировка в памяти |
| 3. Коммуникации по параметру → связанные задачи | поиск → `execution_id` → задачи, при нужде `origin_id` |
| 4. Задача дела по типу → её результат | `WHERE execution_id = ? AND task_type = ?` + [0058](0058-task-result-storage.md) |

Связи из четырёх сценариев нужны **одному**. Остальные три обслуживаются агрегатом и уже
обязательным индексом `(execution_id)`.

### Публичный API

Указатель виден потребителю: в REST-выдаче дела и в публичном типе — необязательным значением
`Origin` (тип создателя, id, попытка, вид связи). Точный состав методов — этап 2 плана работ.

### Закрывается и открытый вопрос 4

«Как процессор добирается до данных породившей его коммуникации» закрывается тем же указателем.
Задача, созданная процессором входящей коммуникации, знает её прямо: `origin_id` плюс собственный
`execution_created_at` дают чтение с отсечением партиций, а `request_id` и весь обмен лежат
в строке попытки этой коммуникации ([0055](0055-communication-exchange-storage.md)).
Неоднозначности, которой боялись при обходе через состав дела, не возникает вовсе: создатель
назван, а не угадывается по имени внешней системы.

Путь через нагрузку задачи остаётся рабочим и задокументированным — он единственный, если
потребитель отказался от привязки.

Побочно закрывается и «нужен ли `ExecutionService`»: сценарии 2 и 4 — это чтение состава дела
из процессора, то есть первые его потребители. Состав операций — этап 2. Ограничение остаётся
прежним: из `process` подзадачи состав дела не читают, миллион подзадач дадут миллион запросов;
в `collect` это один вызов.

## Последствия

- **Связь N:M выразить нельзя.** Задача, которую по смыслу вызвали два колбэка, запомнит одного
  создателя — того, в чьей обработке её создали. Обходные пути прежние: нагрузка или реестр
  корреляции. Если N:M однажды понадобится, это вариант C, то есть новая таблица, а не новая
  колонка.
- **Визуализация собирает рёбра по двум правилам**: дети раскрытия — по `parent_attempt_id`,
  остальные — по `origin_*`. Это обязано быть в комментарии к колонке, иначе выглядит как
  недозаполненные данные.
- **Миллион подзадач не визуализируется.** Отрисовка обязана сворачивать: «задача → группа →
  1 000 000 подзадач (999 998 `SUCCEEDED`, 2 `FAILED`)». Ещё один довод не хранить миллион рёбер
  ради картинки, которая их никогда не показывает.
- **Указатель полиморфный и без внешнего ключа.** Внешних ключей в схеме нет и быть не может
  ([0020](0020-partitioning.md)), целостность на коде — как везде. Но `origin_type` — это
  discriminator, и запрос «прочитай создателя» ветвится по нему.
- **Новая тихая потеря связи.** Явно переданное чужое дело или отказ от привязки убирают не только
  общее дело, но и указатель. Ошибки не будет — место этой ловушки
  в [consumer-contract.md](../consumer-contract.md), рядом с потерей дела при смене потока.
- **[0038](0038-execution-aggregate.md) отвергал черновик `caused_by_*` — и это не отмена того
  отказа.** Тот черновик шёл связкой с полем `metadata` и сквозным `correlationId`, а общей их
  ошибкой 0038 назвал «навешивали поля на существующие сущности, вместо того чтобы назвать
  недостающую». Сущность названа и существует; указатель поверх готового агрегата не несёт ни
  контекста цепочки, ни идентификатора повода — только одно ребро. Отвергнут был **заменитель
  агрегата**, а не дополнение к нему.
- **Поиск по нагрузке коммуникаций так и не сделан.** Сценарий 3 требует глобального поиска
  по параметру, а белый список полей объявлен только для задач ([0016](0016-payload-search.md),
  [0037](0037-search-field-registry.md)): у коммуникаций есть лишь лукап по `request_id`. Пока
  сценарий обходится фильтром по `source` / `destination` внутри дела. Расширение реестра
  на коммуникации — отдельное решение; до первого релиза оно не ломающее, поэтому ждать его
  не обязано ни одно другое решение.
- **Схема перестала быть заблокированной.** Этап 1 плана работ был единственным, что держал этот
  вопрос, и держал справедливо: колонки живут в первой же миграции, а не доклеиваются потом.

## Связанные решения

- [0038](0038-execution-aggregate.md) — агрегат, внутри которого живут эти рёбра, и черновик
  `caused_by_*`, отвергнутый там как заменитель агрегата.
- [0040](0040-communication-correlation.md) — реестр корреляции; ребро, которое он подразумевал,
  получает колонку.
- [0047](0047-children-belong-to-attempt.md) — иерархия раскрытия, которая остаётся на попытках
  и в указатель не попадает.
- [0039](0039-execution-partitioning.md) — партиционирование, из которого следует инвариант
  «создатель в той же партиции».
- [0056](0056-execution-ref.md) — явная передача дела, единственный способ увести ребёнка
  из партиции создателя и тем отменить связь.
- [0041](0041-cancellation-on-root.md) — прецедент колонок только на `tc_task`
  и `tc_communication`.
- [0055](0055-communication-exchange-storage.md) — обмен в строке попытки: тот же довод «связь
  не N:M, значит колонками», и данные, до которых указатель даёт дорогу.
- [0022](0022-batch-data-placement.md) — `task_id` и `batch_id`, одна из трёх уже существующих
  копий иерархии.
