# 0017. Постановка задачи в транзакции потребителя

- **Дата:** 2026-08-27
- **Статус:** принято

## Контекст

Типичный сценарий постановки: потребитель в своём сервисе создаёт бизнес-данные и тут же ставит
задачу на их обработку.

```java
@Transactional
public void createOrder(OrderRequest request) {
    Order order = orderRepository.save(...);
    taskService.submit("order-sync", new SyncParams(order.id()));
}
```

Если стартер записывает задачу **своим** соединением, вне транзакции потребителя, возникает
классическая проблема двойной записи, причём в обе стороны:

- воркер подхватывает задачу раньше, чем закоммитился заказ, и не находит его в БД;
- транзакция потребителя откатывается, а задача остаётся и будет вечно падать на несуществующих
  данных.

## Рассмотренные варианты

### A. Писать в текущую транзакцию потребителя — выбрано

Задача появляется атомарно с бизнес-данными: либо оба есть, либо ни одного.

### B. Отдельная транзакция (`REQUIRES_NEW`) — отвергнуто

Задача создаётся немедленно и не зависит от исхода транзакции потребителя. Ровно та проблема,
которую надо избежать.

### C. Настраивается при постановке — отвергнуто

Гибко, но неверный выбор даёт плавающие ошибки: задача выполняется «иногда раньше, чем нужно»,
в зависимости от нагрузки. Отладка такого стоит дороже, чем гибкость.

## Решение

Стартер записывает задачу **в текущую транзакцию потребителя**. Таблица задач тем самым работает
как outbox: задача становится видимой воркеру ровно в момент коммита бизнес-данных.

## Последствия

- **Стартер использует `DataSource` потребителя и не заводит собственный пул соединений.** Иначе
  он физически не сможет попасть в его транзакцию. Это ограничение на автоконфигурацию, а не
  пожелание.
- Задача, поставленная в откатившейся транзакции, исчезает вместе с ней. Это и есть желаемое
  поведение, а не потеря.
- Долгая транзакция потребителя задерживает старт задачи: пока нет коммита, воркер задачи не видит.
  Ожидаемо и правильно, но потребителя стоит об этом предупредить.
- Метод постановки не может вернуть ничего о ходе выполнения — на момент возврата задача ещё
  не существует для остальной системы. Возвращается только идентификатор.
- Постановка вне транзакции работает как обычно, в режиме autocommit. Специального кода
  не требует.
- Поллер работает в своих потоках и своими транзакциями — на него это решение не влияет.
