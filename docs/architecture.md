# taskcomm: как устроен и как им пользоваться

> **Статус документа.** Проект в начальной стадии: собран скелет, доменного кода ещё нет.
> Здесь описан **целевой дизайн** — то, каким проект спроектирован. Каждое утверждение опирается
> на принятое решение в [журнале ADR](adr/README.md); там же лежат отвергнутые варианты и причины.

---

## 1. Что это

Spring Boot стартер, который берёт на себя две вещи, обычно пишущиеся в каждом приложении заново:

**Таск-менеджмент.** Вы описываете, что нужно сделать над множеством бизнес-объектов, и как
обработать один объект. Стартер отвечает за персистентность, порядок, повторы при ошибках,
разбиение работы на части, распределение между экземплярами приложения и наблюдаемость.

**Коммуникации с внешними системами.** Вы описываете, как отправить сообщение в конкретную внешнюю
систему и как обработать пришедшее от неё. Стартер отвечает за то же самое плюс дедупликацию
повторных доставок и ограничение скорости.

Обе подсистемы горизонтально масштабируются: несколько экземпляров приложения делят работу
между собой, ничего не настраивая.

### Чем отличается от готовых решений

- **Три уровня работы вместо одного.** Задача может быть неделимой, может разбиваться на подзадачи,
  а может — на группы подзадач, где группа существует, чтобы один раз сходить во внешнюю систему
  за данными сразу для всей группы.
- **Никакой дополнительной инфраструктуры.** Только PostgreSQL, который у вас и так есть.
  Ни брокера, ни Redis, ни ZooKeeper.
- **Коммуникации как первоклассная сущность**, а не «задача, которая что-то отправляет».

## 2. Как подключить

Два артефакта: `taskcomm-autoconfigure` со всем кодом и `taskcomm-spring-boot-starter`, который
не содержит ни одного класса и служит только набором зависимостей.

```groovy
implementation 'xyz.avasilev:taskcomm-spring-boot-starter:2.0.0'
```

Настройки — под префиксом `taskcomm.*`:

```yaml
taskcomm:
  enabled: true
  task:
    enabled: true
    retry:
      max-attempts: 3
  communication:
    enabled: true
  rest:
    enabled: true
    base-path: /api/taskcomm
```

Каждая подсистема выключается своим `enabled: false`. Любой бин стартера можно заменить своим —
все объявлены под `@ConditionalOnMissingBean`.

**Стартер не включает за вас глобальные механизмы Spring.** Ни `@EnableScheduling`,
ни `@EnableAsync`, ни `@EnableTransactionManagement` — они меняют поведение всего приложения,
а не только нашей подсистемы. Свой планировщик стартер создаёт сам, отдельным бином.

**Стартер использует ваш `DataSource` и не заводит собственный пул.** Это не деталь реализации,
а следствие того, как ставятся задачи (см. раздел 6).

Схему БД вы применяете сами — своим Liquibase или своим инструментом миграций (раздел 11).

## 3. Понятия

| Термин | Что это |
|---|---|
| **Задача** (`Task<P>`) | Что нужно сделать над множеством бизнес-объектов. `P` — параметры операции: диапазон дат, контрагент, режим |
| **Группа** (`TaskBatch<B>`) | Часть задачи. `B` — параметры группы. Существует, чтобы сходить во внешнюю систему один раз на всю группу |
| **Подзадача** (`TaskUnit<U>`) | Обработка **одного** бизнес-объекта. `U` — сам объект. Минимальная единица работы и повтора |
| **Процессор задачи** (`TaskProcessor<P>`) | Ваш код. Запечатанный базовый контракт с тремя наследниками |
| **Коммуникация** (`Communication<P>`) | Обмен с внешней системой. **Атомарна**, на части не делится |
| **Процессор коммуникации** | Ваш код. Фактически адаптер к одной внешней системе |
| **Тип задачи** (`taskType`) | Строка, по которой ищется процессор. Ключ всей системы |
| **Аренда** | Право экземпляра приложения работать над строкой в течение ограниченного времени |

**Ключевое ограничение модели:** стартер не знает и не должен знать, какие бизнес-объекты вы
обрабатываете. Полезная нагрузка — параметр типа, для стартера непрозрачный. Отсюда и имена: они
называют единицу работы и её место в иерархии, а не содержимое.

Обратите внимание, что **нагрузки трёх уровней — разных типов**. Задача «синхронизировать заказы
за март» несёт диапазон дат; её подзадача несёт один заказ. Это не одно и то же, и в API это
выражено разными параметрами типа.

**Иерархии у задач и коммуникаций намеренно разные:** `Task → TaskBatch → TaskUnit` против плоской
`Communication`. Коммуникация неделима, и повтор применяется к ней целиком. `CommunicationBatch`
и `CommunicationUnit` не существуют и не появятся.

## 4. Три контракта процессора

Форму работы выбирает тип задачи, а не конфигурация. Контракты образуют запечатанную иерархию —
воркер разбирает её через pattern matching без ветки `default`, чтобы появление четвёртого
контракта ломало компиляцию везде, где его надо учесть.

### Плоская задача

Задача выполняется целиком, подзадач нет.

```java
@Component
public class ReportProcessor implements SimpleTaskProcessor<ReportParams> {

    @Override public String taskType() { return "monthly-report"; }

    @Override
    public void process(Task<ReportParams> task) {
        // одна операция от начала до конца
    }
}
```

**Когда:** разовая операция без естественного деления. Сформировать отчёт, пересчитать агрегат,
выгрузить один файл.

### Задача с подзадачами

Задача раскрывается в подзадачи, каждая обрабатывает один объект.

```java
@Component
public class OrderSyncProcessor implements UnitTaskProcessor<SyncPeriod, OrderRef> {

    @Override public String taskType() { return "order-sync"; }

    @Override
    public void expand(Task<SyncPeriod> task, Emitter<OrderRef> units) {
        orderRepository.streamIds(task.payload().from(), task.payload().to())
                .forEach(id -> units.emit(new OrderRef(id)));
    }

    @Override
    public void process(TaskUnit<OrderRef> unit) {
        // обработка одного заказа
    }
}
```

**Когда:** работа над множеством объектов, где каждый обрабатывается независимо и должен
повторяться отдельно от остальных.

### Задача с группами

Задача раскрывается в группы, каждая — в подзадачи.

```java
@Component
public class PriceUpdateProcessor
        implements BatchTaskProcessor<UpdateParams, SupplierBatch, ItemPrice> {

    @Override public String taskType() { return "price-update"; }

    @Override
    public void expand(Task<UpdateParams> task, Emitter<SupplierBatch> batches) {
        suppliers.forEach(s -> batches.emit(new SupplierBatch(s.id())));
    }

    @Override
    public void expandBatch(TaskBatch<SupplierBatch> batch, Emitter<ItemPrice> units) {
        // один поход во внешнюю систему на всю группу
        PriceList list = supplierApi.fetchPriceList(batch.payload().supplierId());
        list.items().forEach(i -> units.emit(new ItemPrice(i.sku(), i.price())));
    }

    @Override
    public void process(TaskUnit<ItemPrice> unit) {
        // применение одной цены; данные уже внутри unit
    }
}
```

**Когда:** обработка каждого объекта требует общих данных, которые дорого получать поштучно.
Прайс-лист на тысячу позиций, справочник курсов, пакетный ответ внешнего API.

**Важно:** данные, полученные при раскрытии группы, **материализуются в нагрузку каждой подзадачи**.
Подзадача самодостаточна — её повтор через месяц не требует ни группы, ни задачи. Отсюда `B` —
это параметры группы, а не собранные данные.

Если общие данные объёмны и дублировать их дорого, заведите **своё** хранилище, ключуя по
`unit.batchId()` — стартер такого хранилища не предоставляет, и это осознанное решение.

## 5. Жизненный цикл

### Каскад раскрытия

```
Task ──expand──> TaskBatch[] ──expandBatch──> TaskUnit[] ──process──> готово
Task ──expand──> TaskUnit[]  ──process──────> готово
Task ──process──────────────────────────────> готово          (плоский контракт)
```

Каждый переход асинхронный. Подзадачи создаёт **процессор**, а не вы при постановке: через API
задача ставится параметрами, миллион объектов в неё не передаётся.

Порождённое отдаётся в `Emitter`, а не возвращается списком. Стартер копит в буфере и вставляет
пачками, каждый сброс — своя короткая транзакция. Ни миллион строк в памяти, ни миллион строк
в одной транзакции.

`Emitter` действителен только внутри вызова `expand`. Сохраните ссылку в поле и вызовите позже —
получите `IllegalStateException`, а не тихую порчу данных.

### Статусы

**Подзадача:** `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `SKIPPED`.

**Задача и группа:** те же плюс `AWAITING_CHILDREN` и `WARNING`.

```
PENDING ──захват──> RUNNING ──> AWAITING_CHILDREN ──> SUCCEEDED | WARNING | FAILED | SKIPPED
   ^                   │
   └───повтор──────────┴──────────────────────────> CANCELLED
```

- `RUNNING` — захвачено и работает: плоская задача выполняется, задача с детьми раскрывается.
- `AWAITING_CHILDREN` — раскрытие закончено, дети в работе, родитель **аренду не удерживает**.
  У плоской задачи не встречается.
- `WARNING` — задача дошла до конца, но часть подзадач исчерпала попытки. Через REST можно
  перезапустить **только упавшие**.

Отдельных статусов «ждёт повтора» нет: это `PENDING` с `next_attempt_at` в будущем.

### Факты вместо статусов

Часть состояний выражена не статусом, а колонкой-фактом. Это сознательный приём: восемь статусов —
потолок, дальнейшие состояния добавляются так.

| Колонка | Что означает |
|---|---|
| `expanded_at` | Раскрытие дошло до конца. Не статус, а факт |
| `cancel_requested_at` | Отмена запрошена. Ортогонален статусу, работает в любой фазе |
| `status_description` | Причина терминального статуса — общая для `SKIPPED` и `CANCELLED` |

`expanded_at` решает случай, который иначе неразличим: раскрытие может **успешно** вернуть ноль
подзадач (заказов за март не было), и это не ошибка. «Упало на раскрытии» определяется по
`expanded_at IS NULL`, а не по отсутствию детей.

### Правила завершения

- Дети доступны для работы только после `expanded_at` **своего непосредственного** родителя.
  Подзадачи группы идут в работу, как только раскрыта эта группа.
- Родителя в терминальный статус переводит воркер, завершивший последнего ребёнка; застрявших
  добирает подстраховочный поллер. Переход идемпотентен.
- Прогресс **вычисляется агрегатом** по детям, денормализованных счётчиков нет.
- Есть `SKIPPED` среди детей — родитель `SUCCEEDED`. **Все** дети `SKIPPED` — родитель `SKIPPED`.
  Собственная отмена родителя перебивает агрегат.

### Пропуск

Процессор может сообщить «делать нечего» — это не успех и не ошибка:

```java
@Override
public void process(TaskUnit<OrderRef> unit) {
    if (alreadySynced(unit.payload())) {
        context.skip("заказ уже синхронизирован");
        return;
    }
    ...
}
```

`expand` и `process` остаются `void`: успех выражен отсутствием исключения, второй канал для того же
факта не нужен. Пропуск засчитывается, только если метод вернулся нормально; исключение перебивает
пропуск; причина обязательна и сохраняется.

### Отмена

Отмена **кооперативная**. Прервать ваш код стартер не может и не будет.

- Новые единицы работы не захватываются.
- Дети в `PENDING` уходят в `SKIPPED`.
- Дети в `RUNNING` **доигрывают и пишут свой настоящий исход** — подзадача, успешно завершившаяся
  после отмены, станет `SUCCEEDED`, а не `CANCELLED`. Её побочные эффекты существуют, и скрывать
  их опасно.

Если обработка длинная, спрашивайте контекст, нужно ли продолжать. Тот же признак истинен и при
отмене, и при потере аренды — для вашего кода это один и тот же случай.

## 6. Что гарантирует движок

### Захват и аренда

Работа между экземплярами делится через `SELECT ... FOR UPDATE SKIP LOCKED`. Транзакция захвата
закрывается сразу — процессор работает **вне** её, соединение из пула не занято вашим кодом.

Право на работу удерживается **арендой**: строка помечается `RUNNING`, ставится `locked_until`
и уникальный токен. Долгие операции аренду продлевают. Продлевает не воркер, а отдельный поток
на экземпляр, одним запросом на такт — воркер не может продлить себя, его поток занят вашим кодом.

Есть верхний предел выполнения — счётчик продлений. Дошли до предела, перестали продлевать, аренда
истекла, строку подобрал поллер. Превышение предела — **обычная неуспешная попытка**, без особого
статуса.

### At-least-once, не exactly-once

**Ваш код может быть вызван дважды для одного и того же объекта.** У живого, но медленного воркера
аренда может истечь, и работу подберёт другой; при превышении предела выполнения это происходит
гарантированно.

Обработка обязана быть идемпотентной. Это не пожелание, а условие корректной работы.

### Повторы

- Повторяются **только упавшие подзадачи**, группа целиком не перезапускается.
- Backoff экспоненциальный и обязательно с джиттером — иначе тысяча подзадач, упавших из-за
  недоступности внешней системы, проснётся одновременно и положит её повторно.
- Исчерпав попытки, подзадача уходит в `FAILED`, задача получает `WARNING`.

### Порядок

FIFO по времени готовности, приоритетов нет. Одна задача с миллионом подзадач займёт воркеров
и задержит остальные — это известная цена простоты.

## 7. Как ставить задачи

```java
@Transactional
public void createOrder(OrderRequest request) {
    Order order = orderRepository.save(...);
    taskService.submit("order-sync", new SyncPeriod(...));
}
```

**Постановка пишется в вашу текущую транзакцию.** Таблица задач работает как outbox: задача
становится видимой воркеру ровно в момент коммита ваших бизнес-данных. Откатилась транзакция —
исчезла и задача.

Отсюда следует, что стартер использует ваш `DataSource` и не может завести собственный пул.
И отсюда же — долгая транзакция задерживает старт задачи: пока нет коммита, воркер её не видит.

## 8. Коммуникации

Направление — **тип, а не значение поля**:

```java
public sealed interface Communication<P> {
    record Inbound<P>(String source, P payload)       implements Communication<P> {}
    record Outbound<P>(String destination, P payload) implements Communication<P> {}
}
```

Невалидную коммуникацию собрать нельзя в принципе, а процессор разбирает направление через pattern
matching.

Процессор ищется по внешней стороне: `source` для входящих, `destination` для исходящих. Фактически
**один процессор = один адаптер к одной внешней системе**. Если в систему уходят сообщения разных
видов, разбирается с этим сам процессор.

**Входящие создаёте вы** — из своего контроллера или слушателя. Собственного приёмного endpoint
стартер не даёт.

### Дедупликация делится пополам

Вы извлекаете ключ идемпотентности — формат знаете только вы: заголовок, `messageId`, хеш.
Стартер гарантирует, что второй коммуникации с таким ключом не появится.

```java
communicationService.receive("supplier-b", messageId, payload);
```

Ключ необязателен: не передали — дедупликации нет. И она **не отменяет** требования
идемпотентности: дедупликация защищает от повторной доставки внешней системой, идемпотентность —
от повторного выполнения по истёкшей аренде. Разные проблемы, обе есть.

### Порядок и скорость

Порядок выполнения **не гарантируется**, всё идёт параллельно.

Ограничение скорости встроено и настраивается на процессор. Лимит действует **на экземпляр
приложения** — свойство так и называется, `rate-limit-per-instance`, потому что три экземпляра
с лимитом 10 дадут внешней системе 30.

Размыкателя (circuit breaker) нет — сознательно отложен.

## 9. Поиск и REST API

Пути под `taskcomm.rest.base-path`, вся подсистема выключается свойством.

**Стартер не объявляет `SecurityFilterChain` и вообще не трогает Spring Security.** Он отдаёт бин
`RequestMatcher` со своими путями — впишите его в свою конфигурацию одной строкой. Из коробки API
не защищён, и это ваша ответственность.

Состав: чтение с фильтрами, поиск по нагрузке, создание, перезапуск упавших подзадач, отмена,
сводка по типам и признак осиротевшей задачи.

### Поиск по нагрузке

Только по **белому списку полей**, который объявляет процессор:

```java
@Override
public List<SearchableField> searchableUnitFields() {
    return List.of(
            SearchableField.string("order_id", "$.orderId"),
            SearchableField.string("customer_inn", "$.customer.inn"));
}
```

```
GET /api/taskcomm/units?payload.order_id=A-1024
```

Три уровня объявляются раздельно: `searchableTaskFields()`, `searchableBatchFields()`,
`searchableUnitFields()` — нагрузки уровней разного типа.

**Тип задачи в запросе не обязателен.** Типы выводятся из реестра по имени поля: ищем во всех, кто
это поле объявил. Так работает сценарий «найти всё, что делалось с этой сущностью, независимо
от типа операции» — изменение заказа и отмена заказа найдутся одним запросом.

Ограничения, которые надо знать:

- **Одно имя поля — один тип значения во всём реестре.** Разные пути у разных типов нормальны,
  разные типы значения — нет. Конфликт роняет приложение при старте.
- Несколько полей в запросе сужают множество типов до объявивших **все** указанные.
- Поле не объявлено никем — `400` со списком известных имён.
- Индексы под поиск стартер в проде **сам не создаёт**: при старте проверяет наличие и пишет
  предупреждение с готовым DDL.

**Бизнес-ключа у сущностей нет.** Идентификатор объекта обязан лежать в нагрузке и быть объявлен
в белом списке — иначе найти работу по нему будет нечем.

## 10. Наблюдаемость

- **Метрики** Micrometer — `optional`: нет Micrometer'а у вас, стартер молчит и ничего не тянет.
  Длина очереди, время выполнения, доля ошибок, число повторов — всё с разбивкой по типу задачи,
  плюс число осиротевших.
- **Health indicator** для движка.
- **Структурные логи**: `tc.taskId`, `tc.batchId`, `tc.unitId`, номер попытки в MDC. Префикс
  настраивается, по умолчанию `tc.` — потому что вам прямо разрешено класть в MDC своё,
  и столкновение имён иначе неизбежно.

**Кладите свой бизнес-идентификатор в MDC сами**, обычным `MDC.put(...)` внутри процессора. Стартер
его не тронет и снимет вместе со своими ключами — MDC восстанавливается снимком, а не поимённой
очисткой, поэтому утечки в пул потоков не будет.

Учтите: в строках, которые стартер пишет **вне** вызова процессора — захват, истечение аренды,
закрытие задачи, — вашего идентификатора не будет. Взять его там неоткуда.

## 11. Схема БД и эксплуатация

### Устройство

- Таблицы с префиксом `tc_`, в **вашей** схеме — имя схемы в SQL не хардкодится.
- Идентификаторы — **UUIDv7**: упорядочены по времени, объём работы наружу не раскрывают.
- Нагрузка — `jsonb`, сериализация Jackson. Java-тип восстанавливается из дженерика процессора,
  полное имя класса в БД не хранится.
- Перечислимые колонки — `text` с `CHECK`, а не нативный enum.
- В каждой таблице `created_at` и `updated_at` сразу после `id`. `updated_at` проставляет
  приложение; heartbeat её **не трогает** — продление аренды не является изменением состояния.
- Каждая колонка снабжена комментарием на русском языке.

### Партиционирование

Все таблицы партиционированы по времени. Очистка — `DROP` партиции, а не `DELETE`.

**Ключ партиционирования для всей иерархии задач — время создания задачи.** У групп и подзадач это
денормализованная колонка `task_created_at`, а не их собственное время: задача, созданная 31 января,
может раскрыться 1 февраля, и иерархия не должна разрываться между партициями.

Отсюда: **внешних ключей между задачей, группами и подзадачами нет** — партиционирование их
не допускает. Целостность обеспечивается кодом.

Партициями управляет стартер — это единственное исключение из правила «стартер не выполняет DDL
в проде»: без заранее созданной партиции вставка падает и система встаёт.

**Удаление старых партиций выключено по умолчанию** и проверяет, что в партиции нет незавершённых
записей. Задача, созданная в январе и всё ещё выполняющаяся в апреле, лежит в январской партиции.

### Миграции

Стартер везёт **и** Liquibase-changelog, **и** голый DDL. На Liquibase включается одной строкой:

```xml
<include file="db/changelog/taskcomm/master.xml" relativeToChangelogFile="false"/>
```

Changelog читается прямо из jar, миграции попадают в вашу `DATABASECHANGELOG`. Обновили версию
стартера — новые changeSet'ы применятся при следующем старте.

Правила, за которые платите дисциплиной:

- **Выпущенный changeSet неприкосновенен** — правка ломает контрольную сумму у всех, кто его
  накатил.
- **Миграции только аддитивные**: при rolling update новая схема какое-то время работает
  со старым кодом.
- Миграция, требующая ручного вмешательства, — мажорная версия.

При старте стартер проверяет свои таблицы и колонки и **падает с внятным сообщением**, если схема
не соответствует версии.

`taskcomm.schema.initialize` (`never` | `embedded` | `always`) — для тестов и локальной разработки,
продовую схему он не ведёт.

### Ограничение

**Одна схема БД обслуживает одно приложение.** Реестр процессоров считается исчерпывающим описанием
всех типов задач в схеме. Несколько сервисов на одной БД разводятся по разным схемам. Нарушение
не обнаруживается автоматически — вы узнаете о нём по предупреждению про сотни «осиротевших» задач,
которые на самом деле чужие.

## 12. Эволюция: что нельзя менять

Задачи живут в базе дольше, чем один релиз вашего приложения. Часть изменений в вашем коде — это
изменение формата уже записанных данных.

**Контракт у существующего типа не меняется — заводится новый тип.** Порядок: клонировать процессор
под новым `taskType` с суффиксом версии, переключить постановку, пометить старый `@Deprecated`.

`@Deprecated` на классе процессора **блокирует постановку новых задач** этого типа; существующие
выполняются как обычно. Список устаревших типов громко печатается при старте — потому что в Java
эта аннотация значит «не используйте в коде», а у нас ещё и «не принимай задачи».

**Процессор не удаляется никогда.** Он нужен и после того, как перестал принимать задачи: из его
дженерика восстанавливается тип нагрузки, из него же берётся белый список полей для поиска
по истории. `@Deprecated` здесь — постоянное состояние, а не шаг к удалению.

Полный разбор с примерами и указанием, какие изменения обнаруживаются, а какие проходят молча, —
в [consumer-contract.md](consumer-contract.md). Читайте перед изменением любого публичного
контракта процессора.

## 13. Сценарии

**Массовая синхронизация.** «Синхронизировать заказы за март» — задача с подзадачами. Раскрытие
перечисляет заказы, каждый обрабатывается и повторяется независимо. Упало сто из миллиона — задача
в `WARNING`, через REST перезапускаются только упавшие.

**Пакетная выгрузка с предзагрузкой.** «Обновить цены по всем поставщикам» — задача с группами.
Группа на поставщика: один запрос прайс-листа вместо тысячи, данные материализуются в подзадачи.

**Разовая операция.** «Сформировать месячный отчёт» — плоская задача. Деления нет, повтор
применяется целиком.

**Интеграция с внешней системой.** Входящий webhook принимается вашим контроллером и кладётся как
входящая коммуникация с ключом идемпотентности — повторная доставка не создаст дубликат. Исходящие
уходят под ограничением скорости, чтобы не положить внешнюю систему.

**Разбор инцидента.** «Что случилось с заказом A-1024» — поиск по нагрузке без указания типа задачи
находит все операции над ним. Статус, число попыток и `status_description` объясняют исход;
`tc.unitId` из выдачи ведёт в логи.

**Миграция контракта.** Формат нагрузки изменился — заводится `order-sync-v2`, постановка
переключается, старый процессор помечается `@Deprecated` и доигрывает оставшееся. Метрика
незавершённых по типу показывает, когда старых задач не осталось.

## 14. Чего проект не делает

Осознанные не-goals — чтобы не искать того, чего нет:

- **Не хранит общие данные группы.** Нужно — заводите своё хранилище по `batchId`.
- **Не даёт приёмный endpoint** для входящих коммуникаций. Их создаёте вы.
- **Не гарантирует порядок** выполнения коммуникаций.
- **Не гарантирует exactly-once.** Только at-least-once.
- **Не трогает Spring Security** и не защищает свой REST.
- **Не выполняет DDL в проде**, кроме управления партициями.
- **Не унифицирует задачи и коммуникации.** Это две независимые реализации с намеренно
  дублирующимся кодом — они обязаны меняться независимо.
